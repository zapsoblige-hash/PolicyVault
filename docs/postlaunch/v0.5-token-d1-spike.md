# v0.5 token support — D1 research spike (working notes)

Status: **RESEARCH IN PROGRESS — NOTHING HERE IS FROZEN.** This document
answers the 2026-08-31 architecture addendum §17 questions with the
current upstream evidence available on 2026-09-01, and classifies every
claim as **SOURCE-VERIFIED** (read from authoritative source),
**SPEC-VERIFIED** (read from a published convention document),
**VM-PROVEN** (demonstrated by an isolated on-machine VM experiment), or
**SPECULATIVE**. Per the addendum, the v0.5 design does not freeze until
the load-bearing claims are VM-PROVEN.

Binding architecture constraints (addendum §3–§9, non-negotiable):

1. Covenant-ID/controller authorization AND hash-verified
   token-output/template pinning are BOTH required; either failing
   fails closed.
2. Per-asset descriptors/adapters live in the shared deterministic core.
3. Token value and KAS fee reserve are separate accounting domains.
4. Indexers/hosted services are non-authoritative at the financial
   boundary.
5. Issuer/controller trust properties are surfaced explicitly.
6. No protocol-level blessed-asset list; no forced migration.

## Q1 — What exact KCC/token model is current?

**SPEC-VERIFIED** (kaspanet/kccs, read 2026-09-01): the Kaspa ecosystem
standardizes conventions as KCCs. Current documents: KCC-0000 (index),
**KCC-0001** (covenant ABI: state codecs, entrypoints, continuation
validation), **KCC-0002** (authority schemes), **KCC-0020** (fungible
token covenant). The Toccata hard fork (June 2026) activated the
consensus substrate (covenants, tx v1, script pricing, ZK opcodes).

KCC-0020 in brief: tokens are UTXOs locked by covenant programs; a
"covenant family" is the transaction's inputs and continuation outputs
sharing one KIP-20 `covenant_id`. Token state is a `KCC20State` record —
`amount (int), owner (byte[32]), owner_scheme (byte), borrow_scheme
(byte), borrow_guard (byte[32]), extension_commitment (byte[32])`.
Transfers run through `transfer(next_states, witness)` on the leader
input and `transfer_delegator(witness)` on the rest; the leader
validates the complete shared transition (program, state, covenant
binding per KCC1) and must preserve the total token amount across the
family.

Notable spec gaps (each an explicit design input for us, not something
to paper over): KCC-0020 defines **no mint/burn entrypoints, no
decimals/denomination field, and no versioning/upgrade mechanism** —
issuance and denomination semantics live with the issuing covenant
design, i.e. they are per-asset trust properties (addendum §8).

## Q2 — How is token ownership represented?

**SPEC-VERIFIED**: by the `owner`/`owner_scheme` pair in `KCC20State`,
interpreted per KCC-0002 authority schemes: `p2pk-schnorr/v1 (0x00)`,
`p2pkh-schnorr/v1 (0x01)`, `p2pkh-ecdsa/v1 (0x02)`, `p2sh/v1 (0x03)`,
`covenant-id/v1 (0x04)`. The last is the one that matters for
PolicyVault: a token owned by `covenant-id/v1` is spendable when the
transaction includes an input belonging to that KIP-20 lineage — i.e. a
PolicyVault covenant instance can own tokens, and the token covenant
recognizes the PolicyVault input's participation (inter-covenant
communication) as the owner's approval.

## Q3 — What does covenant-ID ownership prove, and what does it not?

**SPEC-VERIFIED + SOURCE-VERIFIED**: `covenant-id/v1` approval "MUST
include a transaction input belonging to the KIP-20 lineage identified
by the authority value" — presence of the authorized lineage's input IS
the authorization. It proves *who/what controller authorizes the
spend*. It proves **nothing** about *which asset, which token program,
which transfer semantics, or which successor state* is being moved —
the token covenant's own leader logic enforces its family's rules, but
nothing in the ownership check tells the CONTROLLER (PolicyVault) that
the coin it is helping move is the intended asset under the intended
template. This is the addendum's dual-binding requirement, confirmed
against the current conventions.

## Q4/Q5 — Which introspection primitives can verify foreign token state/templates? Which hash-verified template APIs exist?

**SOURCE-VERIFIED** (`~/rusty-kaspa/crypto/txscript/src/`, the exact
tree our production kaspad v2.0.1 is built from): the engine exposes,
among others, `OpInputCovenantId` / `OpOutputCovenantId` (per-index
covenant identity), the covenant family context (`OpCovInputCount/Idx`,
`OpCovOutputCount/Idx`), the authorized-output context
(`OpAuthOutputCount/Idx`, `OpOutputAuthorizingInput`), and full
transaction introspection including `OpTxOutputAmount`, `OpTxOutputSpk`,
`OpTxOutputSpkLen`, **`OpTxOutputSpkSubstr`** and the input-side
equivalents (`OpTxInputSpkSubstr`, `OpInputAmount`, `OpTxInputDaaScore`,
…). `covenants.rs` implements the KIP-20 contexts
(`CovenantInputContext`, `CovenantSharedContext`, `CovenantsContext`).

**SPEC-VERIFIED**: KCC-0001 defines the template mechanism these
primitives can check: a continuation's redeem bytes are
`R_next = template.prefix || encoded_next_state || template.suffix`;
the output SPK is the version-0 P2SH envelope
(`OP_BLAKE2B OP_DATA_32 Blake2b(R_next) OP_EQUAL`); the **template
hash** is `Hash(LE64(len(prefix)) || prefix || LE64(len(suffix)) ||
suffix)` (BLAKE3-32). A verifier holding the expected prefix/suffix
(or their hash plus the revealed bytes) can therefore reconstruct and
byte-compare a foreign output's SPK — template verification without
trusting any indexer.

**NOT YET VM-PROVEN (required before freeze)**: an isolated experiment
in `tests/vm` must demonstrate a PolicyVault-side program that, inside
real TxScriptEngine execution, (a) locates the token family's
continuation output, (b) reconstructs its expected SPK from a pinned
template + expected state, (c) fails closed on every mismatch class in
§18. Compute/size budgets under script pricing must be measured, not
assumed.

## Q6 — Can PolicyVault pin a token covenant ID and an accepted transfer-template hash simultaneously?

**DESIGN TARGET, mechanically plausible per Q4/Q5 — must be VM-PROVEN.**
The intended v0.5 binding, per asset, is the pair
`(token covenant_id, accepted transfer-template hash(es))` carried in
the PolicyVault policy/descriptor; at spend time the PolicyVault
covenant (and, redundantly, the deterministic core before signing)
verifies BOTH against the actual transaction. Either check failing
fails closed. No implementation may ship on covenant-ID alone.

## Q7 — How are token quantity and successor state encoded?

**SPEC-VERIFIED**: quantity is the bare non-negative integer `amount`
in `KCC20State`; state is PushExplicit-encoded into the redeem script
between the template prefix/suffix; extended state is only present as
the 32-byte `extension_commitment` digest. No decimals field exists —
denomination display semantics are descriptor metadata (asset trust
property), never consensus.

## Q8 — How is conservation proven without trusting an indexer?

**SPEC-VERIFIED** for the token side: the KCC-0020 leader must preserve
the family's total amount; a controller verifying the transition can
re-derive per-output amounts from the revealed state bytes it template-
verifies (Q5) and check the sum itself. **DESIGN TARGET** for
PolicyVault: the deterministic core recomputes token conservation from
transaction bytes alone (inputs' prior states + outputs' next states),
exactly as it does KAS conservation today — indexers remain display-
only (addendum §7). VM proof required.

## Q9 — What KAS fee reserve is required alongside token value?

**SPEC-VERIFIED (consensus generality)**: every transaction still pays
KAS fees under mass/script-pricing rules; token UTXOs also carry a KAS
amount (dust/storage floor). **DESIGN TARGET**: v0.5 vault accounting
models two domains — protected token amount AND the KAS carried/spent
by token outputs + fees — with the existing v0.4 fee-reserve design as
the KAS-side starting point. Token budgets never pay fees; fee reserve
never counts as token value (addendum §6). Exact floors/budgets must be
measured in the VM/live probes.

## Q10 — Compute-unit, script-size, sig-op, mass, standardness limits?

**OPEN — measurement required.** Script pricing (Toccata) changed the
cost model; the D1 probes must record actual compute-unit consumption
of template reconstruction + state parsing at realistic sizes, plus
mempool standardness for the transaction shapes v0.5 needs. No numbers
are asserted here until measured on our node.

## Q11/Q12 — Issuer/controller powers; representable in descriptors?

**SPEC-VERIFIED**: KCC-0020 itself grants no issuer powers — but real
assets are issued by covenants whose OWN programs may mint, freeze,
migrate, or otherwise retain authority; `borrow_scheme`/`borrow_guard`
and `extension_commitment` are exactly where asset-specific authority
can live. **DESIGN TARGET**: the per-asset descriptor (shared core)
carries declared issuer powers (mint/burn/freeze/blacklist/upgrade/…)
as explicit trust properties surfaced in explain output, compliance
exports, and UI (addendum §8). A descriptor cannot *discover* powers it
was not told about — descriptor authorship/verification methodology is
an open design question for D2 (candidate answer: derive from the
issuing covenant's published template set; verify against chain bytes).

## Q13 — Exact hostile substitutions to reject

The §18 matrix, mapped to mechanism (all must be VM-PROVEN before any
implementation claim): wrong token (covenant_id mismatch), wrong
template (template-hash mismatch), wrong controller (family/authorizing
input mismatch), altered amount (state-bytes mismatch), hidden extra
recipient/output (family enumeration + output-count checks), ±1 atomic
unit conservation, KAS-fee manipulation (KAS-domain accounting), token
budget charged for fees / token value consumed as fee reserve
(cross-domain checks), stale token state (outpoint/lineage binding),
mismatched successor state, unsupported token version (fail closed),
malicious/malformed/downgraded descriptor (descriptor hash pinning +
closed schemas), issuer-property omission (descriptor completeness
rules), indexer/API disagreement (chain-bytes-only verification),
cross-asset substitution (per-asset binding), replay/idempotency
(existing pipeline discipline), browser/mobile/CLI parity (existing
cross-runtime equivalence suite extended to descriptors).

## Q14 — Any server/indexer-mediated assumptions?

Current classification: **none may sit on the financial boundary.**
Candidate token discovery/display (which assets exist, balances for UI)
may be server-assisted (non-authoritative, addendum §7); every
financial-boundary fact (asset identity, template, amounts,
conservation, authorization) must derive from transaction/covenant
bytes verified deterministically. Any exception found during D2 must be
classified here explicitly — none is currently known or accepted.
