### Found and fixed this pass (classified, not hidden)

- **PRODUCTION CODE BUG — HD owner-op compute-budget under-commit.** The
  original assumption (recorded in the prior checkpoint) that `ownerControl`/
  `ownerRecover` could reuse `core/model/compute-budget-v7.js`'s budget
  model UNCHANGED was TRUE of the covenant bytes but FALSE of the
  sufficient compute budget: that model's base unit counts were calibrated
  against the ~9,636 B v0.7-payment redeem; the HD redeem is ~42,830 B
  (+33,194 B). Measured via the real engine (`v7_hd_sdk_integration.rs`):
  `ownerControl` (all 5 selectors) actually costs 498,705–498,778 units
  (the reused model alone selects budget 32 = 320,000 raw — **short by
  ~179,000 units, 18 committed budget units**); `ownerRecover` costs
  350,765 units (model alone selects 31 = 310,000 raw — **short by ~41,000
  units, 5 committed budget units**). Fixed with a measured, margined
  correction (`selectHdOwnerComputeBudgetV7`, `core/model/compute-budget-v7-hd.js`).
  Caught by the SDK-integration harness itself before any transaction was
  ever presented as usable — never shipped, never claimed sufficient
  without this fix.
- **TEST BUG — a delegateSetChildRoot2 SDK vector signed with the wrong
  key.** The level-2 delegating parent's leaf carried its OWN public key,
  but the finalize call signed with the level-1 grandparent's key. Caught
  immediately by the real engine (`VerifyError`); fixed by signing with the
  delegating leaf's own key, as the covenant requires
  (`requireLeafAuthorization(parentSig, pubkey(parentLeaf.slice(0,32)))`).
- **TEST BUG — a "revocation" vector that was actually a covenant-refused
  no-op.** `delegateSetChildRoot1/2` require `newChildRoot != current
  childRoot` (a real, intentional covenant guard against ambiguous no-op
  delegations); the original revocation vector targeted a leaf whose
  childRoot was ALREADY zero (no kids), so "revoking to zero" was a no-op
  the covenant correctly refused. Fixed by retargeting the vector to a leaf
  with a genuinely non-zero committed childRoot to revoke FROM.
- **ENVIRONMENT — a genuine shared-cargo-target hazard, not merely
  staleness.** `tests/vm/target` is a symlink into a target directory
  SHARED with other concurrent development lanes (multiple Wave 2 tracks
  build the SAME `[[bin]] pv_call_encoder` target name into the SAME
  shared path). Rebuilding immediately before use (the standing rule) was
  demonstrated INSUFFICIENT: `cargo build --bin pv_call_encoder` reported
  "Finished in 0.1-0.2s" (confirmed via `-v`: no `rustc` invocation at all)
  while the on-disk binary belonged to a different worktree's source and
  lacked this candidate's arm — 8/8 retries against the shared path all
  lost the race. Fixed structurally (not merely retried around) by
  building into a PRIVATE `--target-dir` (still reuses the shared
  dependency/registry cache; ~27 s cold, ~0.4 s incremental) and adding an
  optional `POLICYVAULT_PV_CALL_ENCODER_PATH` env override to
  `sdk/src/vault-builders-v4.js` (additive; every other caller's default
  behavior is byte-identical to before). Recorded here because the same
  hazard will recur for any future lane using the shared target for a
  `[[bin]]` target, not only this one.
- **PRODUCTION CODE BUG — `buildRootedVaultManifestV7`'s build-kind guard
  did not accept an HD owner-op build at all.** `sdk/src/vault-builders-v7-hd.js`'s
  owner-op builds carry `kind: "hdOwnerTransition"` (deliberately distinct
  from the payment profile's `"transition"`, so the two families can never
  be cross-routed by accident), but the manifest guard only widened the
  `contractVersion` check, not the `kind` check — an HD owner op's manifest
  could never be built at all. Fixed additively (the expected kind is now
  selected by contract version).
- **PRODUCTION CODE BUG — the HD owner-op builder never populated
  `accounting.kas.reserveConsumed`.** `verifyRootedVaultManifestV7`
  requires this field for every non-terminal action; its absence meant
  every HD owner-op manifest failed verification with a generic
  `reserveConsumed 0` mismatch. Fixed by computing it with the same
  formula the payment profile uses (`before.feeReserve > after.feeReserve
  ? before - after : 0`).
