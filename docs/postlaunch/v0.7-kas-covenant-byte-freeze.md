## 4. The exact freeze sequence (non-circular; cannot be skipped)

1. **Proposed bytes are reviewed as they are.** The reviewer examines the replacement identities of §3e (the exact image, public candidate, MCP tarball and this PROPOSED record are all inside the reviewed set). Nothing in the deployed code, generated assets or packaged labels changes after the review under the old identity.
2. **Matching PASS.** The owner relays the reviewer's PASS naming those exact identities. A PASS on different bytes, a source-only PASS, or a PASS with unresolved findings does not qualify.
3. **Attestation (records only).** The attestation `V0.7-KAS-COVENANT-BYTE-FROZEN` is recorded in the private canonical continuation notes and `CLAUDE.md` (owner-instruction files), naming the PASS and the exact identities of §1/§3e. The public copy of this record and the CANDIDATE labels are updated by the NEXT release under its own affected review; the attestation never edits the reviewed bytes.
4. **Release.** Under the parent's existing conditional authority the release proceeds (deployment → served verification → publication of the public successor and the MCP tarball). The freeze attestation does not deploy, does not create a mainnet treasury, does not force a migration, and does not supersede any frozen prior generation.
5. **Reopen only by process.** Any later change to the frozen bytes is a NEW additive profile or the established freeze-reopen process; never an in-place edit. The candidate pin test keeps failing on drift until it is replaced by a freeze pin test in the relabelling release.
