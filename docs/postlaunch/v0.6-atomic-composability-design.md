## 1. Proposed v0.6 covenant architecture

v0.6 = **the v0.5 token controller + ONE dedicated composition
entrypoint** (`tokenAtomicSwap`), everything else byte-for-byte the v0.5
semantics:

| element | v0.5 (frozen) | v0.6 (proposed) |
|---|---|---|
| lineage | one controller instance per (vault, accepted asset descriptor, accepted template); owns a KCC20 position by covenant-id ownership; KAS = fee reserve only | same |
| entrypoints | `tokenAgentSpend`, `ownerControl` (4 selectors), `ownerRecover` | same three, UNCHANGED, **plus `tokenAtomicSwap`** |
| foreign covenant inputs | forbidden on every entrypoint (`requireNoForeignCovenantInputs`) | forbidden on the three inherited entrypoints; **`tokenAtomicSwap` alone admits EXACTLY ONE foreign covenant family — the owner-approved pool — and nothing else (`requireOnlyApprovedCovenantInputs`)** |
| token binding | dual binding (pinned family id + hash-verified template, transaction-derived carriage) | same, applied to BOTH token notes in the swap (ours + the pool's reserve note) |
| pool binding (new) | — | pinned pool covenant id (consensus lineage, WHO) **and** hash-verified pool template + geometry via `readInputStateWithTemplate` on the pool input (WHICH); unknown pool → refuse |
| envelope (new) | — | max-in (cap + period budget in token units), min-out at the approved proceeds destination, owner floor price (`minKasOut·floorDen ≥ amountIn·floorNum`), bounded protocol-fee output to the pool's pinned fee key, exactly N outputs each with a role (no hidden output), no other covenant input, our note's KAS carry never leaks, fee-reserve consumption bounded, successor value pinned |
| signature model (new) | checkSig | **in-covenant SIGHASH_ALL gate** on the composition entrypoint (trailing type byte must be 0x01) — a SINGLE/NONE/ANYONECANPAY authorization of a composed transaction is refused by consensus, not only by wallet policy |
| state | boundVaultId, feeReserve, paused, agentRoot, policyNonce | same (+ optional `swapNonce`, see §14) |
| policy leaf | token-agent leaf (125 B) | same leaf reused for the amount-in cap/budget; **swap profile** (approved pool id + pool template hash/geometry + pair + floor + fee bound + proceeds destination) pinned as template constants in the probe and as an **owner-policy swap leaf** in the production design (§7) |

Prefer NO change to v0.5: none is made. v0.6 is additive; existing v0.5
vaults keep working forever and are never forced to migrate.

## 2. Exact delta in authority from v0.5

Under v0.5 a delegate can: move ≤ cap/budget tokens to an allowlisted
P2PK recipient; consume ≤ `agentMaxFeePerTx` of the fee reserve. Under
v0.6 the delegate can ADDITIONALLY: give up ≤ cap/budget tokens **to the
approved pool's reserve note** in exchange for **≥ minKasOut KAS at the
approved proceeds destination**, where minKasOut respects the owner floor,
in ONE atomic transaction that also contains exactly one approved pool
covenant input/successor and one bounded protocol-fee output. The
delegate can NOT: compose with any other covenant family, pay proceeds
elsewhere, add outputs, leak KAS from the token note or the reserve
beyond the fee bound, exceed the token caps, change policy state, or sign
with a non-ALL sighash. The owner's break-glass powers and the v0.5
entrypoints are unchanged. **Nothing in v0.6 gives PolicyVault, the
server, or any hosted component authority**: the delegate key signs; the
covenant enforces; the pool's own covenant enforces the pool's math.

## 5. Transaction shape, sighash / PSKT model, deadline semantics

- **Shape:** one Kaspa v1 transaction, 4 covenant inputs (+ optional plain
  fuel input if the owner prefers not to consume reserve), 6 outputs with
  fixed roles. Extending to BUY (KAS → tokens) and to token → token via
  two pools is a design question (§14), not proven here.
- **Who constructs:** any party (the agent's PolicyVault pipeline, or the
  venue via PSKT). PolicyVault verifies the EXTRACTED bytes; the PSKT is
  carriage, never evidence. rusty-kaspa 2.0.1 ships PSKT roles (Creator
  → Constructor → Updater → Signer → Combiner → Finalizer → Extractor,
  hex transport, per-input sighash type) and the wasm exposes `PSKT`,
  `SighashType`, `createInputSignature(tx, idx, key, sighashType)`.
- **Sighash:** the vault input MUST be SIGHASH_ALL — enforced in-covenant
  (gate) and in pre-sign policy. Under ALL the signature commits to every
  input outpoint, every output (value, script, covenant binding — the
  covenant binding is inside the v1 output hash, source-verified), lock
  time, subnetwork, gas, payload. ANYONECANPAY / SINGLE / NONE would let a
  composer move the signed input into another transaction; the gate makes
  this a consensus refusal. The pool input needs no signature (covenant
  logic); the token notes are covenant-id-witnessed.
- **Deadline / expiry:** Kaspa `lockTime` is a LOWER bound (valid at or
  after); consensus offers no "valid until". What IS consensus-enforced:
  the swap is bound to the EXACT pool outpoint it was built for — once
  anyone else spends the pool UTXO (any other trade), the stale
  transaction can never execute (its input is gone). A stale quote
  therefore fails closed at consensus by outpoint binding, and the
  pre-sign layer additionally refuses to request a signature after the
  manifest's DAA deadline. `tx.time ≥ quotedAt` may be added as a lower
  bound; an upper bound is not expressible and is not claimed.

## 6. Deterministic shared-core verification boundary (KCC20-first adapter architecture)

Dependency direction (binding): raw transaction/state → canonical parser
(`core/model/frozen-tx-v3`, `core/assets` KCC20 codec) → asset/protocol
descriptor (`policyvault-asset-descriptor/1` for tokens; NEW
`policyvault-swap-venue-profile/1` for pools: `{ venueId, poolCovenantId,
poolTemplateVmHashBlake2b256, poolPrefixLen, poolStateLen, poolSuffixLen,
poolStateLayout: "v6-cp-pool-state/1", protocolFeePk, protocolFeeBpsMax,
assetIn, assetOut, sourceProvenance }`, hash-pinned like descriptors, owner-
accepted per vault) → owner policy (swap leaf: approved profile hash,
pair, cap/budget reuse, floor price, max protocol fee, proceeds
destination) → `SwapIntentManifest/1` (the DEX design spec §3, now with
`shape: "S2"`) → deterministic explanation → local pre-sign verification
(`core/swap/verify`: decode bytes, prove the controller leg, prove the
pool leg identity, reproduce the envelope EXACTLY as the covenant does,
decode the pool note/state, check the quote-derived min-out against the
manifest, refuse non-ALL sighash) → external signer (KasWare / USI; sees
the swap block) → covenant enforcement (v0.6) → chain reconciliation
(successor observed; proceeds outpoint observed; `VERIFIED_OUTCOME`
coincides with `CHAIN_VERIFIED` for S2). No adapter re-implements KCC20;
`core/assets` is the only token codec; the pool profile is data, never
code, and unknown profiles fail closed.

## 11. Upstream production-venue maturity assessment

Unchanged from the DEX survey and reinforced by §10: no mainnet venue
publishes verifiable templates (KRON unpublished, seven template versions
in two months); the only published-template AMM is testnet-10 and
compiler-revision-sensitive; three incompatible "KCC20" layouts coexist
(the published fixture adds a fourth owner scheme); KCC-0020 has an open
supply-partition defect; Silverscript v1 is not final. **Therefore: freeze
the PRIMITIVE, not a venue.** The v0.6 design is venue-agnostic by
construction (profile data); the first production profile is admitted
only when a venue's pool + token source, compiler version and template
hashes are published and mechanically verifiable, and the owner
allowlists the exact hashes. KaspaKaha's testnet-10 reference is the
conformance fixture for the implementation phase and nothing more.

## 14. Unresolved risks / questions (owner decisions)

- **OQ-V6-1 BUY direction (KAS → tokens):** the v0.5/v0.6 controller holds
  KAS only as fee reserve; a buy needs a KAS source. Options: (a) a
  plain agent-owned KAS input (the vault gives up no vault KAS — the vault
  only RECEIVES tokens into its position; policy caps the agent's own
  spend?) ; (b) a v0.6 "KAS holdings" domain inside the controller
  (widens v0.5's KAS = fee-reserve-only rule); (c) composition with the
  v0.4.1 KAS vault (another covenant, another design). Recommendation:
  decide before I1; the SELL direction is proven and sufficient for a
  first freeze.
- **OQ-V6-2 proceeds destination kinds:** the probe pins one P2PK; the
  design allows an owner list (recipient tree) and a covenant-id
  destination (another PolicyVault controller receiving the output asset
  for token → token swaps). Which kinds are in the first freeze?
- **OQ-V6-3 multi-hop / two pools in one transaction:** not probed; the
  narrow rule admits exactly one foreign family — keep it that way for
  the first freeze.
- **OQ-V6-4 swap nonce / replay accounting:** UTXO consumption prevents
  replay; a per-swap nonce in state is optional bookkeeping. Keep out
  unless needed by the manifest.
- **OQ-V6-5 fee source:** reserve-paid (probe) vs agent fuel input; both
  fit the envelope.
- **OQ-V6-6 deadline:** accept "outpoint-bound + pre-sign DAA deadline"
  as the frozen semantics (no consensus upper bound exists).
- **Risk:** compiler-revision sensitivity of template hashes until
  Silverscript v1 is final; profile pins must be re-verified against
  on-chain scripts at profile acceptance.
- **Risk:** venue churn (KRON) — profiles are per pool instance and per
  template version; an upgraded venue simply fails closed.

## 15. Non-goals (permanent)

PolicyVault never runs pools, holds liquidity, market-makes, runs an order
book, custodies swap funds, signs user transactions, becomes the
counterparty, trusts hosted quotes/indexers/APIs as financial truth, or
generally permits arbitrary foreign covenants. Frozen v0.5 bytes are
never modified.
