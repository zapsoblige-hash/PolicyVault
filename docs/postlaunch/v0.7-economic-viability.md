# v0.7 organizational root — ECONOMIC VIABILITY (gate I4)

Consensus validity and standardness are necessary, not sufficient. This record
computes what a v0.7 ORGANIZATION actually pays in KAS network fees under
CURRENT mainnet fee policy (rusty-kaspa v2.0.1, post-Toccata), per transaction
shape, across every owner-set size, and over a month of realistic operation.
No economic threshold is invented: the curve is presented and the places where
cost is structural rather than incidental are named.

Tools: `tools/v7-fee-curve.js` (deterministic, `--json` for raw rows) over
`core/model/fee-mass-v7.js`. The shape table in that module is a MEASUREMENT
of finalized production bytes — regenerate with
`node sdk/tools/measure-v7-fee-shapes.js`, which rebuilds every shape through
the real SDK (real SilverScript compiler, real `pv_call_encoder` /
`pv_tx_probe`, real Schnorr signatures over TEST-ONLY keys), finalizes it, and
REFUSES if any fee it derives disagrees with the fee the SDK itself committed.
**Every number below is measured or derived from a measurement by the pinned
consensus arithmetic. Nothing is estimated.**

## Fee policy modeled (source: `~/rusty-kaspa`)

| rule | value | source |
|---|---|---|
| relay-fee floor | `fee_mass × 100 sompi` | `mining/src/mempool/check_transaction_standard.rs`, `config.rs` (`DEFAULT_MINIMUM_RELAY_TRANSACTION_FEE = 100_000 sompi/kg`) |
| fee mass | `max(compute_mass, ceil(transient_mass × 500_000/1_000_000))` | `consensus/core/src/mass/mod.rs` |
| compute mass | `bytes + 10 × Σ(2 + spk_bytes) + 100 × Σ(compute_budget)` | `MassCalculator::calc_non_contextual_masses` |
| transient mass | `4 × serialized bytes` | `consensus/core/src/mass/mod.rs` |
| storage mass (KIP-9) | `max(0, Σ C/out − …)`, `C = 10¹²`; a per-transaction VALIDITY bound of 500,000 grams, never a fee | `calc_storage_mass` |
| block-fit limits (post-Toccata) | compute 500,000 · transient 1,000,000 · storage 500,000 | `consensus/core/src/config/params.rs` |

The arithmetic is not re-implemented for v0.7: `core/model/fee-mass-v7.js`
carries the measured SHAPES and runs them through `core/model/fee-mass.js`, the
source-backed reimplementation the funds path already uses.

## The owner-set curve — 1-of-1 through 12-of-12

A root transaction's owner signature blob is a CONSTANT 780 bytes at every
threshold: abstaining slots carry the canonical placeholder, which is exactly
why the exact-fee freeze survives an out-of-band collection round. The
serialized size therefore does NOT move with M or N. What moves is the
committed compute budget, because the covenant runs one `checkSig` per ACTIVE
owner slot.

**Finding 1 — a bigger quorum is very nearly free.** Up to NINE active owners
the transaction is transient-dominated and the fee is EXACTLY FLAT: a 9-of-9
organization pays the same 0.026366 KAS per governance transaction as a 1-of-1
one. The crossover to compute domination is at TEN active owners, and even the
maximum 12-slot set costs only **+8.5 %** over 1-of-1. An organization is never
priced into a smaller, weaker owner set, which is the property that matters:
the covenant's security parameter and its cost are effectively decoupled.

## Per organization vs per vault

The root is created **once per organization** (0.002083 KAS) and each rooted
vault is created **once** (0.002083 KAS). After that:

- **root-only governance** (authorize, rotate, freeze, unfreeze, recover,
  succession) is charged **per organization**, not per vault — 0.0264 KAS;
- **a rooted owner operation** (root input + vault input + fuel) is charged per
  operation — 0.0461 KAS, which is very close to the two covenant redeems added
  together (root 11,545 B + vault 9,636 B, §12.3);
- **delegate spending never touches the root at all** — 0.0246 KAS, and its
  cost is independent of the owner set, the thresholds and the number of vaults.

The v0.7 controller costs **+363 B of redeem** on every delegate spend versus
the frozen v0.5 controller (measured, §12.3). At the transient-dominated relay
floor that is exactly 200 sompi per byte, so the organizational-root profile
adds **0.000726 KAS (+3.0 %) per ordinary spend** — the price of replacing a
single owner key with an M-of-N organization, paid on the operating path.

## THE SERIALIZATION POINT

`rootAction` is `#[covenant.singleton]`: one root input, one continuation
output, a strictly increasing nonce. Every transaction that needs owner
authority therefore **spends the same UTXO**, so:

- **all root-authorized operations of one organization are STRICTLY SERIAL.**
  Two owner operations cannot be in flight at once — the second would
  double-spend the root outpoint, and the loser must be rebuilt against the new
  root state and re-approved by the quorum. The organization's governance
  throughput is one root transaction per confirmation round, not per second.
  This is a deliberate property, not a defect: it is also what makes the root
  outpoint the freshness kill switch that invalidates every stale approval at
  once.
- **delegate spending is NOT serialized.** The agent path has no root input, so
  N vaults with N agents spend fully in parallel. The serial bound applies only
  to governance, which is exactly where a human quorum is the slower step
  anyway.
- **batching is architecturally permitted but NOT MEASURED.** The covenant's
  per-vault check is `exactly one input and one output of the pinned root
  family`, which several vaults in one transaction can satisfy simultaneously,
  and `policyvault-org-root-manifest/1` already models a list of vault
  operations. The SDK builds ONE vault operation per transaction today, so no
  batched shape was built or measured, and no batched saving is claimed here.
  Each additional vault would add its own ≈9.7 kB redeem to the same
  transaction. **Open item for a later gate.**

## The dead-man's switch — heartbeat cost

Owner recovery and succession are gated by a RELATIVE input age
(`recoveryDelayDaa` / `successionDelayDaa`): the root UTXO must have been
unspent for at least that many DAA score. **Any** root transaction resets the
clock, so an organization's ordinary governance already acts as the heartbeat;
a heartbeat is only a separate cost for an organization that would otherwise
touch its root less often than its own idle delay.

Post-Crescendo mainnet targets 10 blocks per second
(`consensus/core/src/config/bps.rs`, `TenBps = Bps<10>`,
`target_time_per_block = 100 ms`), so a DAA score of D corresponds to roughly
D/10 seconds of DAG progress. **That conversion is a planning approximation —
DAA score tracks difficulty-adjusted block count, not a wall clock — and is
never a consensus guarantee.**

| idle window | `recoveryDelayDaa` | heartbeats / year | cost / year (3 owners) | cost / year (12 owners) |
|---|---|---|---|---|
| ≈30 days | 25,920,000 | 12 | 0.31639200 KAS | 0.34335600 KAS |
| ≈90 days | 77,760,000 | 4 | 0.10546400 KAS | 0.11445200 KAS |
| ≈365 days | 315,360,000 | 1 | 0.02636600 KAS | 0.02861300 KAS |

**Finding 2 — the dead-man's switch is economically free.** Even the tightest
30-day window costs about a third of one KAS per year, and every heartbeat is
an ordinary AUTHORIZE that also refreshes the freshness of every collected
approval. An organization that opts OUT of recovery (`recoveryM = 0`) and
succession (`successorPk = 0`) pays nothing here and accepts, in exchange, that
a lost quorum is permanent (§2.6).

## Honest limits

1. **Relay floor only.** Every number is the consensus MINIMUM. A fee market
   above the floor multiplies all of them linearly; nothing here predicts one.
2. **No KAS price.** Costs are in KAS. Whether 0.026 KAS per governance action
   is cheap depends on a price this record does not model.
3. **The DAA-to-days conversion is a planning approximation**, not a consensus
   guarantee (see above).
4. **The delegate-spend rows use shallow proofs** (a one-leaf agent tree, a
   one-leaf recipient tree). The production proof depths measured in §12.3
   (agent depth 12 / recipient depth 16) add bytes: the VM-measured shape there
   is 13,185 B against 12,283 B at depth 0/0, i.e. roughly +0.0018 KAS per
   spend at full depth. Deep-proof shapes were not re-measured through the SDK
   here.
5. **Batched multi-vault transactions are unmeasured** (see THE SERIALIZATION
   POINT). No saving from batching is claimed.
6. **Storage mass is a validity bound, not a fee.** Every measured shape is
   inside it at its reference values, but an organization that creates dust
   outputs can make a transaction INVALID at any fee. `storageMassFor` is
   provided so a builder can check its own values.
7. **These are TESTNET-shaped measurements of production bytes, not live
   mainnet transactions.** v0.7 is NOT testnet-verified (gate I5). Nothing in this record is an audit.


## Correction (2026-09-03, Wave 2): KIP-9 storage mass and UTXO plurality

Every storage-mass figure in this record was computed with the plurality-1
model (`core/model/storage-mass.js` before commit 6b9da7e). rusty-kaspa
v2.0.1 weighs each UTXO by its storage plurality p = ceil((63 + script
length + 32 if it carries a covenant id) / 100), contributing C·p²/amount —
a covenant-bearing P2SH output has p = 2 and therefore weighs FOUR times the
plain-output estimate used here. Consequences: (1) the dust / minimum-output
thresholds stated for covenant outputs (token notes, protocol-fee outputs,
covenant successors) are understated by up to 4×; the exact numbers are now
produced by the corrected module and enforced pre-sign by the builders'
storage-mass preflight; (2) no live evidence is invalidated (every accepted
transaction was accepted by the node under the correct rule); (3) the
frozen covenant bytes are unaffected (storage mass is not a covenant rule).
Found live on 2026-09-03 when an HD level-1 spend with a 0.05 KAS covenant
carry was refused at 840,919 grams (pinned as an exact regression vector in
`core/model/test/storage-mass-plurality.test.js`).

## KIP-9 plurality — quantitative re-check (2026-09-04, post-Wave-2 hardening)

Re-checked with the exact corrected model (`core/model/storage-mass.js`,
plurality 2 for covenant-bearing P2SH cells). This profile's shapes are
MINIMALLY affected: KAS delegate spends pay a PLAIN P2PK recipient
(plurality 1, unchanged) and owner operations carry only LARGE-amount
covenant outputs (vault + root successors), so corrected storage mass stays
small and well within the 500,000-gram limit (representative KAS delegate
spend ≈ 5,016 grams; representative owner op ≈ 20,178 grams). No
dust/minimum-carry threshold for this profile came from the old model or
changes under the correction. Frozen/candidate covenant bytes are
unaffected (storage mass is a consensus validity rule, not a covenant rule);
the builders' storage-mass preflight fails closed regardless.
