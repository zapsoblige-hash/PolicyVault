## Resolutions (verbatim intent)

- **OQ-V6-1 BUY consideration:** KAS for a BUY comes ONLY from an explicitly
  authorized protected KAS principal (`swapPrincipal`, a dedicated state
  domain of the v0.6 controller funded by the owner), accounted against the
  agent's per-swap KAS cap and periodic KAS budget; token-note KAS backing
  is never consideration; the fee reserve is never principal; an external
  non-covenant KAS funding input MAY be supported only if independently
  identified and mechanically isolated (funding only, no authority) — the
  first candidate does NOT admit one (recorded limitation). Consideration,
  token value and network-fee reserve remain separate domains.
- **OQ-V6-2 destinations:** type A PolicyVault-controlled successor
  (preferred): SELL proceeds accrue to the controller's `swapPrincipal`
  domain; BUY proceeds are a token note owned by the controller's covenant
  id. Type B explicit owner-policy allowlisted P2PK, only where proceeds
  must leave PolicyVault. Destination type + exact identity are in the
  owner-approved swap-policy leaf, the signed manifest and the covenant
  check. No DEX-provided destination is ever valid; no other schemes.
- **OQ-V6-5 network fee:** only from the fee-reserve domain under the
  agent's `agentMaxFeePerTx`; the full value equation is proven in the
  covenant (exact successor value = feeReserve + swapPrincipal; reserve
  consumption ≤ cap ≤ exact fee; principal delta = exactly the swap
  consideration + accounted note backing/protocol fee). Never classified
  as fee: protected principal, token value, pool reserve value, swap
  consideration. External fuel inputs: not admitted in the first candidate.
- **OQ-V6-6 deadline:** `deadlineDaa` is a pre-sign freshness boundary
  enforced by the shared core and signer path (refuse to sign after it);
  exact pool-outpoint binding makes a stale quote unusable once the pool
  transitions; Kaspa lockTime supplies no upper bound and is never claimed
  to; after signature, "authorization deadline passed" and "transaction
  still consensus-valid while its inputs remain unspent" are distinct
  states surfaced in the manifest, explanation and security records.
- **Venue-profile boundary (`policyvault-swap-venue-profile/1`, conceptual;
  final schema subject to review):** profile = mechanically verifiable
  protocol facts (profileId, network, pool covenant family id, pool
  template identity/version + geometry, asset/program layouts, state
  parser id, invariant model, fee model incl. the protocol-fee key, required
  input/output shape, signer/sighash semantics, source provenance). Owner
  policy (swap-policy leaf under `swapRoot`) = venue/pool allowance, pair,
  spend/budget authority (agent leaf), floor (SELL) / ceiling (BUY) price,
  protocol-fee cap, destination, deadline window. Owner financial
  authority never lives in the profile.
