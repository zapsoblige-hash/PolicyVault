## THE CONSENSUS AGE PROOF — `check_sequence_lock`, proven live, twice

This is the property no script engine can prove: a VM evaluates
`OpCheckSequenceVerify` against the input's `sequence` FIELD, but the rule
`utxo.block_daa_score + relative_lock − 1 < pov_daa_score`
(`consensus/src/processes/transaction_validator/tx_validation_in_utxo_context.rs`
`check_sequence_lock`) lives in consensus. **The EXACT SAME finalized bytes
were submitted twice — rejected before the age, accepted after.**

| proof | action | input `sequence` | root UTXO DAA | phase A (before the age) | phase B (after the age) |
|---|---|---|---|---|---|
| step 15 | root action 4 OWNER-RECOVER | 600 | 560,724,990 | virtual DAA 560,725,039, **age 49 < 600** → **REJECTED** | virtual DAA 560,725,626, age **636** → **ACCEPTED**, mined at DAA 560,725,641 |
| step 17 | `rootSuccession` | 600 | 560,725,692 | virtual DAA 560,725,739, **age 47 < 600** → **REJECTED** | virtual DAA 560,726,316, age **624** → **ACCEPTED**, mined at DAA 560,726,323 |

Node rejection text, verbatim, in both phase-A submissions:

```
RPC Server (remote error) -> code:0  message:`Rejected transaction
f04755cb8b04a44c27042ff92f7b0af0c20b72132192484b75cb35d54fd23964:
one of the transaction sequence locks conditions was not met` data:None
```

```
RPC Server (remote error) -> code:0  message:`Rejected transaction
b42ab8222b05f11fa6a9c502973a9b0100fe89540f5a9788e14ef68a407fbf96:
```

The txid is identical in phase A and phase B of each proof (Kaspa's txid
excludes signature scripts, and nothing at all was rebuilt) — so the ONLY
difference between the refusal and the acceptance is the age of the root UTXO.
The dead-man's-switch paths are therefore enforced by consensus, not merely by
the builder.

## What gate I5 proves that no earlier gate could

1. `check_sequence_lock` — the consensus UTXO-age rule behind
   `recoveryDelayDaa` and `successionDelayDaa` — enforced live, both paths,
   with identical bytes across the refusal and the acceptance.
2. The **genesis → spend chain over DERIVED covenant ids**: the root's id came
   from its funding outpoint via the real WASM `covenantId`, the vault pinned
   that id plus the root's template identity and geometry, and 11 subsequent
   root transitions and 5 rooted-vault operations all resolved against it.
3. A rooted vault's owner authority really is an **input, not a key**: five
   owner operations were accepted with **no owner signature on the vault
   input**, and one — 14e — was refused the moment the root's successor bytes
   stopped matching what the vault pins.
4. The lighter emergency quorum (K = 1) reaches the pause and nothing else;
   the full quorum was required (and enforced at 3-of-3) for every expansion.
5. Authority survives a full governance turnover: the vault's terminal
   recovery was authorized by a set installed by a SUCCESSION, three owner-set
   generations after genesis, and still paid only to the genesis-pinned cold
   `recoveryPk`.

## Limitations and unresolved risks (honest)

1. **Bytes are NOT frozen.** This record does not authorize a byte freeze.
2. **Never describe any of this as audited.**
3. **testnet-10 only.** No mainnet transaction was built, signed or broadcast;
   the tool refuses any network other than testnet-10.
4. One organization, one rooted vault, one token family, one delegate. Multi-
   vault organizations (several vaults pinned to one root, several vault
   operations in one transaction) are exercised in the VM/SDK vector suites
   but **not** live.
5. The owner set stayed at 3 active slots or fewer live; the 12-slot geometry
   and the 1-of-1 … 12-of-12 threshold sweep are engine-proven (§10.6, §12.3),
   not testnet-proven.
6. Delays of 600 DAA (≈ 62 s) were chosen so the age paths are provable in
   minutes. Real organizations will use far larger delays; the rule proven is
   the same one, and it scales by the `sequence` field alone.
7. `ROTATE` while frozen (rotate compromised keys before unfreezing) is
   engine-proven but was not exercised live.
8. Gates I3 (presentation + external-signer path) and I4 (fee/mass economic
   model) are still open; §14 of the design doc is reserved for them.
