# v0.7 ORGANIZATIONAL-ROOT APPLICATION SURFACE — COORDINATOR CONTRACT (Wave 2, Track B)

Status: DESIGNED (this contract). Binding for the server, SDK client, web and
MCP lanes of Wave 2 so they build against ONE shape. Every funds-relevant
decision stays in the shared deterministic core / SDK builders / covenant;
the server only orchestrates durable records, signature collection, submission
and PROVEN chain reconciliation. No server-only financial fact may be
introduced (inventory target ZERO).

Authority statement: AI MAY REQUEST · POLICYVAULT DETERMINISTICALLY DECIDES ·
THE COVENANT ENFORCES · SIGNERS RETAIN CUSTODY. PolicyVault is NOT a wallet.

## 0. Two things that must never be confused

| term | meaning | security |
|---|---|---|
| **HOSTED ORGANIZATION** (`/organizations`, existing) | a server-side grouping of vaults, members, roles, governance/risk controls | hosted-layer only; gives NO covenant-level multi-owner security; an admin is not an owner |
| **ON-CHAIN ORGANIZATIONAL ROOT** (`/org-roots`, new) | a `PolicyVault.v0.7-root.sil` covenant UTXO holding N owner slots, M-of-N quorum, emergency FREEZE quorum K, recovery quorum R + delay, succession key + delay | consensus-enforced; every rooted vault's owner operations require this root input |

Every API response, UI surface and MCP tool output that describes a root
carries `authorityModel: "ON_CHAIN_ORGANIZATIONAL_ROOT"`; hosted organizations
carry `authorityModel: "HOSTED_ORGANIZATION"`. A hosted organization MAY link
to a root (`onChainRootId`), but the link is informational: it never grants
authority. Legacy single-owner vaults (v0.4/v0.4.1/v0.5/v0.6) carry
`authorityModel: "SINGLE_ON_CHAIN_OWNER"` and are never presented as M-of-N.

- Rooted vaults reuse `VAULT` with a v0.7 manifest (`sdk/src/manifest-v7.js`): `{ manifestVersion: "policyvault-rooted-vault-manifest-record/1", vaultId, contractVersion: "policyvault-0.7-payment" (later: "policyvault-0.7-kas"), orgRootCovenantId, rootPins (exact), template, state, live, … }`.

The server verifies EVERY envelope against the request's manifest hash, the slot's committed public key and the unsigned transaction before storing it (replay: an envelope for another request/root/nonce is refused with `RESPONSE_BINDING_MISMATCH`).

### 2.1 Hosted tenancy on `/org-roots/*` and `/wallet/v7/*` (rc11 internal security review F-04, 2026-09-04)

Hosted mode REQUIRES a principal on every route of both families. Authority
derives ONLY from durable covenant facts — the root record's ACTIVE owner
slots (normalized through the shared core) plus the pinned successor key
(read-only except for a succession request), the rooted vault's own agent
registry / HD forest leaves, and a request's own creator/signer — never from
`/organizations` roles, request bodies or headers.

| route | rule |
|---|---|
| `GET /org-roots`, `GET /org-roots/:id/requests`, `GET /wallet/v7/requests` | tenant-scoped listings (a caller sees only what it participates in; a live root answers non-participants with 404 on its request list) |
| `GET /org-roots/:id`, `/vaults`, `/requests/:rid` | root participant (active slot or successor) or the request's creator; foreign → 404 `ROOT_NOT_FOUND` / `REQUEST_NOT_FOUND` |
| `POST /org-roots` (genesis) | the funding `signerAddress` MUST be the principal (403 `SIGNER_NOT_PRINCIPAL`) |
| `POST /org-roots/:id/vaults`, `POST /org-roots/:id/reconcile` | an ACTIVE owner slot (successor → 403 `NOT_AN_ACTIVE_SLOT`); genesis signer = principal |
| `POST /org-roots/:id/requests` (root action) | participant (else 404 before any lock), `signerAddress` = principal, then the SDK's active-slot rule (successor only for succession) — a stranger can no longer lock a live root |
| `GET .../slot-request/:slot`, `POST .../slot-signatures` | only the wallet holding THAT slot's key (403 `NOT_AN_ACTIVE_SLOT`) |
| `POST .../signature`, `/finalize`, `/submit`, `/reject` | the request's creator or an active owner; the successor only for a succession request (403 `REQUEST_FORBIDDEN` for a read-only participant) |
| `POST /wallet/v7/requests` | principal holds build authority on the rooted vault (active root owner or registered agent); `signerAddress` is a participant; an agent builds only for itself; an owner may build for its registered agents; `tokenDeposit` is built by a participant for its own key |
| `GET /wallet/v7/requests/:id`, `POST .../signature|submit|reject` | the request's signer or a vault participant (mutations: signer or a wallet with build authority) |

Machine credentials reach both families with `read:org-roots` /
`write:org-roots` (F-06) and act as their creating wallet.

## 3. Web (Track B-web) consumption

- Organizations tab: two clearly separated sections — "Hosted organization (grouping & roles — no on-chain authority)" and "On-chain organizational root (covenant-enforced M-of-N)". The existing single-owner statement stays for legacy vaults.
- Root wizard: owner slots (N), M, K, R, delays, successor → "Exact root policy before signing" panel rendered from the SDK/core explain output (never from UI-local arithmetic) → funder signs genesis → PENDING (not success) → reconcile → root live.
- Root detail: N configured slots / M / K / R / delays / generation & nonce / frozen / pending request / action class / signatures present vs required / signer identity + address per slot / signer-visible manifest digest / outcome ladder / warnings.
- Slot signing: the connected wallet signs ONLY its own slot through the signer adapter (`web/signer-kasware-adapter.js` → `signPskt` on the root input; extract the 65-byte SIGHASH_ALL signature exactly as `collectApprovalV4` does) and POSTs the response envelope; other owners' envelopes are imported (paste / file / QR via the existing air-gap shuttle) and POSTed the same way. Finalize is offered only when present ≥ required; submit only after SIGNED.
- Rooted vault creation bound to a chosen root; owner operations on a rooted vault are created as ROOT REQUESTS (they show the root quorum, never a single-owner button).
- Dangerous actions (ownerRecover, succession, rotate, unfreeze) require an explicit typed confirmation and show: what changes, that recovery/succession LAND FROZEN, the delay, and that a heartbeat AUTHORIZE keeps recovery closed.
- No UI shortcut may bypass the server/core verification; the browser re-verifies the org-root manifest locally through the core bundle before asking the wallet to sign (`web/verify-intent.js` route for `policyvault-org-root-manifest/1`, Track F wires the router; until then use the bundle's `orgRootManifestV7.verifyOrgRootIntentManifest` directly).

#### 6.1.1 Hosted tenancy on `/wallet/v5|v6/*` (rc11 internal security review F-04, 2026-09-04)

The token surface receives the request context and applies the v4 rule set
exactly: a principal is REQUIRED (401); `create` binds `signerAddress` to the
principal (403 `SIGNER_NOT_PRINCIPAL`); `requests` needs build authority on
the controller (owner or registered agent; foreign/unknown/other-generation
vault → 404 `VAULT_NOT_FOUND`), a participant signer (403
`SIGNER_NOT_PARTICIPANT`), agent self-only (403 `SIGNER_NOT_PRINCIPAL`);
listings are tenant-scoped; `GET /:id` and `signature|submit|reject` are
scoped to the request's signer or a vault participant (mutation: signer or a
wallet with build authority; else 403 `REQUEST_FORBIDDEN`). `tokenDeposit` in
hosted mode is built by a participant for its own key (a third-party
depositor is not a hosted flow on these NOT-production generations).
