# v0.7 ORGANIZATIONAL-ROOT APPLICATION SURFACE — COORDINATOR CONTRACT (Wave 2, Track B)

Status: DESIGNED (this contract). Binding for the server, SDK client, web and
MCP lanes of Wave 2 so they build against ONE shape. Every funds-relevant
decision stays in the shared deterministic core / SDK builders / covenant;
the server only orchestrates durable records, signature collection, submission
and PROVEN chain reconciliation. No server-only financial fact may be
introduced (inventory target ZERO).

Authority statement: AI MAY REQUEST · POLICYVAULT DETERMINISTICALLY DECIDES ·
THE COVENANT ENFORCES · SIGNERS RETAIN CUSTODY. PolicyVault is NOT a wallet.

## 0. Two things that must never be confused

| term | meaning | security |
|---|---|---|
| **HOSTED ORGANIZATION** (`/organizations`, existing) | a server-side grouping of vaults, members, roles, governance/risk controls | hosted-layer only; gives NO covenant-level multi-owner security; an admin is not an owner |
| **ON-CHAIN ORGANIZATIONAL ROOT** (`/org-roots`, new) | a `PolicyVault.v0.7-root.sil` covenant UTXO holding N owner slots, M-of-N quorum, emergency FREEZE quorum K, recovery quorum R + delay, succession key + delay | consensus-enforced; every rooted vault's owner operations require this root input |

Every API response, UI surface and MCP tool output that describes a root
carries `authorityModel: "ON_CHAIN_ORGANIZATIONAL_ROOT"`; hosted organizations
carry `authorityModel: "HOSTED_ORGANIZATION"`. A hosted organization MAY link
to a root (`onChainRootId`), but the link is informational: it never grants
authority. Legacy single-owner vaults (v0.4/v0.4.1/v0.5/v0.6) carry
`authorityModel: "SINGLE_ON_CHAIN_OWNER"` and are never presented as M-of-N.

### 2.2 Root moves broadcast outside PolicyVault, the build-time guard and spent inputs (RC45; `policyvault-0.7-kas` treasuries)

Status label, disposition and residuals: `lead5-reconciliation-remediation.md`
§10. Every rule below is decided by the SDK (`sdk/src/wallet-requests-v7.js`,
`sdk/src/reconcile-v7.js`, `sdk/src/wallet-requests-v7-kas.js`); the server
serves its answers.

**Refusal fields on the wire.** This section names a refusal's additional
fields as the SDK exposes them: `extra.submitRead`, `extra.feeInput`,
`extra.earliestDaa` and `extra.latestDaa`, and `extra.withdrawal`. The HTTP
answer has no `extra` member: these fields are top-level members of the error
envelope, beside `code` and `message`, for example `{ "error": { "code":
"RECORDED_OUTPUT_SPENT", "message": "…", "submitRead": { … } } }`. A raw HTTP
client reads `error.submitRead`, `error.feeInput`, `error.earliestDaa`,
`error.latestDaa` and `error.withdrawal.finding`. The SDK's HTTP client error
`PolicyVaultApiError` (`sdk/src/http-client.js`) exposes the same members as
`err.extra.submitRead` and so on; the errors that
`sdk/src/wallet-requests-v7.js` throws in-process carry them as `extra` too.

**Why.** A root request carrying a v0.7-kas delegate rule change
(`ownerSetAgentRoot` on one treasury) is signed by the owners' slot approvals
and by the fee input's signature. Finalize refuses it once a new or changed
delegate's period start has aged out, and such a request can then be
withdrawn, but its approvals still sign its transaction: anyone holding them
and the fee-input signature can broadcast it outside PolicyVault (case 5).
Withdrawal does not revoke signatures or prevent an otherwise valid
out-of-app broadcast. Once that transaction is accepted, the root's recorded
outpoint is spent by a transaction that no PolicyVault submission explains.

#### 2.2.1 Verify attributes the move (`POST /org-roots/:rootId/reconcile`)

When the recorded root outpoint is spent and the existing claim path proves
nothing, Verify attributes the move, under the root's lock (which every hosted
mutation of the root takes), only when all of these hold. Every refusal writes
nothing.

1. **Records first.** The candidates are this root's requests recorded on the
   root's recorded outpoint with a txid and a build. Without one, the answer
   is the earlier `UNKNOWN` (`reason`, no `attribution` field) and no node is
   read.
2. **The successor, exactly.** One canonical virtual-DAA read, then one read
   per distinct candidate root-successor address (more than 64 addresses:
   `CANDIDATE_CAP`). A candidate's root successor counts only when exactly one
   entry carries its txid, at its output index, with the frozen value, the
   frozen covenant id and a reported script equal to the frozen one; anything
   else under that txid is `CONTRADICTION`. No observed successor:
   `NO_CANDIDATE`; the successors of several transactions: `CONTRADICTION`.
3. **One record, in scope.** Several records carrying the observed txid:
   `AMBIGUOUS`. The one record must be a v0.7-kas delegate rule change that is
   either fresh (AUTHORIZED or REFUSED, no final transaction, never attempted)
   or a replay of an earlier attribution (RECONCILIATION_REQUIRED with a bound
   marker). A finalized (SIGNED), never-attempted request answers
   `SUBMIT_TO_RECORD` naming it: its own transaction is already on the chain,
   so press Submit on it, then Verify state (Submit takes the existing
   completion route). Any other record: `NOT_IN_SCOPE` naming it.
4. **Binding.** The txid recomputed from the request's frozen bytes (a Kaspa
   txid excludes the signatures) equals the request's, its build's and its
   manifest's; the manifest's frozen canonical JSON equals those bytes;
   exactly one input carries the root covenant id and it spends the recorded
   root outpoint; the manifest verifies; the stored registry folds to the
   committed agent root. Otherwise `RECORD_DAMAGED`.
5. **Consistency.** Every frozen input of the request is reported spent, and
   the treasury it changes (T1) is recorded on this root at the request's
   predecessor (for a replay: at its predecessor or successor). Otherwise
   `CONTRADICTION`.
6. **The treasury output and the bracket.** T1's successor output: exact →
   FULL; nothing under the txid (spent outside PolicyVault) → PARTIAL;
   anything else `CONTRADICTION`. The root successor and T1's output are then
   read again and must be unchanged (`UNSTABLE` otherwise). A PARTIAL-marker
   replay reads no treasury output and stays PARTIAL; a FULL-marker replay
   whose treasury record already stands at the successor reads none either.
7. **Depth.** The virtual DAA minus the root successor's canonical accepting
   DAA must be at least 1,000 (`BELOW_DEPTH` otherwise; a non-canonical score
   `OBSERVATION_ERROR`); FULL also needs T1's entry at the same accepting DAA
   (`CONTRADICTION` otherwise).

A failed node read is `OBSERVATION_ERROR`; store errors propagate as before.

**UNKNOWN answer:** `{ status: "UNKNOWN", rootCovenantId, reason, attribution:
{ outcome, requestId?, txId?, depthDaa?, requiredDepthDaa: "1000" } }`, with
`outcome` one of `NO_CANDIDATE`, `CANDIDATE_CAP`, `CONTRADICTION`,
`AMBIGUOUS`, `SUBMIT_TO_RECORD`, `NOT_IN_SCOPE`, `RECORD_DAMAGED`, `UNSTABLE`,
`BELOW_DEPTH`, `OBSERVATION_ERROR` or `COMPLETION_REFUSED` (the completion
refused before its first write). A root moved outside PolicyVault in any
other way stays `UNKNOWN`; only the owners' direct on-chain action acts on it.

**Completion.** The first durable write is the request with the marker
`outOfBandAttribution = { schema: "policyvault-oob-attribution/1", via:
"attribution", txId, requestId, observedVirtualDaa, rootEntryDaa, depthDaa,
requiredDepthDaa, mode, modeChangedAt?, treasury: { vaultId,
predecessorOutpoint, state }, at }` and state RECONCILIATION_REQUIRED. Then,
in the existing order: FULL writes T1 at the request's successor with its new
registry (PARTIAL writes no treasury record), then the root, the claims, the
receipt (`reconciled: true`), the history line, CHAIN_VERIFIED and the root's
pointer when it names the request. A marker counts only when it is bound: its
schema and `via` match, it names the request and its txid, the request has no
final transaction, is RECONCILIATION_REQUIRED or CHAIN_VERIFIED and is a
v0.7-kas delegate rule change, the marker names that operation's treasury and
predecessor with the state its mode gives (FULL: ADVANCED, PARTIAL:
UNRESOLVED), and its recorded depth is at least 1,000. A crash after the
marker save is completed once by the next Verify or Submit; such a replay's
CHAIN_VERIFIED history line carries `via` `reconcile` or `submit-recovery`,
while the marker keeps `via: "attribution"`. A FULL replay that finds T1's
output spent since (T1 still at its predecessor) first saves the marker as
PARTIAL (treasury UNRESOLVED, `modeChangedAt`) and completes PARTIAL; it never
records the spent output.

**ADVANCED answer:** `{ status: "ADVANCED", rootCovenantId, txId, requestId,
via: "attribution", mode: "FULL" | "PARTIAL", depthDaa, requiredDepthDaa:
"1000", treasury: { vaultId, state: "ADVANCED" | "UNRESOLVED" }, settled,
unsettled, holds, buildable, reason }`. A Verify that replays an attributed
completion answers the same fields from the marker (with its recorded depth),
never the generic replay answer. FULL: the root and T1 follow the attributed
transaction's outputs; the delegates it installed can pay from T1 outside
PolicyVault at any time, a hosted FREEZE or pause of T1 that loses that race
is refused or fails, and a request it leaves stranded holds the root until it
is withdrawn (two steps, at least 1,000 DAA apart), or longer in the disclosed
cases where a withdrawal cannot be proven safe. PARTIAL: the root follows its
successor; T1 is UNRESOLVED (§2.2.3) and its record is not presented as
current.

**Settlement** (in the same Verify, and later by the hook below), only on
proof that the settled request can never be accepted, because the attributed
transaction, accepted at depth, spent an input it needs:

- another root request on the same root outpoint (AUTHORIZED, SIGNED,
  BROADCAST, CHAIN_SEEN or RECONCILIATION_REQUIRED) whose frozen inputs
  include that outpoint, with no output and no receipt under its own txid:
  SUPERSEDED with `submissionOutcome: { outcome: "SUPERSEDED", proof: { via:
  "attribution", acceptedConflictingTxId, attributedRequestId, spentOutpoint,
  depthDaa } }` (one save when it was never attempted and holds no claim;
  otherwise the existing negative-outcome order, releasing only its own
  claims), and the root's pointer cleared when it names it;
- an unfinished delegate request sharing a frozen input with the attributed
  transaction, with no output under its own txid: SUPERSEDED;
- a root pointer naming a terminal request of that outpoint (SUPERSEDED,
  SUBMISSION_REJECTED, NOT_BROADCAST, REFUSED, STALE, FAILED) without a bound
  receipt: its own claims released and the pointer cleared.

Never settled: other terminal requests, built or never-attempted signed
delegate requests, other roots' requests, and any candidate whose proof fails
(listed in `unsettled: [{ requestId, step, reason }]`). A `settled` entry is
`{ requestId, kind, outcome, spentOutpoint, vaultId? }`, or for a pointer
finish `{ requestId, kind, step: "pointer", outcome, reservation: "RELEASED" }`.
**The hook:** a later Verify whose live root outpoint was created by an
attributed CHAIN_VERIFIED request settles a settlement candidate that remains;
its failures appear as `unsettled: [{ step: "hook", … }]` beside that Verify's
own answer, whose status is kept. Without a candidate the hook reads nothing
from the node and writes nothing.

#### 2.2.2 Holds and buildability (`holds`, `buildable`)

Computed after settlement from the records only (no node read, no write):
`holds` lists the root's pending pointer and every request that still
reserves the root's predecessor as `{ scope: "root", requestId, state }`, and
every UNRESOLVED treasury of the root as `{ scope: <vaultId>, reason:
"UNRESOLVED", requestId, txId }`. `buildable = { root, treasuries }`: `root`
is true when no hold has scope `"root"`; `treasuries` lists, when `root` is
true, the root's treasuries without a hold, and is otherwise empty. `holds:
null, buildable: null` means not determined. Only `buildable.root === true`
means that owner actions on the root and on the listed treasuries, FREEZE
included, can be built again as of this check (a treasury's own unfinished
delegate request still refuses that treasury's owner actions). Otherwise each
hold names what to resolve; press Verify state again after it resolves. This
computation never releases a hold.

#### 2.2.3 An UNRESOLVED treasury

T1 is UNRESOLVED (a record-only rule) while a bound PARTIAL marker of its root
names it and T1's record still stands at the marker's predecessor outpoint.
Every hosted action on it is refused `409 TREASURY_STATE_UNRESOLVED`, naming
the attributed request and its txid, with nothing written: owner operations
built as root requests (FREEZE with emergency pause, pause, recover and the
others), and delegate requests at build, finalize and broadcast. The refusal
comes before `VAULT_PAUSED` and `VAULT_PENDING_REQUEST` (and, for an owner
operation, before the root-pin check), because T1's recorded status describes
a predecessor that moved on chain; the network, generation, identity, genesis
and action-shape checks and the root-wide `ROOT_PENDING_REQUEST` still come
first. A vault Verify of T1 answers
`UNKNOWN` naming the UNRESOLVED state. A root FREEZE does not stop T1's
delegates; only the owners' direct on-chain exit acts on T1. The explanation
served for the code is:

"PolicyVault cannot confirm this treasury's current state: its expected output was spent outside PolicyVault after an out-of-band change to its delegate rules. Hosted actions on this treasury stay closed. A later Verify restores them only if it finds that expected output unspent again (for example after a reorganization); otherwise only the owners' direct on-chain exit can act on it."

**A later Verify.** The Verify that completes a PARTIAL attribution never
upgrades it. A later Verify (with nothing replayed in it) records T1 as
following its expected output, the attributed transaction's treasury output,
only when it freshly observes, in this order: that output exact and unspent;
every frozen input of the attributed request reported spent (one read of each
input address); when the root stands at the attributed successor, the root
successor exact at the same accepting DAA; and that output read a second time,
unchanged; at depth ≥ 1,000 DAA. Only the treasury output is read twice. It
writes, in order: the marker (mode FULL, treasury ADVANCED,
`upgradedFrom: "PARTIAL"`,
`upgradedAt`, `upgradeObservation`), T1's record, and one history line
(`TREASURY_FOLLOWS_ATTRIBUTED_OUTPUT`). Its answer carries `treasuryUpgrades`:
one entry per treasury with exactly ten string fields `vaultId`,
`requestId`, `txId`, `from` (`"PARTIAL"`), `mode` (`"FULL"`), `treasury`
(`"ADVANCED"`), `outpoint` (`"<txId>:<index>"`), `depthDaa`,
`requiredDepthDaa` (`"1000"`) and `reason`; the field is absent when nothing
was upgraded. The depth used is the age of the expected output's acceptance,
not the age of a reversal: when a reorganization makes that output unspent
again, a later Verify can restore hosted actions on T1 at once. If a restored
output is spent again, T1 is refused `RECORDED_OUTPUT_SPENT` by the
build-time guard (§2.2.4). T1 is never restored from stale or spent state. A
marker whose mode is PARTIAL can still carry `upgradedFrom`, `upgradedAt` and
`upgradeObservation` from an upgrade that a crash interrupted and a later
Verify reversed; only mode FULL with treasury ADVANCED means that T1 follows
that output. A later Verify does not report an upgrade again; the summaries
and the marker show it.

**Summaries** (`GET /org-roots/:rootId/vaults`, `GET /wallet/v7/vaults`):
every v0.7-kas treasury carries `stateUnresolved: { requestId, txId } | null`.
Read it first: when it is set, `status`, `generation`,
`latestTransitionTxId`, `agents`, `approvers`, `approvalM` and `live` are the
last record (the predecessor that a transaction broadcast outside PolicyVault
consumed), never the treasury's current state. It is decided from one listing
of each shown root's requests; a damaged organization-root request record of
any root refuses both routes (422, fail closed) for every principal who sees a
v0.7-kas treasury, and an undetermined state is never served as null (`500
TREASURY_STATE_UNDETERMINED`, which these routes cannot reach with the current
SDK). The request id and txid it names are
visible to the treasury's delegates and approvers; they grant no access,
because the root request routes are root-scoped.

#### 2.2.4 The build-time liveness guard (every root request)

In the root request build, after the manifest is verified and after every
other refusal, before the first write: one connection to the configured
synced node and one read per distinct address. Every frozen input whose
covenant id is the root's or, for a v0.7-kas operation, the treasury's must be
reported exactly once at its outpoint with the frozen value, the frozen
covenant id and, where the node reports them, the frozen script and script
version. Otherwise the build answers `409 RECORDED_OUTPUT_SPENT` naming the
role and the outpoint; a node that cannot be connected or read refuses with
its own error. Nothing is written and the root is not reserved.

- **What it prevents, exactly:** recording a root request, and reserving the
  root with it, when the request spends a root or v0.7-kas treasury output
  that the synced node does not report unspent at build time.
- **What it does not prevent:** a spend accepted after this read, or one only
  in the mempool (an attributable root move is then settled as in §2.2.1, any
  other root move answers UNKNOWN, and inputs spent after the build meet the
  submit read of §2.2.5); a broadcast of the request's own transaction outside
  PolicyVault; a node that misreports. It does not promise that an output stays
  unspent after the build. Fee and v0.7-payment vault inputs are checked by the
  input observation of §2.2.5, not by this guard.
- **It never closes a usable treasury:** it keeps no state and refuses only
  while the node does not report the output unspent and exact.
- **Behaviour change:** a root build with an explicit fee input now also needs
  the node.

#### 2.2.5 Spent inputs of a finalized request: input observation, the submit read and the two-step withdrawal

**Input observation at build.** After the guard, the build reads the anchor
A_b, the sink's 20th selected parent, verified on the selected chain and bound
to its header, then every non-root frozen input (fee, treasury, vault), each
of which must be reported exactly once and exact, then A_b again (the
recheck). The anchor is fail-soft: it is null when the first read fails, or
when the recheck cannot read it, no longer finds it on the selected chain or
reads another DAA score. A fee input that is absent, reported with other
contents or unreadable answers `409 FEE_INPUT_NOT_LIVE` with
`extra.feeInput = { index, outpoint, reason: "ABSENT" | "MISMATCH" |
"READ_FAILED", detail }`; a treasury or v0.7-payment vault input `409
RECORDED_OUTPUT_SPENT`; any other read failure `422`; a null anchor (it could
not be read, or it left the selected chain by the recheck) while a non-root
input is less than 1,000 DAA deep `422 OBSERVATION_ERROR`. Nothing is written
on a refusal. Otherwise the build's existing first write carries
`inputObservation = { schema:
"policyvault-input-observation/1", txId, virtualDaa, anchor: { hash, daaScore
} | null, at, inputs: [{ index, role, outpoint, blockDaaScore, existence? }]
}`. A root request's automatically chosen fee input is the largest ordinary
UTXO at least 1,000 DAA deep when one exists, otherwise the largest one as
before; it never refuses for freshness.

**Existence evidence.** An input reported absent is called spent only with
evidence that its creating transaction was accepted on the selected chain for
good (`path`):

- `E1`: accepted at least 1,000 DAA below the build's virtual DAA;
- `E1s`: another output of the same creating transaction is observed unspent,
  at least 1,000 DAA deep, by the same observation (independent of the node's
  retained history);
- `E2`: accepted at or below A_b, with A_b verified on the selected chain;
- `E3`: its creating transaction is located in exactly one chain block K′ of
  one `getVirtualChainFromBlock` answer from A_b that removes nothing, with K′
  verified on the selected chain (a creator that lost to a conflicting
  transaction is not found);
- or evidence recorded final earlier.

The slot-request, slot-signature and finalize saves (and a succession's
signature save) evaluate E2 and E3 for inputs without E1 and record the
evidence as final in `inputObservation.inputs[].existence = { path, block,
daaScore, finalAt }` when its block is on the selected chain at least 1,000
DAA below the virtual DAA. This is fail-soft, never refuses the save and adds
no save. E2 and E3 need the node's retained history from the build (at least
about 30 hours by default).

**The submit read** runs in Submit after the claim check and before the first
submit-state write, and writes nothing on any refusal: (1) the start A_s, the
sink's 20th selected parent (unreadable: `422 OBSERVATION_ERROR`), which
becomes `submitStartHash`; (2) every non-root input in frozen order, then the
root input last; (3) only when an input is not reported unspent, the request's
own output addresses; (4) only for a candidate spend, the existence evidence
of the absent inputs.

| Read result | Answer |
|---|---|
| every input reported unspent and exact | the existing submit route |
| an input not reported unspent, and an output of the request's own transaction observed | the existing submit route: the request's own transaction was broadcast outside PolicyVault, and Verify proves it through the claim path |
| the root input not reported unspent, no own output | `409 SUBMIT_INPUT_UNRESOLVED`, finding `ROOT_INPUT_NOT_LIVE`: either this request's transaction was broadcast outside PolicyVault and its outputs were already spent, or another root transaction spent the root output; PolicyVault cannot tell which; no withdrawal |
| the root input unspent, a non-root input reported with other contents | `409 SUBMIT_INPUT_UNRESOLVED`, finding `INPUT_CONTRADICTED`; no withdrawal |
| the root input unspent, an absent non-root input with existence evidence | `409 RECORDED_OUTPUT_SPENT`, finding `CONFLICTING_SPEND`: spent by another transaction; withdrawable in two steps |
| the root input unspent, absent non-root inputs without existence evidence | `409 SUBMIT_INPUT_UNRESOLVED`, finding `INPUT_EXISTENCE_UNPROVEN`: not treated as spent (the input may still be created); submit again once it is reported unspent |
| a node error in reads (1)–(3) | that error (`422`) |

Each 409 carries `extra.submitRead = { finding, role, outpoint, withdrawal:
"TWO_STEP" | "NONE", existence: "E1" | "E1s" | "E2" | "E3" | null,
existenceGap: "NO_MARKER" | "ANCHOR_UNAVAILABLE" | "CREATOR_NOT_LOCATED" |
null }`. The request stays SIGNED and never attempted, and keeps the root's
reservation. "Spent by another transaction" is said only when the root input,
which this request's own transaction also spends, is read unspent after the
absent input, so that transaction has not been accepted. For E2 or E3
evidence not yet recorded final, the answer adds that the withdrawal must
start while the node still holds the history from this request's build (at
least about 30 hours by default). A Submit under a new key re-runs the read and can only refuse again
or send exactly the same transaction.

**Own transaction versus conflicting spend.** "Never attempted by the server"
does not mean that the request's transaction was never broadcast: the fee-input
signer, owners who kept their approvals, the successor key of a succession,
or anyone they pass the bytes to can broadcast it. PolicyVault keeps the
request's completion route whenever its own transaction may have spent the
input: an observed own output takes the existing submit route; Verify answers
`SUBMIT_TO_RECORD` naming a finalized request whose transaction is on the
chain; and the withdrawal refuses while the root input is not reported
unspent, an own output is observed, or the transaction is in the node's
transaction pool or accepted after the anchor.

**The two-step withdrawal** (`POST /org-roots/:rootId/requests/:id/reject` on a
SIGNED request; every other request takes the earlier withdrawal path,
unchanged):

- **Record preconditions** (no node read): a root request, SIGNED, whose final
  transaction binds its frozen bytes and txid, with no submission evidence,
  with exactly one input carrying the root covenant id that spends the
  recorded root outpoint, which is still the root record's live outpoint, and
  with a bound `inputObservation` (requests built before this release have
  none).
- **Each step observes afresh, in order:** the anchor A (the sink's 20th
  selected parent); the root input unspent and exact; the other inputs (any
  reported with other contents: refused; none absent: refused, submit it; the
  absent ones need existence evidence); the request's transaction in the
  node's mempool (a miss, or the orphan pool only); the root input again,
  unchanged; every output address, with no output of the request's own
  transaction.
- **Step 1** records only the anchor (`inputSpentObservation`, schema
  `policyvault-input-spent-observation/1`) and answers `409
  WITHDRAWAL_DEPTH_PENDING` with `extra.earliestDaa` = DAA(A1) + 1,000 and
  `extra.latestDaa` = DAA(A1) + 12,000, where A1 is the recorded anchor and
  DAA(A1) its own header DAA. Earlier than that: pending, nothing written;
  later than that: the anchor is renewed (recorded again, with the same
  pending answer).
- **Step 2** withdraws only when every check holds again and: the existence
  block of an absent input lies at or below A1 and at least 1,000 DAA below
  the virtual DAA; the acceptance window from A1 is complete and does not
  accept the request's transaction; and a scan of at most 64 block batches
  from A1 to the sink finds no other transaction naming one of its inputs
  (inclusion in a block counts, accepted or not). Then one save, REFUSED with
  `inputSpentWithdrawal = { schema: "policyvault-input-spent-withdrawal/1",
  requestId, txId, anchor, withdrawnAt, observedVirtualDaa, depthDaa, sink,
  spent, windowBlocks, scanBlocks, scanBatches }`, then the root's pointer is
  released. A check that is not yet met renews the anchor (another ≥ 1,000
  DAA) or refuses.
- **Writes:** only the request (the anchor, then REFUSED) and the root's
  pointer. Each save of the request follows a reload that refuses with
  `STORE_CHANGED`, writing nothing, if the request changed or the root record
  no longer names the request's root predecessor as live. The pointer save
  reloads the root and clears its pointer only when it still names this
  request; it never refuses. No claim, receipt, root or treasury state, no
  SUPERSEDED and no `submissionOutcome` is written; nothing is settled. After a
  crash between the REFUSED save and the pointer save, a repeated withdrawal
  finishes it with no node read.
- **Refusals:** `409 CANNOT_REJECT` with `extra.withdrawal.finding` one of
  `RECORD`, `NODE_ERROR`, `ROOT_INPUT_NOT_LIVE`, `INPUT_CONTRADICTED`,
  `INPUTS_LIVE`, `INPUT_EXISTENCE_UNPROVEN`, `MEMPOOL_UNCLEAR`,
  `IN_TRANSACTION_POOL`, `UNSTABLE`, `OWN_OUTPUT`, `ACCEPTED_IN_WINDOW`,
  `SCAN_UNCLEAR` or `STORE_CHANGED`, with nothing written.
- **Uncertainty never withdraws:** no withdrawal, claim release or retry under
  a new key rests on an unproven, contradictory, not-yet-final or unreadable
  observation; each answers `CANNOT_REJECT`, a pending 409 or a renewal. After
  the withdrawal, Submit, finalize and signing are refused (the request is
  REFUSED), and a root FREEZE can be built again.
- **The request's own transaction wins during the wait:** the withdrawal
  refuses (`ROOT_INPUT_NOT_LIVE`, `ACCEPTED_IN_WINDOW` or `OWN_OUTPUT`), Verify
  answers `SUBMIT_TO_RECORD`, and Submit completes the request. The web keeps
  Submit offered for every SIGNED, never-attempted request, with or without an
  anchor; the server's submit read decides.

**Constants** (exported by `sdk/src/wallet-requests-v7.js`):

| Constant | Value | Basis |
|---|---|---|
| `INPUT_SPENT_WITHDRAWAL_DEPTH_DAA` | 1000 | equal to `ATTRIBUTION_DEPTH_DAA`, the depth settlement uses |
| `CHAIN_ANCHOR_HOPS` | 20 | 20-deep selected-chain ancestors were never seen removed in read-only testnet-10 samples, while 33–40% of sinks were |
| `WITHDRAWAL_ANCHOR_MAX_AGE_DAA` | 12000 | about 20 minutes at ten blocks per second; bounds step 2 and the scan |
| `WITHDRAWAL_SCAN_MAX_BATCHES` | 64 | up to 15,936 blocks at ten blocks per second, above the about 12,050 merged blocks of a 12,000-DAA window |

**Served withdrawal texts.** Every withdrawal of a request that carries owner
signatures, except the input-spent withdrawal, states: "Withdrawing marks this request withdrawn in PolicyVault and releases the root's reservation. It does not revoke the owner signatures already given: anyone holding them and the fee-input signature can still broadcast this exact transaction outside PolicyVault while the outputs it spends are unspent. Withdrawing broadcasts nothing."
The input-spent withdrawal states, in place of that text (and the
`WITHDRAWAL_DEPTH_PENDING` message ends with its first sentence): "Withdrawal does not revoke signatures or prevent an otherwise valid out-of-app broadcast. PolicyVault withdraws this finalized request only because the <role> output it spends was spent by another transaction, and that spend is final at 1,000 DAA. This request's transaction can therefore no longer be accepted unless the network reverses more than 1,000 DAA of its history; if that happened and the transaction were broadcast outside PolicyVault, PolicyVault would not recognize it as this request. Withdrawing marks this request withdrawn in PolicyVault and releases the root's reservation. It broadcasts nothing."

Submit: an input was spent by another transaction; nothing written; two-step withdrawal |

- Root wizard: owner slots (N), M, K, R, delays, successor → "Exact root policy before signing" panel rendered from the SDK/core explain output (never from UI-local arithmetic) → funder signs genesis → PENDING (not success) → reconcile → root live.
- Root detail: N configured slots / M / K / R / delays / generation & nonce / frozen / pending request / action class / signatures present vs required / signer identity + address per slot / signer-visible manifest digest / outcome ladder / warnings.
- Slot signing: the connected wallet signs ONLY its own slot through the signer adapter (`web/signer-kasware-adapter.js` → `signPskt` on the root input; extract the 65-byte SIGHASH_ALL signature exactly as `collectApprovalV4` does) and POSTs the response envelope; other owners' envelopes are imported (paste / file / QR via the existing air-gap shuttle) and POSTed the same way. Finalize is offered only when present ≥ required; submit only after SIGNED.
- Rooted vault creation bound to a chosen root; owner operations on a rooted vault are created as ROOT REQUESTS (they show the root quorum, never a single-owner button).
- Dangerous actions (ownerRecover, succession, rotate, unfreeze) require an explicit typed confirmation and show: what changes, that recovery/succession LAND FROZEN, the delay, and that a heartbeat AUTHORIZE keeps recovery closed.
- No UI shortcut may bypass the server/core verification; the browser re-verifies the org-root manifest locally through the core bundle before asking the wallet to sign (`web/verify-intent.js` route for `policyvault-org-root-manifest/1`, Track F wires the router; until then use the bundle's `orgRootManifestV7.verifyOrgRootIntentManifest` directly).

**Delegate rule changes and approval time.** A delegate rule change must collect every owner approval and be finalized within the new or changed delegate's budget period minus ten minutes (never less than one minute) of its build — 50 minutes for a 1-hour period, 23 h 50 min for a daily one. A slower quorum cannot finalize it: the request can then only be withdrawn and built again. The web shows the deadline on the request, next to each approval button and on the Change delegate rules form (on the request it shows the deadline as unknown when the treasury's installed delegate rules cannot be loaded; PolicyVault then decides at finalize). API, SDK and MCP callers may request a later budget period start, which extends the window; the web has no such input in this release. A finalized request is not re-checked for its period start at submit and cannot be withdrawn on that ground (it can be withdrawn only in the two-step case of §2.2.5, when an input it spends was spent by another transaction); the web shows each delegate's immediately spendable amount before it is submitted. Delegates the change leaves exactly as installed keep their start, so an idle one can still spend every unused period's budget at once (a property of the installed covenant that this rule does not change).

#### 6.1.1 Hosted tenancy on `/wallet/v5|v6/*` (rc11 internal security review F-04, 2026-09-04)

The token surface receives the request context and applies the v4 rule set
exactly: a principal is REQUIRED (401); `create` binds `signerAddress` to the
principal (403 `SIGNER_NOT_PRINCIPAL`); `requests` needs build authority on
the controller (owner or registered agent; foreign/unknown/other-generation
vault → 404 `VAULT_NOT_FOUND`), a participant signer (403
`SIGNER_NOT_PARTICIPANT`), agent self-only (403 `SIGNER_NOT_PRINCIPAL`);
listings are tenant-scoped; `GET /:id` and `signature|submit|reject` are
scoped to the request's signer or a vault participant (mutation: signer or a
wallet with build authority; else 403 `REQUEST_FORBIDDEN`); `reject` is
narrower, as on `/wallet/v4`: only the request's signer or the controller
owner may reject a request (any other participant, a registered agent
included, 403 `REQUEST_FORBIDDEN` with nothing written). `tokenDeposit` in
hosted mode is built by a participant for its own key (a third-party
depositor is not a hosted flow on these NOT-production generations).
