# v0.7 ORGANIZATIONAL-ROOT APPLICATION SURFACE — COORDINATOR CONTRACT (Wave 2, Track B)

Status: DESIGNED (this contract). Binding for the server, SDK client, web and
MCP lanes of Wave 2 so they build against ONE shape. Every funds-relevant
decision stays in the shared deterministic core / SDK builders / covenant;
the server only orchestrates durable records, signature collection, submission
and PROVEN chain reconciliation. No server-only financial fact may be
introduced (inventory target ZERO).

Authority statement: AI MAY REQUEST · POLICYVAULT DETERMINISTICALLY DECIDES ·
THE COVENANT ENFORCES · SIGNERS RETAIN CUSTODY. PolicyVault is NOT a wallet.

## 0. Two things that must never be confused

| term | meaning | security |
|---|---|---|
| **HOSTED ORGANIZATION** (`/organizations`, existing) | a server-side grouping of vaults, members, roles, governance/risk controls | hosted-layer only; gives NO covenant-level multi-owner security; an admin is not an owner |
| **ON-CHAIN ORGANIZATIONAL ROOT** (`/org-roots`, new) | a `PolicyVault.v0.7-root.sil` covenant UTXO holding N owner slots, M-of-N quorum, emergency FREEZE quorum K, recovery quorum R + delay, succession key + delay | consensus-enforced; every rooted vault's owner operations require this root input |

Every API response, UI surface and MCP tool output that describes a root
carries `authorityModel: "ON_CHAIN_ORGANIZATIONAL_ROOT"`; hosted organizations
carry `authorityModel: "HOSTED_ORGANIZATION"`. A hosted organization MAY link
to a root (`onChainRootId`), but the link is informational: it never grants
authority. Legacy single-owner vaults (v0.4/v0.4.1/v0.5/v0.6) carry
`authorityModel: "SINGLE_ON_CHAIN_OWNER"` and are never presented as M-of-N.

- **GLOBAL VAULT-RECORD UNIQUENESS (RC33-ID-01, 2026-09-11; `sdk/src/vault-identity.js`).** `VAULT` is ONE category shared by every covenant generation (v0.1 … v0.7-kas), keyed by `vaultId`, discriminated only by each record's own schema tag. A vault identity is therefore global: (1) a NEW genesis of ANY generation refuses an identity that a vault record of ANY generation already holds, or that ANY existing creation request (wallet request or org-root request, in ANY state) already names — closed code `VAULT_ID_IN_USE` (HTTP 409), refused BEFORE anything is built or written; identities are never recycled (a withdrawn or rejected draft keeps its identity; a new creation takes a fresh one). (2) A request's own signature and submission are refused with the same code — before the signature is accepted, before any claim and before any broadcast — when a vault record of any generation holds the identity or when ANOTHER request that may already carry a signed transaction or a broadcast names it (any state outside the closed `UNCOMMITTED_REQUEST_STATES` allowlist; unknown states count as committed). Every genesis build, signature acceptance and submission of every family runs under a per-identity lock taken INSIDE the existing root / signer / request lock (internal read-only review finding F1, 2026-09-11: without it the commit-phase check is check-then-act and a pre-correction pair of drafts naming one identity could double-sign or double-broadcast under concurrency — `sdk/test/vault-identity-uniqueness.test.js` cases 16–18, RED on the first correction, GREEN on the committed one). (3) Genesis COMPLETION of EVERY generation is an ATOMIC CREATE-ONLY write — the store's create-only primitive (`link()`/`EEXIST` on the JSON driver, `INSERT … ON CONFLICT DO NOTHING` on PostgreSQL) is the arbiter, never a read followed by an overwrite; an existing record is accepted only when it is byte-for-byte the same genesis outcome (same schema tag, every field except `updatedAt` / `createdAt` / `label`), otherwise the completion is refused as `RECONCILIATION_REQUIRED`: the existing record (whatever generation wrote it) is preserved untouched and the proven chain effect stays on the request with its signed bytes, txid and submission claim for reconciliation — nothing is rebuilt, re-signed or rebroadcast. A refusal names only the identity the caller supplied, never the other record's owner, root, label, generation or state. Regressions: `sdk/test/vault-identity-uniqueness.test.js` (the reviewer's six cases + every generation), `sdk/test/vault-identity-store-arbiter.test.js` (real JSON and PostgreSQL arbiters), `sdk/test/hosted-vault-identity-uniqueness.test.js` (served boundary).
- **TRUTHFUL SUBMISSION OUTCOMES, OBSERVATION-ONLY GENESIS RECOVERY, DURABLE HEADLESS RESERVATION (RC35-REC-01 / REC-02 / RES-01 / legacy F4, independent RC35 affected review 2026-09-11; owner repair directive of the same day).** (1) **Classification** — `sdk/src/submission-classification.js` is the ONE classifier of a node's answer to `submitTransaction`, used by EVERY submitter (headless v0.1 / v0.2, v0.2 requests, v0.4.1, v0.5, v0.6, v0.7 root + rooted genesis, v0.7-payment-hd, v0.7-kas — genesis, transition, deposit and delegate paths alike): `REJECTED` = the node's `Rejected transaction {id}: {reason}` envelope naming THIS attempt's txid with a reason that is not an already-known reason; `ALREADY_KNOWN` = the exact rusty-kaspa answers `RejectAlreadyAccepted` ("transaction {id} was already accepted by the consensus"), `RejectDuplicate` ("… is already in the mempool"), `RejectDuplicateOrphan` — POSITIVE answers about the submitted transaction, never a rejection: the claim is kept and the submitter proceeds to observation exactly as after an accepted response; `AMBIGUOUS` = transport failures, an envelope naming ANOTHER txid, malformed envelopes — the claim is kept (`RECONCILIATION_REQUIRED`). A `REJECTED` verdict settles a negative ONLY with chain confirmation (`sdk/src/genesis-recovery.js`): a genesis when its expected output is provably ABSENT under its txid, a transition / deposit when its input is still UNSPENT AND every frozen output is absent; the settled negative carries `submissionOutcome.proof` (`boundRejection`, `outputsAbsent`). A rejection the chain contradicts, or whose check fails, keeps every claim. (2) **Recovery of persisted negatives** — a request persisted `SUBMISSION_REJECTED` is recovered by OBSERVATION ONLY through the SAME request (KAS / v0.4.1 / v0.5 / v0.6 / v0.7-payment-hd submit or reconcile entries; the v0.4.1 `POST /wallet/v4/requests/:id/reconcile` route; the v0.4.1 unresolved-creation guard and `?unresolved=1` listing count a non-established negative as unresolved): an observed output completes it (claim re-established first, so a conflicted completion leaves it in place); an unobserved output keeps an ESTABLISHED negative (the observer's proof, the bound-rejection proof, or a legacy record whose stored answer is a bound rejection of its own txid) as it is and PROTECTS every other (the reviewer's "already accepted" false negative, an absent or unbound answer): claim re-established, `RECONCILIATION_REQUIRED`. Nothing is rebuilt, re-signed or rebroadcast; identities are never recycled. The identity arbiter counts a `SUBMISSION_REJECTED` request as uncommitted at commit time ONLY when its negative is established (`requestProvablyUncommitted`). (3) **Root / rooted genesis recovery (REC-02, legacy F4)** — `POST /org-roots/:rootId/requests/:id/submit` on a `rootGenesis` / `rootedVaultGenesis` request in `BROADCAST` / `CHAIN_SEEN` / `RECONCILIATION_REQUIRED` / `SUBMISSION_REJECTED` (or `CHAIN_VERIFIED` with incomplete records) RECOVERS it by observation without any pre-existing root record: the expected outcome is derived from the original request and the immutable definitions (root script recompiled from template + initial state and compared to the build; the frozen output must pay that script and carry the request's covenant id; the signed bytes must reconstruct the frozen txid); the root record is created ATOMICALLY (create-only) or accepted only as this genesis's own root (generation 0 at this outpoint, or a later generation proven by this genesis's receipt) — a different record under the covenant id is never replaced; receipt / audit / claim release are idempotent and the request is written last (a crash between any two steps is replayed). Recovery of an existing attempt is gated on the OPERABLE set, never the creatable set (the creation kill switch keeps it available). Hosted tenancy scopes a pending genesis (no root ACL yet) to its CREATOR: a foreign principal receives the non-oracle 404 before any lock or node call; `POST /org-roots/:rootId/reconcile` stays root-scoped (404 without a root record — SDK-level `reconcileOrgRootV7` routes a missing root with a recoverable genesis request to the same completion: `GENESIS_PENDING` / `ADVANCED`). v0.5 / v0.6 genesis submits accept the same recovery states (observation only; refused on mainnet because these generations were never mainnet-authorized). (4) **Headless reservation (RES-01)** — the headless v0.1 / v0.2 creators (`sdk/src/create-vault.js`, `sdk/src/vault-ops-v2.js`; direct SDK / testnet utilities, never a hosted route) write a DURABLE headless creation record (`Categories.REQUEST`, schema `policyvault-headless-creation/v1`: creator, vault identity, immutable definition, exact expected outcome, signed bytes) the moment the signed genesis exists — BEFORE the submission claim and the broadcast — so the identity stays reserved across any restart; the arbiter ALSO treats a durable submission claim naming an identity as a reservation in both phases (only the caller's own transaction is excluded), which covers claims retained by earlier runtimes; `sdk/src/headless-creation.js` recovers a record by observation only, lists legacy retained claims, and completes a legacy claim ONLY from the operator-supplied ORIGINAL definition (derived identity must equal the claim's; covenant id read from the observed output; unobserved → the claim stays exactly as it is). Supported contract: ONE service writer per data root; the per-identity lock is process-local; the create-only arbiters hold across processes. Regressions: `sdk/test/submission-classification-rc35-rec01.test.js`, `kas-genesis-outcome-recovery-rc35-rec01.test.js`, `org-root-genesis-recovery-rc35-rec02.test.js`, `legacy-genesis-recovery-rc35-f4.test.js`, `headless-identity-reservation-rc35-res01.test.js`, `hosted-org-root-genesis-recovery-rc35-rec02.test.js`.
- Rooted vaults reuse `VAULT` with a v0.7 manifest (`sdk/src/manifest-v7.js`): `{ manifestVersion: "policyvault-rooted-vault-manifest-record/1", vaultId, contractVersion: "policyvault-0.7-payment" (later: "policyvault-0.7-kas"), orgRootCovenantId, rootPins (exact), template, state, live, … }`.
- Slot signature envelopes are the `policyvault-org-root-slot-request/1` / response envelopes of `core/signer/org-root-slot-v7.js` (signer v1) — and, once Track G lands, `policyvault-signer/2` bound envelopes. ### 2.1 Hosted tenancy on `/org-roots/*` and `/wallet/v7/*` (rc11 internal security review F-04, 2026-09-04)

Hosted mode REQUIRES a principal on every route of both families. Authority
derives ONLY from durable covenant facts — the root record's ACTIVE owner
slots (normalized through the shared core) plus the pinned successor key
(read-only except for a succession request), the rooted vault's own agent
registry / HD forest leaves, and a request's own creator/signer — never from
`/organizations` roles, request bodies or headers.

| route | rule |
|---|---|
| `GET /org-roots`, `GET /org-roots/:id/requests`, `GET /wallet/v7/requests` | tenant-scoped listings (a caller sees only what it participates in; a live root answers non-participants with 404 on its request list) |
| `GET /org-roots/:id`, `/vaults`, `/requests/:rid` | root participant (active slot or successor) or the request's creator; foreign → 404 `ROOT_NOT_FOUND` / `REQUEST_NOT_FOUND` |
| `POST /org-roots` (genesis) | the funding `signerAddress` MUST be the principal (403 `SIGNER_NOT_PRINCIPAL`) |
| `POST /org-roots/:id/vaults`, `POST /org-roots/:id/reconcile` | an ACTIVE owner slot (successor → 403 `NOT_AN_ACTIVE_SLOT`); genesis signer = principal |
| `POST /org-roots/:id/requests` (root action) | participant (else 404 before any lock), `signerAddress` = principal, then the SDK's active-slot rule (successor only for succession) — a stranger can no longer lock a live root |
| `GET .../slot-request/:slot`, `POST .../slot-signatures` | only the wallet holding THAT slot's key (403 `NOT_AN_ACTIVE_SLOT`) |
| `POST .../signature`, `/finalize`, `/submit`, `/reject` | the request's creator or an active owner; the successor only for a succession request (403 `REQUEST_FORBIDDEN` for a read-only participant) |
| `POST /wallet/v7/requests` | principal holds build authority on the rooted vault (active root owner or registered agent); `signerAddress` is a participant; an agent builds only for itself; an owner may build for its registered agents; `tokenDeposit` is built by a participant for its own key |
| `GET /wallet/v7/requests/:id`, `POST .../signature|submit|reject` | the request's signer or a vault participant (mutations: signer or a wallet with build authority) |

Machine credentials reach both families with `read:org-roots` /
`write:org-roots` (F-06) and act as their creating wallet.

## 3. Web (Track B-web) consumption

- Organizations tab: two clearly separated sections — "Hosted organization (grouping & roles — no on-chain authority)" and "On-chain organizational root (covenant-enforced M-of-N)". The existing single-owner statement stays for legacy vaults.
- Root wizard: owner slots (N), M, K, R, delays, successor → "Exact root policy before signing" panel rendered from the SDK/core explain output (never from UI-local arithmetic) → funder signs genesis → PENDING (not success) → reconcile → root live.
- Root detail: N configured slots / M / K / R / delays / generation & nonce / frozen / pending request / action class / signatures present vs required / signer identity + address per slot / signer-visible manifest digest / outcome ladder / warnings.
- Slot signing: the connected wallet signs ONLY its own slot through the signer adapter (`web/signer-kasware-adapter.js` → `signPskt` on the root input; extract the 65-byte SIGHASH_ALL signature exactly as `collectApprovalV4` does) and POSTs the response envelope; other owners' envelopes are imported (paste / file / QR via the existing air-gap shuttle) and POSTed the same way. Finalize is offered only when present ≥ required; submit only after SIGNED.
- Rooted vault creation bound to a chosen root; owner operations on a rooted vault are created as ROOT REQUESTS (they show the root quorum, never a single-owner button).
- Dangerous actions (ownerRecover, succession, rotate, unfreeze) require an explicit typed confirmation and show: what changes, that recovery/succession LAND FROZEN, the delay, and that a heartbeat AUTHORIZE keeps recovery closed.
- No UI shortcut may bypass the server/core verification; the browser re-verifies the org-root manifest locally through the core bundle before asking the wallet to sign (`web/verify-intent.js` route for `policyvault-org-root-manifest/1`, Track F wires the router; until then use the bundle's `orgRootManifestV7.verifyOrgRootIntentManifest` directly).

#### 6.1.1 Hosted tenancy on `/wallet/v5|v6/*` (rc11 internal security review F-04, 2026-09-04)

The token surface receives the request context and applies the v4 rule set
exactly: a principal is REQUIRED (401); `create` binds `signerAddress` to the
principal (403 `SIGNER_NOT_PRINCIPAL`); `requests` needs build authority on
the controller (owner or registered agent; foreign/unknown/other-generation
vault → 404 `VAULT_NOT_FOUND`), a participant signer (403
`SIGNER_NOT_PARTICIPANT`), agent self-only (403 `SIGNER_NOT_PRINCIPAL`);
listings are tenant-scoped; `GET /:id` and `signature|submit|reject` are
scoped to the request's signer or a vault participant (mutation: signer or a
wallet with build authority; else 403 `REQUEST_FORBIDDEN`). `tokenDeposit` in
hosted mode is built by a participant for its own key (a third-party
depositor is not a hosted flow on these NOT-production generations).

### 6.3 Web (Track H-web)

Vault cards and creation flows are VERSION-AWARE: a token (v0.5) vault shows the asset descriptor identity, token balance in atomic units + symbol, and the KAS fee reserve SEPARATELY, with the sentence "token amounts and KAS are never converted into each other"; a v0.6 vault shows "optional atomic composability — no real DEX venue is supported (fixture/conformance only)"; a rooted HD vault shows the delegation tree (levels, per-level caps/budgets/counters, the effective intersection at the selected leaf), delegate-creation (`delegateSetChildRoot`) and revocation flows, and the verbatim expiry sentence; legacy single-owner vaults keep the truthful single-owner statement; no UI arithmetic on amounts (bundle `amounts` only); refusal explanations for the closed codes above; PENDING is never success.
