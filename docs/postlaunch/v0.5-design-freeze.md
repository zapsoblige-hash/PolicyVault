## Frozen carriage: TRANSACTION-DERIVED VERIFIED TEMPLATE CARRIAGE

D1.1 Variant C. Canonical name rule: Variant C is never called
"argument-supplied" — Variant B (caller pushes template bytes as call
arguments) is the argument/caller-supplied design.

| Variant | Disposition |
|---|---|
| C — transaction-derived verified template carriage | **FROZEN DESIGN** |
| B-lean — caller-supplied, hash-verified | proven FALLBACK only |
| A — baked-in template | historical / reference implementation only |

Rationale (owner): C preserves the same dual-binding security properties;
introduces no caller-supplied template transport; keeps the controller call
interface effectively unchanged; reuses template bytes already present in
the transaction; verifies the template before treating foreign token state
as authoritative; materially reduces controller compute, transaction size,
mass/relay-fee burden, and estimator cost; remains standard at the target
shape; requires no asset-descriptor schema change.

## I. Frozen architecture

1. **Dual binding is non-negotiable.** Every supported token spend
   requires BOTH (A) controller/covenant-ID authorization and (B)
   hash-verified token template/output identity. Either binding failure
   MUST fail closed. Covenant-ID answers WHO is authorized; it does NOT by
   itself establish WHICH asset/output is authorized.
2. **Template carriage.** The controller pins the accepted VM template
   hash; pins the template geometry required to make the unframed VM
   hash unambiguous; derives prefix/suffix from the token input's
   consensus-visible redeem; verifies those bytes through the
   consensus-relevant template mechanism; does not trust foreign token
   state before successful verification; verifies successor/output state
   against the accepted template. Never duplicate full template bytes
   inside the controller redeem. Never add caller-supplied template bytes
   to normal production builder interfaces.
3. **Hash semantics — two identities, separate forever.**
   `templateVmHashBlake2b256`: consensus/VM financial-boundary identity,
   blake2b-256 over `prefix || suffix`, REQUIRED for spendable binding;
   geometry MUST be pinned because the concatenation is unframed.
   `templateKcc1HashBlake3`: KCC-0001 convention/interoperability
   identity, BLAKE3 over LE64-framed fields, optional/interoperability
   only, can NEVER substitute for the VM hash. Never infer one from the
   other.
4. **Asset descriptor `policyvault-asset-descriptor/1` — FROZEN.**
   Closed schema; closed enums; exact version match; unknown fields
   refuse; unknown versions refuse; dual binding mandatory; token
   covenant ID mandatory; non-empty accepted transfer-template set; VM
   hash mandatory; template geometry pinned; state layout pinned;
   KCC-0001 identity optional; issuer/controller powers explicitly
   declared; atomic-unit values deterministic; display decimals
   display-only; no protocol-level blessed asset list. Carriage remains
   an execution concern — no transport/witness details in the descriptor.
5. **Two accounting domains.** Token protected value and KAS fee reserve
   are independent. Token conservation MUST be independently verified.
   Never: use KAS conservation as token proof; reduce a token budget
   because a KAS fee was paid; combine token amount and fee-reserve
   accounting; let UI/indexer metadata become authoritative financial
   state.
6. **Asset onboarding (D2 direction, frozen).** Owner-authorized
   acceptance; deterministic descriptor validation; deterministic
   template/hash corroboration; descriptor hash pinned into vault policy;
   descriptor downgrade/substitution refused; issuer/controller powers
   explicitly surfaced; uncorroborated trust properties visibly
   DECLARED-ONLY; indexers assist discovery/display only; owner policy
   chooses accepted assets; explicit asset removal; KAS-only vaults remain
   supported without forced migration.
7. **Standardness envelope.** The token path's static sig-ops scale with
   the unrolled family bound (one checkSig per iteration); the standard
   P2SH limit is 15; therefore accepted templates with family bound > 15
   MUST fail the v0.5 standardness/onboarding gate unless future
   consensus/standardness evidence explicitly changes that. A descriptor
   never becomes spend-enabled if its selected template violates the
   envelope.
8. **Fees.** The script-unit-only D1 approximation is superseded.
   Production fee tooling accounts for transaction mass, transient mass,
   the estimator result, and the node-configurable relay floor. Measured
   bound-2 C target (evidence, never a hard-coded protocol assumption):
   controller 44,939 script units excl. sig-op; controller redeem 968 B;
   controller sigscript 1,156 B; transaction 3,282 B; fee mass 6,564
   grams; minimum relay at the source-default 100 sompi/gram ≈ 0.0066 KAS;
   controller estimator 219,100. Never hard-code 0.0066 KAS.

## II. Implementation phase (dependency direction)

New v0.5 covenant/version lineage; the frozen v0.4/v0.4.1 production
covenants are never modified. Order: raw transaction/state → canonical
token parser → `policyvault-asset-descriptor/1` validation → asset
adapter → policy evaluation → manifest → explain → local deterministic
verification → external signer → covenant enforcement. Deterministic
token semantics live in the shared portable core; browser, Android, iOS,
server, CLI, self-host, MCP, x402 and future USI reuse it. MCP stays thin
with no independent token-policy logic.

Required work (owner list): A descriptor validator promoted into the
core with public interfaces/tests; B canonical KCC20 adapter; C
transaction-derived verified template carriage in the new v0.5 covenant;
D builder/preflight (token per-spend cap, periodic cumulative token
budget, period accounting, allowlist/recipient policy, owner
controls/recovery, token conservation, separate KAS fee reserve,
descriptor pin verification, template variant verification,
family-bound standardness gate); E manifests/explain with token identity,
token amount, token policy impact, KAS fee/reserve impact, issuer powers,
descriptor hash, template identity, verification result shown
separately; F fee/mass estimation from the real estimator/mass model;
G `core/assets/test/` in EVERY applicable core-suite runner before any
successor release gate.

## III. Hostile test requirements (implementation-complete bar)

Wrong covenant family · wrong token template · wrong accepted-template
variant · alien token input · hidden extra token-family output · token
conservation +1 / −1 · over-cap spend · budget exhaustion ·
period-accounting misreport · descriptor substitution · descriptor
downgrade · unknown descriptor version · unknown descriptor field ·
wrong VM hash · wrong geometry · geometry/split manipulation · wrong
signer · ownership theft · controller-KAS drain riding a token spend ·
token/KAS accounting confusion · issuer-property omission ·
non-standard family bound · malformed token state — plus any new case
discovered during implementation. Happy-path tests alone are
insufficient.
