# v0.7-hd (rooted hierarchical delegation) — ECONOMIC VIABILITY (gate I4)

Consensus validity and standardness are necessary, not sufficient. This
record computes what `contracts/PolicyVault.v0.7-payment-hd.sil` (contract
`PolicyVaultRootedTokenHD`, `tools/gen_v7_payment_hd.js`) actually costs in
KAS network fees and in `MAX_STACK_SIZE` headroom, per operation, at shallow
and maximum proof depth. **Every number below is a real-engine measurement**
from `tests/vm/tests/v7_hd_production.rs`
(`hd_rooted_measurement_redeem_units_mass_sigops_and_stack`, run
2026-09-03, real `TxScriptEngine`, rusty-kaspa v2.0.1, real Schnorr, real
KCC20 token side, real production root `contracts/PolicyVault.v0.7-root.sil`)
under PRODUCTION sig-op pricing (`Gram(1000)` = 100,000 priced units per
executed `checkSig`). Nothing here is estimated except where explicitly
labeled an estimate (compute-budget interpolation, §4).

For the STACK viability finding specifically — the binding constraint for
hierarchical delegation, not fee economics (see §2) — this record is the
gate I1 asked for: "MEASURE FIRST under rooted composition… decide the
MAXIMUM PROVEN ROOTED LEVEL from measurement."

must), so every call reveals the same redeem and therefore the same 5
`checkSig` call sites (one per HD entrypoint: `hdSpend`, `childSpendL2`,
`childSpendL3`, `delegateSetChildRoot1`, `delegateSetChildRoot2`). 5 is well
inside `MAX_STANDARD_P2SH_SIG_OPS` (15).

## 2. THE BINDING CONSTRAINT IS STACK, NOT FEE OR MASS

| level | peak combined stack | headroom to 244 |
|---|---:|---:|
| 1 (`hdSpend`) | 119 | 125 |
| 2 (`childSpendL2`) | 162 | 82 |
| **3 (`childSpendL3`)** | **208** | **36** |
| `delegateSetChildRoot1` | 51 | 193 |
| `delegateSetChildRoot2` | 75 | 169 |

These numbers are **byte-for-byte identical** to the un-rooted experimental
probe's measurements (design record §6.5). This is not a coincidence: the
organizational-root authorization machinery (`requireRootAuthorization`,
`requireOnlyRootCovenantInputs`, `requireOnlyRootAndTokenCovenantInputs`)
lives ENTIRELY inside `ownerControl` and `ownerRecover` — two call sites the
HD spend/delegation entrypoints never invoke. Composing hierarchical
delegation with the rooted vault architecture therefore cost **zero
additional stack items** on the delegate path, because the two concerns
never share a code path within one call. This is the direct, measured
verdict on the design freeze's binding question ("if MAX_LEVEL 3 cannot fit
with adequate stack… STOP and report the maximum PROVEN rooted level"):

**MAXIMUM PROVEN ROOTED LEVEL = 3**, with 36 of 244 stack items of headroom
— the same margin the probe measured for the un-rooted case, now confirmed
in composition with the rooted owner-authority architecture. A level-4 spend
was not built (no entrypoint accepts one by construction) but would
extrapolate to the same ~254 items the probe recorded as OVER the limit,
since the HD chain logic contributes the same marginal stack cost per level
here as it did in the probe (no rooted-specific term changes it).

## 4. Compute budget model (engineering estimate, not an independent measurement)

`core/model/compute-budget-v7-hd.js` selects a committed budget per
operation. Shallow-shape sufficiency is PROVEN for all five operations
(§1); deep-shape sufficiency is PROVEN only for `childSpendL3` and
`delegateSetChildRoot2` (the only two operations this wave measured at
maximum depth). The module conservatively applies the LARGER of those two
measured shallow→deep deltas (+126,973 units for spends, +42,152 units for
delegation ops) to every operation in its family, which is SOUND (a
shallower chain has strictly fewer proof components than the one actually
measured, so its true delta cannot exceed the applied one) but not as tight
as a dedicated per-level sweep. **Tighten with real `hdSpend` /
`childSpendL2` / `delegateSetChildRoot1` deep measurements before relying
on the interpolated mid-range numbers for anything beyond a safe upper
bound.**

**Finding — hierarchical delegation costs roughly 3.7× the flat delegate
spend at level 1, and going all the way to level 3 (two full delegated
levels) adds only ~1% more on top of that** (91,160 → 91,892 fee mass,
level 1 → level 3, shallow). The dominant cost is committing to the HD leaf
format and its explicit SIGHASH gate at all (redeem +33,194 B, §3), not the
depth of delegation actually used — an owner who never delegates still pays
the level-1 HD price if they choose this covenant generation over the flat
v0.7-payment one. This is the real economic trade PolicyVault asks an owner
to make for hierarchical delegation, and it is larger than a v0.6 atomic
swap (0.0816 KAS) at every level measured here.

## 6. Honest limits

1. **Relay floor only**, same caveat as `docs/postlaunch/v0.7-economic-viability.md`
   — a real fee market multiplies every number here linearly.
2. **Two proof depths only** (shallow and maximum) were measured per
   operation, and only for `childSpendL3` / `delegateSetChildRoot2` at
   maximum depth. No monthly-cost / owner-set-curve tool
   (`tools/v7-fee-curve.js`-equivalent) was built for HD this wave — the
   flat v0.7 tool does not model the HD leaf format, and building an
   HD-specific one is future work, not done here.
3. **These are TESTNET-shaped measurements of production bytes on the real
   engine, not live mainnet or even live testnet transactions.** v0.7-hd is
   NOT testnet-verified (gate I5 in `docs/postlaunch/v0.7-hd-readiness.md`
   records that live testnet lifecycle was not run this wave). Nothing here is an audit.
4. **The compute-budget model is a documented estimate for three of the
   five operations** (§4) — funds-safety-relevant, since an under-committed
   budget fails a live transaction, but it errs conservatively (over-, never
   under-committing) by construction, not merely by intent.
5. **`contracts/PolicyVault.v0.7-payment-hd.sil` is NOT covenant-byte-frozen.**
   Every number in this record is subject to change if the candidate is
   revised before any future freeze decision.


## Correction (2026-09-03, Wave 2): KIP-9 storage mass and UTXO plurality

Every storage-mass figure in this record was computed with the plurality-1
model (`core/model/storage-mass.js` before commit 6b9da7e). rusty-kaspa
v2.0.1 weighs each UTXO by its storage plurality p = ceil((63 + script
length + 32 if it carries a covenant id) / 100), contributing C·p²/amount —
a covenant-bearing P2SH output has p = 2 and therefore weighs FOUR times the
plain-output estimate used here. Consequences: (1) the dust / minimum-output
thresholds stated for covenant outputs (token notes, protocol-fee outputs,
covenant successors) are understated by up to 4×; the exact numbers are now
produced by the corrected module and enforced pre-sign by the builders'
storage-mass preflight; (2) no live evidence is invalidated (every accepted
transaction was accepted by the node under the correct rule); (3) the
frozen covenant bytes are unaffected (storage mass is not a covenant rule).
Found live on 2026-09-03 when an HD level-1 spend with a 0.05 KAS covenant
carry was refused at 840,919 grams (pinned as an exact regression vector in
`core/model/test/storage-mass-plurality.test.js`).

## KIP-9 plurality — quantitative re-check (2026-09-04, post-Wave-2 hardening)

The Wave-2 qualitative note is now quantified with the exact corrected
model (`core/model/storage-mass.js`, verified by reproducing the live
refusal EXACTLY: the HD level-1 spend with a 0.05 KAS covenant recipient
carry = 840,919 grams, the plurality-1 model said 210,229, the node
refused at 840,919). For any token spend whose recipient is a
COVENANT-bearing P2SH note (plurality 2, four times a plain output's
weight), the minimum recipient/covenant-note carry that keeps a
representative spend within the 500,000-gram limit is **≈ 0.087 KAS**
(single-covenant-cell floor C·4/limit = 0.08 KAS); the production tools and
builders use a safe **0.2 KAS** carry (`RECIPIENT_CARRY`, wired with the
storage-mass preflight in every builder). A 0.05 KAS carry is REFUSED at
build (`STORAGE_MASS_OVER_LIMIT`) — no funds risk, frozen bytes unaffected
(storage mass is a consensus validity rule, not a covenant rule). Old-model
carry floors (~0.02 KAS) were 4× too low and must not be published.
