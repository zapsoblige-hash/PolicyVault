# v0.5 asset descriptors & owner onboarding — D1/D2 design draft

Status: **DESIGN-STAGE DRAFT — the v0.5 design gate decides adoption.**
Executable reference: `core/assets/descriptor.js` (+ its test suite),
which is imported by NO production path. VM evidence:
`tests/vm/tests/v5_experiment_token_dual_binding.rs` (12 green tests on
the real TxScriptEngine). Companion research: `v0.5-token-d1-spike.md`.

## 1. The descriptor schema (`policyvault-asset-descriptor/1`)

One closed, versioned, fail-closed record per asset, owned by the
shared deterministic core and reused verbatim by browser, mobile,
server, CLI, self-host, MCP, x402, USI, and SDK surfaces. No adapter,
service, indexer, or UI re-implements or overrides it.

| Field | Type | Meaning |
|---|---|---|
| `schema` | `"policyvault-asset-descriptor/1"` | exact-match version gate; unknown versions REFUSE (never route to a default) |
| `assetId` | 64-hex | PolicyVault's stable identity for the asset (owner-scoped; see §3) |
| `displayName` | string ≤64 | display only; never an identity |
| `tokenStandard` | closed enum, today `"kcc20/1"` | unknown standards REFUSE |
| `tokenCovenantId` | 64-hex | **BINDING 1** — the KIP-20 token family/controller lineage authorized to carry the asset |
| `acceptedTransferTemplates[]` | non-empty | **BINDING 2** — hash-verified template pinning (below) |
| `decimalsDisplay` | int 0..18 | DISPLAY metadata only — KCC20 has no consensus decimals; all amounts remain atomic-unit integer strings |
| `issuerPowers` | all 8 keys explicit booleans | declared asset trust properties (below) |
| `notes` | optional string ≤2000 | free text, never semantic |

Every object is a **closed schema**: any unknown field refuses. Token
amounts everywhere are non-negative atomic-unit **decimal strings**
with sompi-grade rejection (no signs, leading zeros, floats, exponents;
u64-bounded) — and they are **never KAS**: the KAS fee-reserve domain
is separate end to end (§4).

### Accepted transfer template (per entry)

| Field | Meaning |
|---|---|
| `templateVmHashBlake2b256` | REQUIRED. blake2b-256 over `prefix || suffix` — the identity the **in-VM** `readInputStateWithTemplate` / `validateOutputStateWithTemplate` helpers verify at consensus. This is the hash that makes outputs spend-safe. |
| `templateKcc1HashBlake3` | OPTIONAL. BLAKE3-256 over `LE64(len(prefix))‖prefix‖LE64(len(suffix))‖suffix` — the **KCC-0001 convention-level** template identity used by ecosystem tooling/registries. |
| `prefixLen`, `suffixLen` | template split geometry (ints, bounded) |
| `stateLayout` | closed enum, today `"kcc20-state/1"` (the KCC20State record) |

**Hash-convention discipline (binding rule):** the two hashes are
different conventions over the same underlying bytes and are NEVER
conflated or inferred from one another. In-VM pinning requires the
blake2b value; ecosystem interop uses the KCC-0001 value; a descriptor
missing the blake2b value cannot authorize spends, full stop.

### The dual binding (non-negotiable, VM-PROVEN)

A v0.5 transition involving the asset must satisfy **both**
`tokenCovenantId` (WHO is authorized — family membership/enumeration by
covenant id) **and** an entry of `acceptedTransferTemplates` (WHICH
bytes carry the asset — template reconstruction of every family
continuation). Either failing fails closed. The V5 probe demonstrates
both checks executing in-covenant on the real engine and refusing every
core substitution class.

### Issuer powers — explicit trust properties

`issuerPowers` carries all eight keys (`mint`, `burn`, `freeze`,
`blacklist`, `redemptionControl`, `upgradeMigration`,
`controllerRotation`, `emergencyControl`) as **explicit booleans —
omission is not deniability** (a missing key refuses). These are
properties of the ASSET, not PolicyVault guarantees: PolicyVault
enforces spending policy deterministically regardless, and every
surface (explain output, UI, compliance exports, MCP responses)
surfaces them verbatim. An issuer-controlled asset is never described
as trustless. Descriptor authorship cannot *discover* powers; §3
defines how declared powers are corroborated at onboarding.

## 2. Production envelope (measured 2026-09-01, real engine)

| KCC20 family bound | controller units | token units | tx grams | ctrl sigscript |
|---|---|---|---|---|
| 2 (v0.5 target: position + 1 recipient) | 74,484 | 18,709 | 932 | 7,240 B |
| 4 | 126,772 | 31,285 | 1,581 | 12,104 B |
| 8 | 231,348 | 56,437 | 2,878 | 21,832 B |

- v0.5 target shape ≈ **8 + 2 compute-budget units ≈ 0.0009 KAS fee
  class** (project convention: 1 budget unit = 10,000 script units;
  grams = units/100; fee impact = grams × 100 sompi). Envelope guards
  are pinned in the probe suite.
- Sig-ops: 1 (controller Schnorr) / 0 (covenant-id token path) — far
  under the mempool's `MAX_STANDARD_P2SH_SIG_OPS = 15`. All outputs are
  version-0 P2SH — a standard script class. Post-Toccata, the legacy
  100k standard mass cap is relaxed; the per-tx ceiling is the
  block-fit mass limits, orders of magnitude above these shapes.
- The mempool admission estimator (`estimate_script_units_upper_bound`
  = sigops×units + total_script_len×100) over-estimates our executed
  cost ~11× (827,500 vs 74,484 at bound 2) — still comfortably
  admissible, but fee/priority tooling must budget from the ESTIMATOR,
  not the executed cost.
- **Key scaling finding:** controller cost scales with the PINNED
  TEMPLATE SIZE because the reference pattern bakes the token
  prefix/suffix into the controller's own redeem. Design note for the
  implementation phase: supply prefix/suffix as call ARGUMENTS verified
  against a pinned hash (the descriptor's blake2b value), keeping the
  controller redeem small; the bytes still ride the transaction, but
  the controller's own continuation stops re-carrying them. This is an
  optimization decision for the freeze gate, not assumed here.
  **RESOLVED 2026-09-01 (D1.1, `v0.5-template-carriage-decision.md`):**
  the driver was constant INLINING (four verbatim template copies in
  the baked-in redeem); the recommended carriage is TRANSACTION-DERIVED
  (the controller slices the proven template out of the token input's
  own redeem — no call-interface change, no descriptor change):
  controller sigscript constant 1,156 B, −40 % compute, −65…−75 %
  bytes/fee. The fee class above was script-unit-only; the post-Toccata
  minimum relay fee at the source default (100 sompi/gram, mass-priced)
  is 0.0187 KAS baked-in → 0.0066 KAS tx-derived at bound 2.

## 3. D2 — owner onboarding of an asset

**Principles:** no protocol-level blessed list; discovery/indexers
assist display only; nothing external is authoritative at the financial
boundary; owner policy chooses accepted assets; KAS-only vaults are
never migrated implicitly.

Flow (all steps wallet-session-gated owner actions):

1. **Obtain a descriptor** — from the core's shipped verified standard
   descriptors, from an issuer's publication, or hand-authored. Origin
   is irrelevant to safety: the descriptor is DATA until verified and
   accepted.
2. **Deterministic corroboration (core, not services):** the client
   re-derives `templateVmHashBlake2b256` (and the KCC-0001 hash when
   present) from issuer-published template bytes, checks the geometry,
   and — where chain access exists — verifies that a live asset UTXO's
   revealed template matches byte-for-byte and that its family carries
   `tokenCovenantId`. Declared `issuerPowers` are corroborated against
   the issuing covenant's published templates where inspectable;
   anything not corroborated is surfaced as DECLARED-ONLY. An indexer
   may *suggest* candidates; it can never upgrade a descriptor's
   status.
3. **Explicit owner acceptance** — the owner reviews the descriptor
   (identity, both hashes, issuer powers verbatim, DECLARED-ONLY
   markers) and signs the vault-policy change that adds
   `(assetId, descriptor-hash)` to the vault's accepted-assets policy.
   Acceptance is an authority-EXPANDING policy mutation and uses the
   stronger governance path (owner/multisig), like every such change.
   The vault pins the **hash of the accepted descriptor**, so a
   descriptor can never silently change under an acceptance
   (descriptor-downgrade refusal falls out of the pin).
4. **Two-domain accounting from the first moment:** onboarding creates
   the asset's token-domain policy state (per-spend cap, periodic
   budget — atomic-unit strings) alongside, and never mixed with, the
   KAS fee-reserve accounting. Manifests, explain output, verification,
   and compliance exports carry the two domains as separate, labeled
   sections; no KAS fee ever silently reduces a token budget, and token
   value is never spendable as fees.
5. **Removal/rotation** — removing an asset or rotating to a new
   descriptor version is again an explicit owner policy change; pending
   requests under the old acceptance fail closed after removal.

## 4. What stays true everywhere

- Covenant/controller authorization answers WHO; template pinning
  answers WHICH; v0.5 requires both; either failing fails closed.
- Token conservation is verified independently from KAS accounting.
- Indexers/services/UI/MCP never substitute for deterministic
  verification; signer keys never enter PolicyVault; non-custodial
  always; frozen production covenants untouched until an explicit
  redesign/freeze gate.
