## 1. What the browser now proves before any wallet prompt

Before the signing modal offers ANY signing action, and again inside
`walletSign` immediately before the provider is invoked (stage `D2`),
the browser:

1. takes the EXACT `unsignedSafeJson` string it is about to hand to the
   wallet's `signPskt` and strictly decodes it (closed schemas; any
   unknown key, pre-filled signature, non-zero gas/mass/payload, or
   malformed value refuses);
2. builds the REQUESTED INTENT from its OWN action context — the
   amounts the user typed, the recipients the user entered (resolved
   through the server's single address-identity boundary), the
   client-generated vaultId at genesis, the connected wallet identity —
   never from a server description;
3. combines that with the covenant state this browser already knows
   (the vault presentation the user is looking at: live outpoint,
   covenantId, protected value, fee reserve, approver slots, agent
   policies, recipient registry);
4. derives a v1 Transaction Intent Manifest **in the browser** through
   the portable shared core (`core/intent buildIntentManifest`) and runs
   the complete fail-closed detector catalogue
   (`verifyIntentManifest`), binding the caller's independent intent and
   independent transaction decode;
5. renders the `core/explain` human-readable lines in the signing
   dialog on a FULL PASS — requested action, every output with its full
   destination key and exact KAS value, fee (with the client's cap),
   protected value / fee reserve before and after, per-spend cap and
   period budget consumption, approvals tier, policy impact, warnings,
   and the exact statement *THIS TRANSACTION DOES EXACTLY WHAT WAS
   REQUESTED AND NOTHING ELSE.* — full values only, no truncation-only
   display; plus a collapsed details block with the manifest hash,
   transaction id, verdict, and per-detector results;
6. on ANY refusal renders the unmistakable `DO NOT SIGN` state with the
   detector codes and **renders no signing action at all**; `walletSign`
   independently refuses (`VERIFICATION_REQUIRED` /
   `VERIFICATION_REFUSED` / `VERIFICATION_TX_BINDING_MISMATCH`) any
   signing attempt whose verification outcome is missing, refused, or
   bound to different bytes. A verification error is a refusal; there is
   no partial verdict and no proceed-anyway.

The wallet-prompt gate is bound to the exact payload: the passing
outcome carries the verified `unsignedSafeJson` string and `walletSign`
requires string identity with the payload it is signing.

### Flows wired

| Flow (web/app-v4.js) | Intent provenance |
|---|---|
| fresh `runFlow` (below-threshold spends + all owner ops incl. addAgent/removeAgent/rotateAgent/rePolicyAgent/setApprovers/pause/unpause/topUp/topUpReserve/recover) | the client's own `params` built from the user's inputs, plus the client-selected fuel UTXO |
| fresh above-threshold spend (informational AWAITING_APPROVALS modal) | same as fresh `runFlow` |
| approver review (`approve`) | the DURABLE server request (see §4 — the approver never saw the original form) |
| acting-agent sign after approvals | the durable server request |
| `createVault` genesis | the client's create-form context (client-generated vaultId, typed deposit/reserve, resolved approver + agent identities, optional typed fee cap) |

The client applies a fee expectation of **1 KAS**
(`CLIENT_MAX_FEE_SOMPI`) as `requested.maxFeeSompi` wherever the user
did not set an explicit cap — real PolicyVault fees are ~0.0001–0.001
KAS; the ceiling exists purely in the blocking direction so a hostile
builder cannot reroute value into the network fee.

## 2. How the browser runs the shared core

`web/` is plain classic `<script>` files served statically (no modules,
no bundler). The minimal mechanism chosen: a **deterministic repo-
generated bundle**, `web/core-bundle.js`, produced by the committed
node script `web/tools/build-core-bundle.js` (node builtins only, no
external bundlers, no npm dependencies). Properties:

- the 23 core sources (`core/intent/{canonical,manifest,verify,index}.js`,
  `core/explain/{kas,intent-explain}.js`,
  `core/signer/{errors,interface}.js`, — F1 wave —
  `core/model/{amounts,contract-version,vault-state,recipient-merkle-v3,
  agent-merkle-v4}.js`, — F2 fee/state recomputation wave —
  `core/model/{compute-budget-v3,compute-budget-v4,fee-mass,
  frozen-tx-v3,vault-state-v4,vault-transitions-v4}.js`, — residuals
  wave — `core/governance/{canonical,authority-delta,index}.js` +
  `core/explain/governance-explain.js`, activating the
  `web/gov-risk-explain.js` governance seam
  (`window.PolicyVaultCore.governanceExplain`), and — W4-refinements —
  `core/explain/risk-explain.js`, activating the SAME file's risk seam
  (`window.PolicyVaultCore.riskExplain`: the stored risk evaluation's
  composed decision/codes are RECOMPUTED from the per-adapter results
  before rendering, so a self-inconsistent record refuses —
  DECISION_MISMATCH — instead of being narrated; the per-adapter
  verdicts themselves are stored evidence, not re-derivable in the
  browser, and the rendering says so); NOTE
  `core/governance/canonical.js`'s `governanceProposalDigest` uses
  `Buffer.from` and therefore FAILS CLOSED (throws) in the browser — the
  explain path never calls it, pinned by the crossruntime suite) are
  embedded **verbatim** inside a ~50-line CommonJS loader — core modules
  are never rewritten;
- the ONLY Node builtin the core uses, `require("crypto")`, is satisfied
  by a shim providing exactly
  `createHash("sha256").update(str,"utf8").digest("hex")` (synchronous
  pure-JS FIPS 180-4 — WebCrypto digest is Promise-only),
  `createHash("sha256").update(<Uint8Array>).digest()` → Uint8Array
  (F1: the byte-native Merkle modules), and
  `randomBytes(n).toString("hex")` over `crypto.getRandomValues`;
  everything outside that exact surface fails closed;
- reproducible: same input bytes ⇒ same bundle bytes (no timestamps, no
  environment data); the header pins the sha256 of every embedded
  source; `node web/tools/build-core-bundle.js --check` byte-compares;
  `web/test/core-bundle.test.js` regenerates and asserts byte identity,
  asserts sha256-shim equality with node:crypto over adversarial
  vectors (multi-byte UTF-8, block boundaries), and asserts that
  manifests/verdicts/explanation lines through the bundle are identical
  to the real core modules;
- the loader's module set is CLOSED: requiring anything outside the
  reviewed list throws.

Load order in `web/index.html`: `core-bundle.js` → `verify-intent.js` →
`signer-kasware-adapter.js` → `wallet.js` → `identity.js` → `app.js` →
`app-v4.js`.

**Degraded page rule (honest):** if `verify-intent.js` is loaded, the
gate is mandatory and cannot be bypassed (missing core bundle ⇒ every
verification refuses ⇒ prompts blocked). If the page is served WITHOUT
the verification layer entirely (a legacy build, or a test harness that
evaluates `app-v4.js` alone), `app-v4.js` behaves as before and the
signing modal carries a visible warning: *"Independent browser
verification is not loaded in this build…"*. Client-side code cannot
defend against the server that serves the client-side code (see §5 row
1) — a hostile host would simply strip the module — so a hard failure
here would add no security, only break non-hostile legacy contexts; the
warning makes the state visible instead of silent.

## 3. Browser derivation path vs. the SDK bridge (what differs, exactly)

`core/intent/bridge/derive.js` maps the REAL builder output
(`buildV4Transaction` / `buildCreateV4`) into manifest inputs. The
browser never has that build object (`presentRequest` strips `build`
before the document leaves the server), so `web/verify-intent.js`
implements the derivation honestly from what the browser actually
holds:

| Manifest input | Bridge (server/SDK) source | Browser source |
|---|---|---|
| decoded transaction | builder's `frozenCanonicalJson` + probe `txId` | strict decode of the EXACT `unsignedSafeJson` handed to the wallet (kaspa-wasm `serializeToSafeJSON` string form, field layout read from rusty-kaspa `consensus/client/src/serializable/string.rs`); `txId` = the REQUIRED `request.txId` claim (F2-1: the `id` embedded in the unsigned payload is not the consensus txId and carries no verification weight — see residual row 3) |
| covenant-input classification | UTXO `covenantId` from the build | client knowledge: the input spending the vault's live outpoint the client knows gets the client-known covenantId (the server's Safe JSON carries `covenantId: null` on inputs); no match ⇒ refusal |
| requested intent | caller-supplied or reconstructed from the build | the client's own action context (§1.2); builder-determined values (`periodsElapsed`, `reserveConsumedSompi`) are DERIVED from the observed bytes (lockTime arithmetic against the client-known agent policy; covenant drawdown minus the requested payment) and then bounded by the verifier's limits detectors |
| stateBefore | builder predecessor state | the client's vault view (server-served chain reads fetched before the action) |
| stateAfter | builder successor state | derived client-side **through the canonical `core/model/vault-transitions-v4` builders** (F2 wave: the exact per-entrypoint successor builders the SDK's own `planOwnerOp`/`agentSpendSuccessorV4` use — covenant equations, caps, period budgets, reserve rules, pause rules, nonce rules); the successor `agentRoot` is independently recomputed (F1) and the successor `stateId` is **independently recomputed via `computeStateIdV4`** (F2) — the request's claims must EQUAL both recomputations |
| agent policy before/after | build `callExtra` + single-leaf fold cross-check against the real successor root | the client's displayed agent policy — **verified as a leaf of the recomputed registry tree that must hash to the covenant state's agentRoot** (F1); `policyAfter` and the successor root come from the SAME `applyAgentSpendV4` derivation (canonical-rebuild == single-leaf-fold asserted inside the module) |
| accounting | builder's exact 11 fields | recomputed from the decoded transaction + derived states (all BigInt); **the network fee is additionally bound to the canonical fee/mass rules** (F2 wave: `core/model/fee-mass` + `frozen-tx-v3` — the identical SDK `exactFee` call path): EXACT equality for all-ordinary-input shapes (genesis), enforced floor + structural standard-mass cap for covenant transitions; **every input's committed compute budget is pinned to the canonical proven-safe tier** (`core/model/compute-budget-v4` — the module the SDK commits from) |
| allowlist verdicts | SDK-proven membership | membership proven **under the covenant-committed `agentRecipientRoot`**: the displayed recipient list is rebuilt into a Merkle tree in the browser and its root must equal the committed root (`ALLOWLIST_ROOT_MISMATCH` otherwise; F1 wave); not a member of the root-consistent set ⇒ `ALLOWLIST_NOT_PROVEN` refusal |
| genesis stateId | build `stateId` | **the REAL canonical commitment formula** (`computeStateIdV4`, F2 wave — the pseudo-state-id placeholder is gone) recomputed over the client-derived initial state (owner = connected wallet, vaultId = client-generated, network = session); its `agentRoot` component is ITSELF recomputed from the request's disclosed `initialRegistry` leaf tuples (residuals wave — no bare-claim component remains) |

Every adopted server claim is (a) cross-checked for consistency against
everything else the client holds (the displayed review, the request
document, the client's vault view, the payload itself — any
inconsistency refuses with `REVIEW_MISMATCH`/`SERVER_CLAIM_INVALID`),
and (b) disclosed in the manifest's `BROWSER_SERVER_CLAIMED_FIELDS`
warning, which `core/explain` renders as a visible line on the signing
screen.

## 4. Detection coverage (the required hostile classes)

All cases below are covered by `web/test/verify-intent.test.js` +
`web/test/app-v4-gate.test.js` as policy-invalid adversarial test
transactions modeling a hostile server/builder; each produces a REFUSED
outcome with the listed code(s), and a refused outcome provably blocks
the wallet prompt (no confirm button rendered; `walletSign` D2 refuses
before any provider call).

| Hostile case | Detector code(s) observed |
|---|---|
| recipient substitution (tx pays someone else than requested) | `HIDDEN_RECIPIENT` |
| payment amount inflation | `HIDDEN_RECIPIENT` (no output pays the requested recipient the requested amount) |
| hidden extra output funded from the covenant | `RESERVE_RULE_VIOLATION` (impossible reserve drawdown) |
| hidden extra output funded from fuel | `UNEXPECTED_OUTPUT` + `HIDDEN_RECIPIENT` |
| change rerouted to a third party | `HIDDEN_RECIPIENT` |
| fee inflation beyond the request's expectation | `EXCESSIVE_FEE` (and `REVIEW_MISMATCH` when the displayed fee lies) |
| reserve overdraw beyond the agent's fee cap | `RESERVE_RULE_VIOLATION` |
| wrong successor value (covenant keeps less/more than derived) | `WRONG_SUCCESSOR` |
| smuggled nonce advance / smuggled agent-root change in a value op | `REVIEW_MISMATCH` |
| wrong network | `NETWORK_MISMATCH` / `REVIEW_MISMATCH` |
| wrong vault / foreign predecessor outpoint | `PREDECESSOR_MISMATCH` (tx level), `REVIEW_MISMATCH` (claim level) |
| stale client state / foreign predecessor stateId | `REVIEW_MISMATCH` |
| requested action ≠ serialized transaction | `WRONG_SUCCESSOR` + `EXCESSIVE_FEE` (+ `TX_MISMATCH`/`REQUEST_MISMATCH` family inside the core catalogue) |
| txId claim missing or malformed (the claim is REQUIRED — F2-1) | `SERVER_CLAIM_INVALID` |
| recipient outside the displayed allowlist | `ALLOWLIST_NOT_PROVEN` |
| lockTime not a whole-period rollover | `LOCKTIME_RULE_VIOLATION` |
| pre-signed / smuggled-field / non-zero-mass payloads | `SAFE_JSON_INVALID` |
| genesis deposit mismatch, underfunded genesis vault, genesis siphon | `REVIEW_MISMATCH` / `WRONG_SUCCESSOR` / `VALUE_CONSERVATION_VIOLATION` |
| genesis owner or initial-agent substitution | `REVIEW_MISMATCH` |
| signer-identity confusion (wallet ≠ acting agent / owner / approver-set member) | `REVIEW_MISMATCH` / `IDENTITY_UNRESOLVED` |
| client-selected fuel substituted | `REVIEW_MISMATCH` |
| environment failures (no core bundle, no vault knowledge, unresolved identity, unknown action, internal error) | `CORE_UNAVAILABLE` / `VAULT_KNOWLEDGE_MISSING` / `IDENTITY_UNRESOLVED` / `UNKNOWN_ACTION` / `BROWSER_VERIFIER_INTERNAL` — an error is never a pass |
| **F2 wave — fee/budget/state recomputation classes:** | |
| genesis fee off by ±1 sompi (no fee claim exists in a genesis review — only the recomputation binds it) | `FEE_MISMATCH` |
| transition fee below the recomputed unsigned-shape floor, with a FULLY consistent hostile document (fee claim + successor state id all rewritten to match) | `FEE_RULE_VIOLATION` |
| transition fee moved without updating the claim (±1 sompi) | `REVIEW_MISMATCH` |
| fee between the structural cap and the old 1-KAS ceiling (0.8 KAS, honest review — previously passable) | `EXCESSIVE_FEE` (cap tightened to the recomputed structural maximum) |
| committed compute budget under/over the canonical tier, wrong approval-class tier, non-tier fuel input, or a lying review budget | `COMPUTE_BUDGET_MISMATCH` / `REVIEW_MISMATCH` |
| ROOT-CONSISTENT over-budget spend (registry + ids all internally consistent; the arithmetic itself violates `newSpent <= periodBudget`) | `TRANSITION_RULE_VIOLATION` (canonical `vault-transitions-v4`) |
| spend against a paused vault; pause of an already-paused vault | `TRANSITION_RULE_VIOLATION` |
| successor state id flipped by one hex digit (claims fully consistent) | `STATE_ID_MISMATCH` |
| vault view state id not the commitment of the displayed state | `STATE_ID_MISMATCH` |
| genesis under an unknown covenant version | `UNSUPPORTED_COVENANT_VERSION` |
| missing `successorStateId`; stale bundle without the fee/state modules | `SERVER_CLAIM_INVALID` / `CORE_UNAVAILABLE` |
| outputs reordered against the builder's pinned shape | `ACTION_TX_SHAPE_MISMATCH` |
| zero-approver `ownerSetApprovers` target (genesis-only tier) | `TRANSITION_RULE_VIOLATION` / `STATE_RECOMPUTE_FAILED` |
| **Residuals wave — genesis registry-disclosure classes:** | |
| genesis document without / with empty / with malformed `initialRegistry` tuples (REQUIRED for v4 documents) | `SERVER_CLAIM_INVALID` |
| tampered genesis tuple; EXTRA (hidden) agent tuple (root left as served) | `AGENT_REGISTRY_ROOT_MISMATCH` |
| duplicate genesis agentPk tuples (independent budget lanes) | `MERKLE_RECOMPUTE_FAILED` |
| genesis tuple whose disclosed recipients do not hash to its own allowlist root | `ALLOWLIST_ROOT_MISMATCH` |
| FULLY CONSISTENT genesis substitution (tuple + allowlist root + agentRoot all rewritten to agree): per-spend cap, or recipient allowlist, differing from what the user typed | `REVIEW_MISMATCH` (typed-context pins) |
| reordered genesis tuples (same set) | PASS-pair — canonical set, identical manifestHash |

Resumed flows (approver review, agent-sign-after-approvals): the
original requester's typed intent is not available to this browser, so
the intent is reconstructed from the DURABLE server request and the
verification statement is honestly weaker: *the transaction does
exactly what the displayed request claims and nothing else, against
this browser's own vault knowledge*. The outcome's notes state this
provenance, and it is rendered in the details disclosure.

## 5. Residual-trust table (what browser v1 canNOT independently verify)

| # | Residual trust | Why | Strongest check applied instead |
|---|---|---|---|
| 1 | **The served client code itself.** A hosted server that serves the JS can serve JS without/with a defanged verifier. | Client-side verification cannot authenticate the client. | The verification layer, once loaded, cannot be bypassed; the degraded state is visibly labeled. True independence requires an out-of-band client (the CLI signer path / a pinned local build) — that is exactly why the shared core is portable. |
| 2 | **Chain-state freshness/authenticity** (`stateBefore`, live outpoint, covenantId, agent registry, DAA-based data). | The browser has no Kaspa node; vault views are server-served chain reads. | Everything is bound to ONE consistent snapshot the user is looking at; any divergence between payload, request, review, and the client's view refuses. **F2 narrows this residual to freshness only:** the view's CONTENT is now internally proven — the displayed registry must hash to the committed `agentRoot` (F1) and the displayed state tuple must hash to the view's `stateId` (F2) — so only "is this the LIVE state" remains trusted. The Kaspa covenant remains the hard boundary: a stale/false state produces a transaction consensus will reject, not a spendable theft. |
| 3 | **Consensus hashing** (`txId`, sighash). | Standing project rule: consensus hashing is never reimplemented in JS. | **CORRECTED (F2-1,** `docs/postlaunch/f2-fee-state-recomputation.md`): the id kaspa-wasm embeds in the UNSIGNED Safe JSON payload is NOT the consensus txId (the real id exists only after `finalize()`; the server serializes the wallet payload pre-finalize — proven by direct experiment, and the original embedded-id equality check here refused EVERY honest real document). Missing/malformed tuples on a v4 genesis document refuse (`SERVER_CLAIM_INVALID`) — compatible with all recorded documents (documented compat rule: the field has always been stored, and genesis verification only runs on fresh session-local documents). | Remaining nuance (not a root residual): `periodStartDaa` (node DAA) and the human-period→DAA normalization are server-derived values INSIDE the hashed tuples — disclosed, hashed, and shown under review.technical, but not recomputable from typed form input. Tuple ORDER is canonicalized by the tree builder (the committed set is order-free; duplicates refuse). | Any tuple/root mismatch refuses (`AGENT_REGISTRY_ROOT_MISMATCH` / `ALLOWLIST_ROOT_MISMATCH` / `MERKLE_RECOMPUTE_FAILED`); a fully self-consistent hostile substitution is caught by the typed-context pins (`REVIEW_MISMATCH`). What the actual genesis SCRIPT bytes encode remains row 8 (script contents), as for every other state component. |
| 5 | ~~State ids~~ **CLOSED (F2 wave; genesis nuance closed by the residuals wave).** Predecessor, successor, AND genesis state ids are INDEPENDENTLY RECOMPUTED via the canonical `computeStateIdV4` formula (the same bundled module the SDK computes them with): the vault view's `stateId` must equal the commitment of the displayed state, the request's `successorStateId` must equal the commitment of the client-derived successor, and the genesis manifest carries the real formula value whose `agentRoot` input is now ITSELF recomputed (row 4) — no component of the genesis id is a bare claim any more. | — | Any state-id mismatch refuses (`STATE_ID_MISMATCH`); the successor state itself is derived through the canonical `vault-transitions-v4` builders. |
| 5b | **Covenant-input final signature-script bytes** (compiled covenant script + call encoding) — the ONE undisclosed length in the fee equation. | Reproducing it client-side would reimplement the covenant compiler/call encoder (the exact consensus re-implementation this design forbids — see row 8), and the hosted request does not disclose the byte length. | The network fee is INDEPENDENTLY BOUNDED instead of exactly recomputed for covenant transitions: actual fee (inputs − outputs, always derived from the payload) >= the recomputed unsigned-shape floor (committed budgets + serialized size through the canonical fee/mass rules), and <= the recomputed structural cap (`STANDARD_MASS_CAP` ⇒ 0.5 KAS — no standard transaction can REQUIRE more; PolicyVault builders never overpay). All-ordinary-input shapes (genesis) have NO undisclosed length: their fee is recomputed EXACTLY and equality-enforced. Compute budgets are exactly pinned in all shapes. |
| 6 | **Address → x-only resolution.** | The single address-identity boundary is server-side (rusty-kaspa parser); the browser performs no address decoding by design. | The resolved keys are echoed into the P2PK scripts of the actual outputs, which the browser byte-checks; the wallet displays addresses independently. |
| 7 | **Input UTXO amounts** embedded in the Safe JSON (fuel value, covenant input value). | UTXO truth lives in the node's UTXO set. | The covenant input's value must equal the client-known protected+reserve; the fuel input must be the exact UTXO the client itself selected (outpoint + amount); consensus rejects fabricated UTXO values at broadcast. |
| 8 | **Successor script contents** (the state encoded in the covenant script bytes). | Decoding compiled covenant scripts client-side would be a consensus re-implementation. | Value-level checks (successor output value = derived protected+reserve) plus the covenant itself: the predecessor script enforces the successor's state encoding on-chain. |
| 9 | **KasWare itself** (the extension displays and signs). | The signer is the user's trust anchor, outside PolicyVault by design. | The interface transports frozen bytes verbatim; pre/post identity and live-network gates; Schnorr forced explicitly; PolicyVault is not a wallet and holds no keys. |

## 6. KasWare behind the Universal Signer Interface (item 4, browser side)

`web/signer-kasware-adapter.js` is now the ONLY place
`window.kasware` appears in the production flows:

- `createKasWareUsiAdapter` — the core/signer interface-v1 adapter
  (descriptor exactly as mapped in
  `docs/postlaunch/signer-kasware-mapping.md` §1; schnorr-only,
  mainnet/testnet-10, specific-input signing, account events;
  registered/validated via `validateAdapter`).
- `createKasWareSessionAdapter` — the drop-in session surface consumed
  by `web/app.js`/`web/app-v4.js`, which routes **every** signature
  through `executeSigning` + the frozen request creators
  (`createMessageSigningRequest` / `createTransactionSigningRequest`),
  adding the interface's fail-closed gates (capability, scheme, LIVE
  network, pre+post identity) on top of the unchanged app-level checks.
  UI-only KasWare conveniences stay direct but isolated in the adapter
  file: silent `reconnect` resume, the raw compressed pubkey for hosted
  auth verify, origin-scoped disconnect, and the public-key
  normalization diagnostic log.
- `web/app.js` instantiates KasWare via the session adapter when the
  module is loaded (legacy `web/wallet.js` `KasWareAdapter` remains the
  fallback and the byte-behavior reference — it is still covered by
  `sdk/test/wallet-adapter.test.js` and was not modified);
  `hostedSignIn` passes the expected signer + network so the
  interface's gates bind to the attempt; `walletSign` passes the
  session network + expected signer for the transaction request.

Preserved bit-for-bit (proven by `web/test/signer-kasware-adapter.test.js`
byte-comparing provider invocations against the legacy adapter over the
same mocked `window.kasware`): the exact challenge string and
`{ type: "schnorr" }` to `signMessage`; the exact frozen
`txJsonString` + canonical `{ index, sighashType: 1 }` entries to
`signPskt`; the 128-hex lowercased signature result; connect/reconnect/
disconnect (incl. origin) semantics; 02/03-compressed → x-only
normalization with 04 refused; provider-label network normalization;
account/network event propagation; USER_REJECTED classification on
4001//reject|denied/i. Errors carry `signerCode` (v1 taxonomy) AND the
legacy `walletCategory` (1:1 where one exists) AND `code`, so existing
handlers keep working while gaining specificity. One deliberate,
taxonomy-true refinement: a malformed provider signature now surfaces
`INVALID_SIGNATURE_RESPONSE` where the legacy message path said
`PROVIDER_ERROR`.

Wrong-network and identity re-check semantics are enforced TWICE: the
existing app-level session gates (unchanged) and the interface's live
`getNetwork()` + pre/post `getActiveAccount()` gates
(`WRONG_NETWORK` / `ACCOUNT_CHANGED`, signature discarded) — proven by
the wrong-network-no-provider-call and mid-popup-account-switch tests.
