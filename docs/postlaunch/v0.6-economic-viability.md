# v0.6 atomic swap — ECONOMIC VIABILITY (owner addendum 2026-09-03 §A)

Consensus validity and standardness are necessary, not sufficient. This
record computes the candidate swap's expected KAS network fee under
CURRENT mainnet fee policy (rusty-kaspa v2.0.1, post-Toccata) and reports
fee-as-percentage of swap value for representative principals. No economic
threshold is invented; the curve is presented and the ranges where the fee
is a material fraction of swap value are identified. Tool:
`tools/v6-fee-curve.js` (deterministic; `--json` for the raw rows).

## Findings

1. **Network fee is a material fraction of swap value below roughly 10 KAS**
   (≥ 0.8 %), dominant below ~2 KAS (≥ 4 %), and negligible (≤ 0.16 %)
   from ~50 KAS upward at the relay floor. Any fee-market multiplier moves
   these boundaries proportionally.
2. **KIP-9 storage mass is a VALIDITY boundary, not a fee:** with a
   bps-sized protocol-fee output, swaps below ~50 KAS produce a dust output
   (`C/out > 500,000` at < 0.02 KAS) and the transaction is INVALID
   (block-fit limit), independent of the fee paid. The builder-side remedy
   is to over-pay the venue's protocol fee up to the owner's
   `maxProtocolFeeKas` so the output is ≥ ~0.025 KAS; that padding is a real
   cost (10.5 % at 1 KAS, 1.9 % at 5 KAS, 0.9 % at 10 KAS). The same
   constraint applies to the token-note carries (sized at 0.2 KAS here, a
   one-time backing that persists across swaps, not a per-swap cost).
3. **Classification:** a consensus-valid, standard, relayable swap of the
   candidate design is **ECONOMICALLY NOT VIABLE below ~10 KAS** at the
   relay floor (≥ 0.87 % effective cost, rising steeply), **marginal at
   10–50 KAS** (0.16–0.87 %), and **viable from ~50 KAS** (≤ 0.16 %) for a
   venue whose protocol fee is bps-sized. Owner policy (`maxProtocolFeeKas`,
   `kasMaxPerSwap`, floor/ceiling) can express a minimum economic swap
   size; the core's explanation MUST surface fee-as-percentage before
   signing.
4. **Where the bytes go:** controller redeem 24,920 B (≈ 61 % of a swap
   transaction), pool fixture 10,566 B, two KCC20 notes 2 × 2,733 B, call
   arguments ≈ 1.6 KB. A smaller controller (single swap entrypoint with a
   direction argument, ≈ −6 KB) or a smaller venue program would cut the
   floor fee roughly proportionally; neither changes the storage-mass
   boundary.


## Correction (2026-09-03, Wave 2): KIP-9 storage mass and UTXO plurality

Every storage-mass figure in this record was computed with the plurality-1
model (`core/model/storage-mass.js` before commit 6b9da7e). rusty-kaspa
v2.0.1 weighs each UTXO by its storage plurality p = ceil((63 + script
length + 32 if it carries a covenant id) / 100), contributing C·p²/amount —
a covenant-bearing P2SH output has p = 2 and therefore weighs FOUR times the
plain-output estimate used here. Consequences: (1) the dust / minimum-output
thresholds stated for covenant outputs (token notes, protocol-fee outputs,
covenant successors) are understated by up to 4×; the exact numbers are now
produced by the corrected module and enforced pre-sign by the builders'
storage-mass preflight; (2) no live evidence is invalidated (every accepted
transaction was accepted by the node under the correct rule); (3) the
frozen covenant bytes are unaffected (storage mass is not a covenant rule).
Found live on 2026-09-03 when an HD level-1 spend with a 0.05 KAS covenant
carry was refused at 840,919 grams (pinned as an exact regression vector in
`core/model/test/storage-mass-plurality.test.js`).
