## 3. Independent adversarial review

**Verdict: FREEZE-NOT-FALSIFIED.** An internal independent agent review (a
separate agent session with no authorship stake in the candidate) attempted to falsify the freeze with **20 new real-engine
probes** in 8 tests (`tests/vm/tests/v7_adversarial_review_freeze.rs`, kept
permanently; reviewer run 8/8 in 27.84 s; coordinator re-run 8/8 in 26.45 s).
**No probe produced an accepted transaction in which a legitimate delegate, a
sub-quorum owner subset, the emergency quorum, or an outsider exceeds the
authority the design assigns them, moves protected value, redirects recovery,
or mutates state without the stated quorum.** Refuted on the real engine:
succession/recovery installing sets with holes or duplicate keys; succession
against a malformed predecessor; a duplicate key straddling the two counting
frames; succession draining the root beyond `rootMaxFeePerTx`; ROTATE to
`emergencyK = 0` / `recoveryM = −1` (lower bounds); 64- and 66-byte succession
signature blobs; rooted-vault genesis pinned with prefix/state/suffix lengths
off by one; a REAL frozen v0.5 controller impersonating the pinned root
(clean `InvalidIndex` refusal, no panic). Accepted as designed: OWNER-RECOVER
while already frozen (informational), zero-value-loss AUTHORIZE, an extra real
signature in an inactive slot (ignored).

**D1 proven load-bearing (evidence FOR the freeze):** a measurement-only
variant with D1 removed (`contracts/experiments/V7ReviewNoD1.sil`, never an
acceptance candidate) accepts a trivial succession signed by nothing but the
successor key, producing a state byte-identical to a FREEZE result that a
real, unmodified rooted vault then accepts as authorization for an emergency
pause; the identical shape against the FROZEN candidate is refused at the
root (D1 fires). D1 is present in the frozen bytes and closes exactly the gap
it exists to close.

**Findings:** FUNDS-CRITICAL none · AUTHORITY-CRITICAL none against the
candidate (every guard held) · DEFENSE-IN-DEPTH: redundant blob-length checks
and the inactive-slot sentinel skip confirmed worth keeping · **DOCUMENTATION
(corrected in this record and by dated addenda to the design/readiness
records): multi-vault batching under one root transition is REFUSED by the
covenant, not "architecturally permitted"** — `requireOnlyRootCovenantInputs`
in the rooted payment covenant requires every input other than the vault
itself and the pinned root family to carry a ZERO covenant id, so a sibling
rooted vault in the same transaction is a foreign rider and each vault refuses
the transaction (probe 20; coordinator verified in source). Direction is safe
(more restrictive than documented; fails closed). Consequence for the
application surface: exactly ONE vault operation per root transition
(`docs/postlaunch/v0.7-app-surface-contract.md` updated). Not probed (with
reasons recorded in the review): argument aliasing at the counting call site
(no runtime-indexed offsets exist), the v0.6 impostor direction (same P2SH/
geometry defense as the v0.5 impostor probe), recovery-destination type
confusion (needs KCC20 token-pin machinery), hostile stack padding (honest
worst-case headroom already measured), live negative validation (closed I5
evidence).

## 4. Limitations (prominent, carried from the readiness record with the review correction)

1.; no mainnet organization exists; NOT deployed.
2. ONE rooted profile is frozen (the v0.5-derived token payment profile). The rooted KAS (v0.4.1) profile and the hierarchical-delegation profile are being built in this wave as NEW additive candidates on the same root mechanism; they are NOT frozen by this record.
3. The root UTXO serializes OWNER operations (one owner-op transaction per root transition); delegate spends are unaffected. **Multi-vault batching in one transaction is REFUSED by each rooted vault's own input-closure rule (review probe 20) — one vault operation per root transition.** A future additive profile could permit siblings that share the same pinned root id; the frozen bytes do not.
4. Root template = 12 owner slots; larger sets are a different template/version.
5. `successorPk`, `recoveryDelayDaa`, `successionDelayDaa`, `rootMaxFeePerTx` are template constants (changing them = root migration); `recoveryM` is state.
6. Relative-age semantics are DAA-score based; owners keep recovery closed by heartbeating (AUTHORIZE) within the delay — an operational discipline the application must surface.
7. The org-root manifest's slot-key binding at the portable-core boundary is a claim check plus an optional injected verifier; the cryptographic slot↔key binding is the covenant's own `checkSig` (consensus).
8. The live proof used a 2-of-3 / 3-of-3 root with K=1, R=1, 600-DAA delays; owner sets above 3 active slots and ROTATE-while-frozen are engine-proven only.
9. Economic: an owner operation costs ≈ 0.046 KAS and a delegate spend +3.0 % vs v0.5 at the relay floor; no fee-market modelling beyond the floor.
10. **Internal review only.** Internal reread + independent internal agent review (never described as an audit).
