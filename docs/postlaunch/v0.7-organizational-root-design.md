## 1. Architecture comparison (deliberate, as directed)

### A. Organization-root successor of the restrictive v0.5 safe-payment profile (owner slots EMBEDDED in the vault)

Replace `pubkey owner` in the v0.5 token controller with N owner slots + `ownerM` in the vault STATE, count M-of-N signatures inside `ownerControl`/`ownerRecover`.

- Sig-op budget: the v0.5 redeem has 3 static sig-ops (agent, ownerControl, ownerRecover). Counting inlines at each call site, so the two owner entrypoints must be MERGED into one (recover as a selector) to count once: N + 1 ≤ 15 → N ≤ 14 in the v0.5 profile; in the v0.6 profile (agent auth in spend/sell/buy = 3) N ≤ 12.
- Every DELEGATE spend reveals the whole redeem script: the owner-counting code (~N×65-byte slot extraction + checkSig + C(N,2) distinctness at rotation) inflates every ordinary agent transaction's transient mass, forever, for a code path that transaction never takes.
- Rotation is PER VAULT: an organization with V vaults performs V rotations to change one signer; the sets drift; a stale set on one vault is exactly the failure an organizational root exists to prevent.
- Recovery/succession keys and delays would also be per vault.

### B. Organization-root successor of v0.6 composability (same embedding, larger redeem)

Same properties as A with the 24.9 KB v0.6 redeem: N ≤ 12, and every swap (already fee-material at ~0.08 KAS) carries the owner machinery in its transient mass. Composability attack surface would be forced into every organizational vault even where a safe-payment profile is wanted — explicitly discouraged by the directive.

### C. Shared reusable ORGANIZATIONAL ROOT covenant + profile-specific rooted successors (SELECTED)

One `PolicyVaultOrgRoot` covenant per organization holds the owner set, threshold, freeze flag, recovery quorum and nonce. A rooted vault (v0.5-profile "payment" first; v0.4.1-KAS and v0.6-composability profiles later, same mechanism) pins the root's covenant id and template identity as template constants, has NO owner key and NO owner signature check: an owner-authorized vault operation is valid only if the transaction also spends the organization's root covenant, whose own script proved M-of-N (or the lighter emergency quorum), and the vault pins the root's exact successor shape so the vault can tell WHICH root path ran.

- Sig-op budget: root = N owner checks + 1 successor-key check ≤ 15 → N ≤ 14; we pin **N_MAX = 12** (13 static sig-ops, headroom 2). Rooted vaults DROP two sig-ops (v0.5 profile: 3 → 1).
- Delegate spends are untouched: no root input, no owner code in the vault redeem beyond the small root-introspection block; measured in §7.
- Rotation, threshold change, freeze, recovery, succession happen ONCE for all vaults.
- The root UTXO is a serialization point for OWNER operations only (one owner-operation transaction per root transition); delegate spends never touch it. That serialization is desirable: it makes every quorum approval outpoint-bound (stale-quorum kill switch, exactly the v0.6 freshness model).
- Failure isolation: a compromised or lost root does not affect delegate spending; a vault's `paused` flag remains per vault.

Least-authority: C is the smallest architecture that provides organizational ownership for EVERY profile without forcing swap surface into payment vaults and without duplicating M-of-N consensus logic per profile. It reuses, conceptually and mechanically, the PROVEN v0.4.1 approval-counting pattern (65-byte SIGHASH_ALL-gated slots, sentinel-zero inactive slots, pairwise distinctness, single counting frame) at a distinct authority tier with its own threat model. **Selected: C.** A and B are measured by a throw-away probe for the record only (§7).

## 2. The root covenant `PolicyVaultOrgRoot` (v0.7-root)

### 2.1 Template constants (immutable per root instance; changing any = root migration)

```
byte[32] orgId                       // application identity (informational; the covenant id is the authority identity)
pubkey   initOwner1 … initOwner12    // zero = inactive slot; active slots contiguous from 1
int      initOwnerM                  // 1 ≤ M ≤ activeCount
int      initEmergencyK              // 1 ≤ K ≤ M   (lighter quorum: FREEZE only)
int      initRecoveryM               // 0 ≤ R ≤ M   (0 = owner-recovery path DISABLED)
int      recoveryDelayDaa            // ≥ 1; relative idle age before owner-recovery
pubkey   successorPk                 // zero = succession path DISABLED
int      successionDelayDaa          // ≥ 1; relative idle age before succession
int      rootMaxFeePerTx             // the ONLY value the root may lose per transition
```

### 2.2 State (all fields preserved unless a rule below moves them)

```
byte[32] boundOrgId; pubkey owner1..owner12; int ownerM; int emergencyK; int recoveryM; int frozen; int rootNonce;
```

Well-formedness `WF(S)`: `ownerM ≥ 1`; `ownerM ≤ active(S)`; active slots contiguous from slot 1 (no active slot after an inactive one); all active keys pairwise distinct (66 byte-inequality checks); `1 ≤ emergencyK ≤ ownerM`; `0 ≤ recoveryM ≤ ownerM`; `frozen ∈ {0,1}`.

### 2.3 Signature blob and counting (ONE call site)

`ownerSigs` is exactly 12 × 65 = 780 bytes. Slot i (0-based) = bytes `[65i, 65i+65)`. For an ACTIVE slot: the 65th byte MUST be `0x01` (SIGHASH_ALL gate, A7) and the slot counts 1 iff `checkSig(sig(slot), owner_i)`; the canonical placeholder (65 zero bytes with trailing 0x01) fails verification and counts 0. Inactive slots never count and are not inspected. `count = Σ_i count_i`.

Why duplicates cannot be counted twice: every active key is distinct (WF on prev AND on every new set), each slot is verified against exactly one key, and one signature verifies under exactly one key. Why a stale approval cannot replay: every counted signature is SIGHASH_ALL over the whole transaction, which commits to the root's outpoint (single-use by consensus) and to every output including the root's successor state (`rootNonce` strictly increases).

### 2.4 Entrypoints

`rootAction(State prev, State new, int action, byte[] ownerSigs)` — `#[covenant.singleton]`, one continuation output of the root family, exact-successor rules:

- common: `WF(prev)`; `ownerSigs.length == 780`; `new.boundOrgId == prev.boundOrgId`; `new.rootNonce == prev.rootNonce + 1`; `tx.outputs[successor].value >= tx.inputs[this].value − rootMaxFeePerTx`; `action ∈ [0,4]`.
- **0 AUTHORIZE** (full quorum `count ≥ prev.ownerM`): `prev.frozen == 0`; `new == prev` except `rootNonce`. This is the ONLY root shape a rooted vault accepts for general owner operations (§3).
- **1 ROTATE** (full quorum): `new.owner*`, `new.ownerM`, `new.emergencyK`, `new.recoveryM` as supplied; `WF(new)`; `new.frozen == prev.frozen`. Allowed while frozen (rotate compromised keys before unfreezing). Class: AUTHORITY-EXPANDING (a key gains authority) — full quorum always.
- **2 FREEZE** (lighter quorum `count ≥ prev.emergencyK`): `prev.frozen == 0`; `new == prev` except `frozen = 1`, `rootNonce`. Class: AUTHORITY-REDUCING. Monotonicity proof: the only effect is `frozen 0→1`; while frozen, actions 0 and 2 are refused and every rooted vault's general owner path is refused (§3); nothing on this path can ever produce a spend, a set change, a threshold change or an unfreeze; composing it with any other path is impossible in one transaction (the root has one input and one action), and the next transaction must satisfy the full-quorum rules. Hence FREEZE cannot become an authority expansion by composition.
- **3 UNFREEZE** (full quorum): `prev.frozen == 1`; `new == prev` except `frozen = 0`, `rootNonce`. Class: AUTHORITY-EXPANDING.
- **4 OWNER-RECOVER** (recovery quorum `prev.recoveryM ≥ 1 && count ≥ prev.recoveryM`; `this.age ≥ recoveryDelayDaa`): same effect and `WF(new)` rule as ROTATE. Class: AUTHORITY-EXPANDING, gated by idle delay + explicit opt-in (`recoveryM > 0`). Threat model: a recovery-quorum subset can take over only if the full owner set stops touching the root for `recoveryDelayDaa`; the app's heartbeat is an AUTHORIZE transaction (action 0) — cheap, and it also refreshes the freshness of every stale approval.

`rootSuccession(State prev, State new, sig successorSig)` — `#[covenant.singleton]`: `bytes(successorPk) != zero`; `checkSig(successorSig, successorPk)` (65-byte SIGHASH_ALL gate as well); `this.age ≥ successionDelayDaa`; `WF(prev)`; `WF(new)`; `new.boundOrgId == prev.boundOrgId`; `new.rootNonce == prev.rootNonce + 1`; `new.frozen == 1` (the installed set must deliberately unfreeze — one extra full-quorum step that also surfaces the succession in every vault's manifest); value rule as above. Class: TERMINAL for the old set, AUTHORITY-EXPANDING for the successor; gated by idle delay + explicit opt-in (`successorPk ≠ 0`).

Static sig-ops: 12 (counting) + 1 (succession) = **13 ≤ 15**.

### 2.5 Explicit terminality rules

The root has NO terminal transition: it cannot be dissolved, and it cannot spend to a non-successor output. Rationale: a terminated root would permanently strand the owner path of every vault pinned to it (a self-locking transition). Organizational wind-down = recover every vault (each vault's own terminal path, §3), after which the root's dust simply remains. Root MIGRATION (to a future root version) = new root genesis + per-vault migration authorized by the OLD root; the old root persists (harmless).

### 2.6 Deterministic recovery behaviour

If keys are lost below `ownerM`: (a) `recoveryM > 0` → after `recoveryDelayDaa` idle, `recoveryM` surviving owners install a new set; (b) `successorPk ≠ 0` → after `successionDelayDaa` idle, the successor key installs a new (frozen) set; (c) neither → the root is permanently stuck: every vault's DELEGATE policy continues to function within its caps until exhausted; vault recovery is impossible. (c) is the deliberate, documented consequence of choosing no recovery — identical in kind to losing today's single owner key, and the app must warn at genesis.

## 3. Rooted vault profile `PolicyVaultRootedToken` (v0.7-payment, derived from frozen v0.5)

Delta from `contracts/PolicyVault.v0.5.sil` (generator-derived; every v0.5 protection retained: dual binding A/B, transaction-derived template carriage, token-denominated agent leaves, exact conservation, fee-reserve domain, break-glass recovery):

- Template constants: REMOVE `pubkey owner`; ADD `byte[32] orgRootCovenantId`, `byte[32] rootTemplateVmHash`, `int rootPrefixLen`, `int rootStateLen`, `int rootSuffixLen`, `pubkey recoveryPk` (the organization's cold recovery destination; recover pays feeReserve and the whole token position to `P2PK(recoveryPk)` / owner-identifier `recoveryPk` — pinned at genesis so a hijacked quorum-signing session cannot redirect recovery; changing it = vault migration).
- `requireRootAuthorization(int expectFrozenAfter)` (called ONCE per owner entrypoint):
  1. `OpCovInputCount(orgRootCovenantId) == 1`, `OpCovOutputCount(orgRootCovenantId) == 1`, `rootIn = OpCovInputIdx(orgRootCovenantId, 0)`;
  2. `RootState prevRoot = readInputStateWithTemplate(rootIn, rootPrefixLen, rootSuffixLen, rootTemplateVmHash)`; slice prefix/suffix from the root input's signature script exactly as v0.5 does for the token input (verified carriage);
  3. `prevRoot.frozen == 0`;
  4. `validateOutputStateWithTemplate(OpCovOutputIdx(orgRootCovenantId,0), { …prevRoot, frozen: expectFrozenAfter, rootNonce: prevRoot.rootNonce + 1 }, prefix, suffix, rootTemplateVmHash)` — the root's successor is pinned to exactly AUTHORIZE (expectFrozenAfter = 0) or FREEZE (= 1); any other root path (rotation, unfreeze, recovery, succession) in the same transaction makes the vault operation invalid. Rotation and vault operations are therefore separate transactions by construction.
  5. `requireNoForeignCovenantInputs` is generalised to permit exactly the pinned token family (where the path allows it) and the pinned root family — nothing else.
- `ownerControl(prev, new, opSelector)` (selectors 0..3 as v0.5): `requireRootAuthorization(0)` replaces `checkSig(ownerSig, owner)`; no owner signature argument exists.
- `emergencyPause(prev, new)`: `requireRootAuthorization(1)`; `prev.paused == 0 → new.paused == 1`; everything else preserved; `policyNonce` unchanged. AUTHORITY-REDUCING; the ONLY vault effect reachable from the root's lighter quorum.
- `ownerRecover(prev, nextStates, recipientNew)`: `requireRootAuthorization(0)`; pays `feeReserve` to `P2PK(recoveryPk)` at output 0 and the token position to owner-identifier `recoveryPk` (p2pk scheme) — otherwise the frozen v0.5 rules verbatim. TERMINAL.
- `tokenAgentSpend`: byte-for-byte the v0.5 logic (the agent path never sees the root).

Static sig-ops in the rooted vault: **1** (agent).

Mutation classes for the rooted vault (recorded for governance/manifests): setAgentRoot = EXPANDING unless the new tree is a proven subset (governance classifier decides; consensus requires full quorum either way in v0.7); topUpReserve = NEUTRAL; pause = REDUCING; unpause = EXPANDING; recover = TERMINAL. v0.7 applies the full-quorum rule to every class except pause-via-FREEZE; the lighter rule is used ONLY where §2.4 proves monotonicity.

### 7.9 Deviations from the specification

**D1 — `rootSuccession` must install a different primary key (RULE ADDED).** §2.4 does not require a succession to change the owner set. Without that requirement, a succession that re-installs the SAME set produces a successor state **byte-identical** to the one a FREEZE produces (`frozen = 1`, everything else preserved, nonce + 1), so the rooted vault's `emergencyPause` pin — which §3 claims excludes succession — could be satisfied by a succession transaction. `V7OrgRootProbe.sil` therefore adds `require(bytes(newState.owner1) != bytes(prevState.owner1));`. It costs a legitimate successor nothing (it installs its own key) and makes every root path's successor shape distinguishable. Probed both ways: the honest succession accepts, the same-primary-key succession is REFUSED, and "root running SUCCESSION under `emergencyPause`" is REFUSED. **The general-owner path (`requireRootAuthorization(0)`) was never reachable by succession** even without D1, because succession requires `newState.frozen == 1`.

**D2 — F1 hardening `require(periodLengthDaa > 0)` (RULE ADDED, coordinator addendum from the v0.6 adversarial review).** A zero-length period makes the period budget vacuous: with `periodLengthDaa == 0` and `periodsElapsed >= 1` the rollover branch computes `newStart == periodStartDaa`, so `tx.time >= newStart` holds inside the SAME period and `periodSpent` resets to the current spend — the agent can drain the position one cap-sized spend at a time without the period ever ending. The check was added at the top of `requireTokenAgentTransition` in `V7RootedTokenControllerProbe.sil`. Probed: the rooted v0.7 vault REFUSES the degenerate leaf; the FROZEN v0.5 controller ACCEPTS it. That acceptance is **documented inherited behaviour** (the leaf is owner-committed, so it is an owner-misconfiguration hazard rather than a delegate escalation) and the frozen v0.3–v0.6 files were NOT modified.

**D3 — the architecture-A probe omits break-glass recovery (SCOPE).** §1.A requires the owner entrypoints to be merged so the 12 counting sig-ops appear once; folding a termination-mode recovery into that merged entrypoint is a non-trivial ABI exercise that the measurement does not need. The omission **understates** architecture A, i.e. it biases the comparison in A's favour, and it is quantified in §7.5 (+2,106 B).

**D4 — observation, not a deviation.** ROTATE with an unchanged owner set produces the same successor shape as AUTHORIZE. There is no authority difference (both require the full quorum) and no vault consequence (the vault independently requires `prevRoot.frozen == 0`, which is exactly what separates the two while frozen). Recorded so a future reviewer does not mistake it for a finding.

**D5 — harness technique.** The root probe exposes `initFrozen` / `initRootNonce` as constructor parameters for exact-live-state compilation; the v0.5-derived probes use the same source-templating anchors the v0.5 production suite uses. Neither changes consensus-visible structure: both produce the identical fixed-width state region.

## 9. Probe phase 2 — BYTE-LEVEL ROOT-SUCCESSOR PINNING (coordinator decision, 2026-09-03)

§7.5 falsified the delegate-cost claim because the vault decoded and re-encoded the
root's 18-field state at every inlined owner entrypoint. The security properties
are untouched by the fix chosen here; the fix changes HOW the vault pins the root
successor, not WHAT it pins. The owner set stays as in-state slots in the root
(covenant-level duplicate prevention and threshold well-formedness are kept — a
Merkle-set root would move "duplicate owner keys impossible" to the SDK, which
the directive forbids).

### 9.1 Root state layout change (root covenant)

- Field ORDER: `boundOrgId`, `owner1..owner12`, `ownerM`, `emergencyK`, `recoveryM`
  stay first ("HEAD"); the two fields that change on AUTHORIZE/FREEZE come LAST as
  FIXED-WIDTH bytes ("TAIL"): `byte frozen` (0x00/0x01) and `byte[8] rootNonce`
  (unsigned little-endian; the root increments it as
  `bytes(OpNum2Bin(int(prev.rootNonce) + 1, 8))`).
- If small ints (`ownerM`/`emergencyK`/`recoveryM`, all ≤ 12) do not encode at a
  constant width in the state region, type them `byte` too. Goal: the state
  region length is a CONSTANT (`rootStateLen`, expected 33 + 12·33 + 3 + 2 + 9 =
  443 B, to be measured), so a rooted vault can slice HEAD and TAIL by offsets.
- Everything else in §2 is unchanged (single counting site, WF(prev)/WF(new),
  actions 0–4, succession incl. D1, value rule, 13 static sig-ops).

### 9.2 Rooted vault: `requireRootAuthorization(int expectFrozenAfter)` rewritten

Inputs pinned at genesis: `orgRootCovenantId`, `rootTemplateVmHash`,
`rootPrefixLen`, `rootStateLen`, `rootSuffixLen`. Steps (no `readInputStateWithTemplate`,
no `validateOutputStateWithTemplate`, no decoding of owner slots):

1. `OpCovInputCount(orgRootCovenantId) == 1`, `OpCovOutputCount(orgRootCovenantId) == 1`;
   `rootIn = OpCovInputIdx(orgRootCovenantId, 0)`, `rootOut = OpCovOutputIdx(orgRootCovenantId, 0)`.
2. `sigLen = OpTxInputScriptSigLen(rootIn)`; `redeemStart = sigLen − (rootPrefixLen + rootStateLen + rootSuffixLen)`;
   `redeem = OpTxInputScriptSigSubstr(rootIn, redeemStart, sigLen)`;
   `prefix = substr(redeemStart, redeemStart + rootPrefixLen)`; `suffix = substr(sigLen − rootSuffixLen, sigLen)`;
   `require(blake2b(prefix + suffix) == rootTemplateVmHash)` (exactly the template
   identity `readInputStateWithTemplate` checks) and
   `require(tx.inputs[rootIn].scriptPubKey == new ScriptPubKeyP2SHFromRedeemScript(redeem))`
   (the P2SH commitment `readInputStateWithTemplate` checks).
3. `head = substr(redeemStart + rootPrefixLen, sigLen − rootSuffixLen − TAIL_LEN)`;
   `tailPrev = substr(sigLen − rootSuffixLen − TAIL_LEN, sigLen − rootSuffixLen)`
   where `TAIL_LEN` = the encoded length of `byte frozen` + `byte[8] rootNonce`
   pushes (expected 2 + 9 = 11; measure). Require the frozen push of `tailPrev`
   to be the 0x00 byte (root not frozen); extract `prevNonce` from the 8 nonce
   bytes (`int(bytes)`).
4. Expected successor tail: frozen push of `expectFrozenAfter` + nonce push of
   `OpNum2Bin(prevNonce + 1, 8)` (build the pushes byte-exactly as silverc encodes
   them — verify by compiling a root state and reading the bytes).
   `expectedRedeem = prefix + head + tailNew + suffix`;
   `require(tx.outputs[rootOut].scriptPubKey == new ScriptPubKeyP2SHFromRedeemScript(expectedRedeem))`.
   Because the root's own script validates its successor with `validateOutputState`
   in the same transaction, the two pins agree on honest paths; every other root
   path (ROTATE/UNFREEZE/RECOVER/SUCCESSION) changes HEAD or the frozen byte in a
   way the vault's expected bytes do not, and D1 keeps SUCCESSION distinguishable.
5. Family closure unchanged (§3 item 5).

### 9.3 Vault entrypoints

- MERGE `ownerControl` and `emergencyPause` into ONE `#[covenant.singleton]`
  entrypoint `ownerControl(prev, new, opSelector)` with selectors 0..4 (0
  setAgentRoot, 1 topUpReserve, 2 pause, 3 unpause, 4 EMERGENCY pause); the
  root-authorization block is called ONCE with `expectFrozenAfter = (opSelector == 4 ? 1 : 0)`;
  selector 4 keeps exactly the `emergencyPause` rules of §3.
- `ownerRecover` stays a separate termination-mode entrypoint (second call site of
  the now-cheap block).
- `require(periodLengthDaa > 0)` (D2) stays.

  the exact number and the per-site cost of the new block.

### 10.7 Deviations from section 9, with their source-level reasons

**D7 — `ownerM` / `emergencyK` / `recoveryM` stay `int` (CONDITION NOT MET).**
Section 9.1 says to retype the three small ints "if they do not encode at a
constant width in the state region". They DO. A state field's encoded chunk is
`data_prefix(fixed_type_size) || payload`
(`~/silverscript/silverscript-lang/src/compiler/compile.rs`
`encoded_field_chunk_size`), `fixed_type_size_ref` returns a constant 8 for
`int` (`compile.rs:591`), and the value is written by
`encode_fixed_size_value` as `serialize_i64(n, Some(8))` (`compile.rs:943`) —
a fixed 8-byte sign-magnitude little-endian encoding, zero-padded, never
minimal. Every `int` state field is therefore exactly 9 bytes wide for every
value, so the state region is already CONSTANT. Retyping them would have saved
21 B of root state and cost byte/int conversions at seven comparison sites, so
the condition being false, they were left alone. The measured `rootStateLen`
is 467 B, not the 443 B section 9.1 estimated: the estimate charged 1 B per
small int and 33 B for the org id, but every field carries a push prefix
(`data_prefix(1) = [OpData1]`, `data_prefix(8) = [0x08]`,
`data_prefix(32) = [0x20]`), so `byte` costs 2 B, `int` 9 B, `pubkey` 33 B.
`TAIL_LEN` is exactly the predicted 11 B (2 + 9).

**D8 — the retyped tail needed BYTE-domain well-formedness (RULE STRENGTHENED).**
Phase 1 checked `0 <= frozen <= 1` numerically. With `frozen` a raw byte that
check is not sufficient: Kaspa's `deserialize_i64` reads `[0x80]` as negative
zero, i.e. `0` (`~/rusty-kaspa/crypto/txscript/src/data_stack.rs:190`), so
`0x80` would pass a numeric range check while equalling neither `0x00` nor
`0x01`. A root in that state could never AUTHORIZE, FREEZE or UNFREEZE again —
a permanent self-lock reachable only from a malformed genesis, but exactly the
class WF(S) exists to exclude. `V7OrgRootProbe2.sil` therefore requires the
byte to be one of the two canonical values and adds `int(rootNonce) >= 0`.
Both are probed (three new root-side rows).

**D9 — loop comparands hoisted out of the unrolled family-closure loops
(CODE SIZE ONLY, no rule change).** `for (i, 0, inCount, 8)` unrolls to its
compile-time bound, so a 32-byte literal inside the body is emitted as a
33-byte data push EIGHT times. `requireOnlyRootCovenantInputs` and
`requireOnlyRootAndTokenCovenantInputs` compare each foreign input's covenant
id against two 32-byte constants, so the naive form cost 528 B per inline site
in pushes alone. Binding both to locals before the loop makes each reference a
stack access. Measured effect: the rooted phase-2 delegate redeem drops from
10,913 B to 9,636 B (-1,277 B) with the compared values and the rule
unchanged; the hostile rows that exercise the rule ("foreign covenant family
riding an owner operation", "two inputs of the root family", "tokens riding an
owner control operation") are still REFUSED. `tokenAgentSpend`'s
`requireNoForeignCovenantInputs` was deliberately NOT touched: it is the
frozen v0.5 function verbatim.

**D10 — phase 1's per-call-site figure was overstated (METHODOLOGY
CORRECTION).** Section 7.5 measured "2,468 B per call site" by deleting the
whole `emergencyPause` entrypoint, which removes the entrypoint body and its
dispatch as well as one inline site. Phase 2 isolates the site exactly by
deleting only the `requireRootAuthorization(...)` CALL from `ownerRecover`
(test `v7p2_marginal_cost_of_one_root_authorization_site`). The phase-2
figure below is therefore a true marginal cost; the phase-1 figure is an upper
bound on its own block, not a like-for-like comparand. The like-for-like
comparison that matters is the whole delegate redeem, which is measured
identically in both phases.

**D6 — OWNER-RECOVER that leaves the HEAD unchanged is indistinguishable from
AUTHORIZE (OBSERVATION, present identically in phase 1).** Root action 4
requires `WF(new)` but not `requireSetPreserved`, and it carries `frozen`
across unchanged. A recovery quorum that supplies `new == prev` except the
nonce therefore produces a successor byte-identical to an AUTHORIZE successor,
so a rooted vault accepts a general owner operation in the same transaction.
Measured, not reasoned: `v7p2_observation_owner_recover_with_an_unchanged_head_looks_like_authorize`
runs it with `recoveryM = 2 < ownerM = 4` past the idle delay and BOTH inputs
accept. This is NOT an authority escalation — the same recovery quorum can
already rotate itself into the owner set (action 4 with a new set) and then
AUTHORIZE with the full quorum of that new set, so it reaches the same
outcome in two transactions instead of one — but section 3's wording ("the
root's successor is pinned to exactly AUTHORIZE ... any other root path ...
makes the vault operation invalid") is imprecise as written. Phase 1 had the
identical property (its `validateOutputStateWithTemplate` pinned the same
field values), so this is a pre-existing specification gap that the byte-level
pin neither introduces nor removes. Proposed hardening for the owner to
decide, NOT built in this phase because it changes section 2.4 semantics and
the root's byte geometry: require action 4 to land FROZEN
(`newState.frozen == FROZEN_YES`), mirroring succession. A recovery would then
be indistinguishable only from a FREEZE, whose sole vault effect is the
AUTHORITY-REDUCING emergency pause, and the recovered set would have to
UNFREEZE under its own full quorum before any general vault owner operation —
which also surfaces the recovery in every vault's manifest.

### 12.6 Deviations from the I1 specification, with source-level reasons

**I1-D1 — `rootStateLen` is 467 B, and the root redeem is 11,545 B, not the
probe's 11,546 B.** The 1-byte difference is decision D6 and nothing else
(a state-vs-constant comparison instead of a state-vs-state one). Recorded so
no reviewer mistakes it for drift.

**I1-D2 — the root's D9 hoisting is a no-op.** §11 lists D9 among the rules the
root generator must carry. D9 is "bind a loop's 32-byte comparands to locals
before an unrolled `for`", and the root covenant contains no loops at all
(counting is a half-split call chain, not a loop). The rule is therefore
carried where it exists — in the payment profile's two generalised family
closures — and is vacuous in the root. No behaviour was changed to satisfy it.

**I1-D3 — three hostile rows were added beyond the ported matrices.** The
production suites are supersets, not subsets, of §7.8/§10.8: (a) root — the
lighter emergency quorum attempting OWNER-RECOVER; (b) root — a forged `0x01`
gate byte over a SIGHASH_NONE *succession* signature (§7.8 forged the gate byte
only on an owner slot); (c) vault — `ownerRecover` under a FREEZE root
successor, i.e. the emergency quorum attempting to terminate a vault. All three
are REFUSED.

**I1-D4 — the recovery-path hostile rows now land FROZEN.** Under D6 an
OWNER-RECOVER landing unfrozen is refused by the frozen rule alone, which would
have masked what the four ported recovery rows (before the idle delay, disabled
sequence bit, recovery disabled, below the recovery quorum) are supposed to
prove. Each row therefore lands frozen so its refusal is attributable to the
rule it targets, and the "landing unfrozen" case is its own separate row.

**I1-D5 — the D6 consequence on the vault side is recorded, not eliminated.**
A frozen OWNER-RECOVER whose HEAD is unchanged is byte-identical to a FREEZE
successor, so it can still ride vault selector 4 (the EMERGENCY pause). This is
measured (`v7pay_d6_frozen_recovery_can_still_ride_only_the_emergency_pause`,
both inputs accept) and it is exactly the outcome §11 accepted when it adopted
D6: the reachable effect is AUTHORITY-REDUCING, and the recovered set must
UNFREEZE under its own full quorum before any general owner operation.

**I1-D6 — the encoder's unknown-version refusal is reported by the shared
signature field first.** For a pre-v0.7 `contractVersion` string the binary's
mandatory 65-byte `signature` parse runs before the version dispatch, so an
unknown version supplied WITHOUT a signature fails closed with "signature is
required" rather than "unknown contractVersion". Both refuse; only the message
differs. The test supplies a well-formed signature so the row proves the
version dispatch itself fails closed. No shared parsing order was changed,
because changing it would alter diagnostics for every existing generation for
no security gain.

only the set of runtimes that can compute it does.

### 13.8 Deviations from the I2 specification, with reasons

**I2-D1 — every v0.7 owner path takes its fee from an ordinary FUEL UTXO,
so the root never loses value.** §2.4's value rule permits the root to lose
up to `rootMaxFeePerTx` per transition, and a root-funded fee would need a
fee fixed point (as the reserve-funded delegate spend has). I2 requires fuel
instead — exactly the discipline the frozen v0.5 owner path already uses
("owner operations pin every covenant value, so the network fee MUST come
from an ordinary fuel UTXO") — and then ASSERTS the covenant's allowance
anyway via `assertRootValueRuleV7`, so a build can never quietly exceed it.
`accounting.kas.rootValueLoss` is therefore `0` on every honest path, and
`neg_root_value_drained` proves consensus refuses the violation. A
root-funded fee path is additive and can be added later without touching the
covenant.

**I2-D2 — a rooted-vault operation has no standalone manifest VERIFIER.**
`routeIntentManifestVerifier("policyvault-0.7-payment")` refuses with
`VERIFY_WITHIN_PARENT`. A rooted vault's authority IS its root input;
verifying the vault half alone would produce a "VERIFIED" verdict for half
of the security property. The route table therefore exposes the BUILDER for
that version and names the parent manifest inside which it is verified.

**I2-D3 — the v0.7 core modules are NOT added to `web/core-bundle.js`.**
§11.1 explicitly prefers not bundling yet, and presentation is gate I3.
The cross-runtime probe therefore tests the COMMITTED SOURCE's portability
(and, per I2-D3's motivating find, closed a real gap), not the shipped
bundle.

**I2-D4 — the encoder binary in this worktree was STALE.**
`tests/vm/target/debug/pv_call_encoder` did not contain the I1 v0.7 arms even
though `cargo build` reported it fresh: the checked-out source's mtime was
OLDER than the binary's, so the fingerprint never invalidated. It was rebuilt
after touching the source. The generator now fails closed with an explicit
message if the encoder returns an implausibly short v0.7-root call, so a
stale binary can never silently produce a different generation's bytes. This
is an ENVIRONMENT class finding, not a product defect — but it is exactly the
failure mode the production-byte rule exists to catch, so it is recorded.

**I2-D5 — Schnorr signing draws fresh auxiliary randomness.** Every negative
vector that edits a signature slot must edit the bytes the finalizer actually
placed, not a freshly-signed equivalent. The generator therefore produces
each slot signature EXACTLY ONCE and reuses it. Recorded because the first
generator run failed loudly on this and a silent version of the same mistake
would have produced negatives that reject for the wrong reason.

**I2-D6 — no v0.7 reconciler, because there is no v0.5 one to make version
aware.** §11.1 asks for "reconcile helpers if the v5 ones need version
awareness". There are none: `sdk/src/reconcile-v4.js` resolves its manifest
through `resolveV4Abi` and therefore ALREADY fails closed on any v0.5, v0.6
or v0.7 manifest, and `reconcile-v2.js` pins `CONTRACT_VERSION_V2` outright.
Nothing needed changing, and adding a v0.7 reconciler before the live
lifecycle exists (gate I5) would be writing chain-reconciliation logic with
no chain to reconcile against — precisely the "only proven chain
reconciliation advances the live manifest" rule read backwards. Recorded so
the omission is a decision, not an oversight.

effectively decoupled, which is the property that matters — an organization is
never priced into a smaller, weaker owner set.

**Per organization vs per vault.** The root is created once per organization
and each vault once (0.002083 KAS each). Root-only governance is charged per
ORGANIZATION; a rooted owner operation is charged per operation and costs about
the two covenant redeems added together; delegate spending never touches the
root and its cost is independent of the owner set, the thresholds and the
number of vaults. The v0.7 profile adds the measured **+363 B** of redeem to
every delegate spend versus frozen v0.5 — exactly **+0.000726 KAS (+3.0 %)** at
the transient rate of 200 sompi/byte.

**THE SERIALIZATION POINT.** `rootAction` is `#[covenant.singleton]`, so every
transaction needing owner authority spends the SAME UTXO: all root-authorized
operations of one organization are STRICTLY SERIAL, and a loser must be rebuilt
against the new root state and re-approved. That is the same fact that makes
the root outpoint the freshness kill switch. Delegate spending is NOT
serialized. Multi-vault batching is architecturally permitted (the covenant's
per-vault check is satisfied by one shared root input, and the manifest already
models a list of operations) but the SDK builds one vault operation per
transaction, so no batched shape was built, measured, or claimed — recorded as
an open item.

> **ADDENDUM (2026-09-03, post-freeze documentation correction — independent adversarial review probe 20, coordinator-verified in source):** the sentence above holds for the ROOT's own check only. ### 14.8 Deviations from the I3/I4 specification, with reasons

**I3-D1 — there is no `core/signer/v2`, so the slot path is layered on the
FROZEN `policyvault-signer/1` interface.** §11.1 names a "USI v2 request
shape", but no v2 exists in this tree (`policyvault-signer/2` appears only as a
hostile unknown-version fixture), and the UNIVERSAL SIGNER INTERFACE is a
separate roadmap item. Inventing an interface generation inside this gate would
have created a second signer contract with no adapters, no conformance suite
and no review. The slot path therefore declares its OWN versions
(`policyvault-org-root-slot-request/1` / `-response/1`) and builds the
underlying request through the existing `createTransactionSigningRequest`, so
every v1 adapter — CLI, air-gapped, hardware, extension, HSM, MPC — works
unchanged and the closed v1 error vocabulary is never extended.

**I3-D2 — the cryptographic slot↔key binding is the covenant's, with two core
guards in front of it.** Portable core contains no cryptography by design
(`core/signer/interface.js` identity boundary), and the vendored WASM exposes
no raw Schnorr verify over a transaction sighash. The slot path therefore binds
what it CAN see — the signer's own reported public key against the slot's key
(the SLOT-KEY GATE), and every structural binding of the envelope — and accepts
an OPTIONAL injected verifier whose failure is fatal. The signature itself is
verified by the root covenant's per-slot `checkSig` under consensus, proven on
the real engine by `tests/vm/tests/v7_sdk_integration.rs`.

**I3-D3 — the real-Schnorr end-to-end signer test lives in the SDK suite, not
under `core/signer/adapters/cli/test/`.** It needs the production builders
(silverc + the encoder) to produce a real v0.7 root transaction for the
adapters to sign; putting that in the CLI adapter's own suite would give a core
package a compiler dependency. It is classified
REQUIREMENT_NOT_AVAILABLE-skippable like every other build-dependent SDK suite.

**I3-D4 — a standalone `policyvault-rooted-vault-manifest/1` is EXPLAINED only
as a refusal.** The gate asks for explanations of both manifest versions; the
rooted-vault version is rendered as a CHILD of a verified parent (that is where
its authority is), and handed to `structured` on its own it refuses with
`verifyWithinParent`. Rendering the vault half alone as a normal approval would
contradict I2-D2 and present half of the security property as the whole one.

**I4-D1 — the threshold sweep is BUILT at every active-slot count, not
extrapolated.** The constant-size property could have been used to derive rows
1..12 from one measurement plus the budget model. All twelve were built,
finalized and measured instead, which is what turned the crossover at ten
active slots from a prediction into an observation.

**I4-D2 — the v0.5 comparison row is DERIVED, not re-measured.** The v0.5
delegate-spend row in the economic record is computed from the measured +363 B
redeem delta of §12.3 at the transient rate, and is labelled derived. A fresh
v0.5 build was not made because the frozen v0.5 controller is unchanged and the
delta is already an engine measurement.

**I4-D3 — no batched multi-vault shape was measured.** See THE SERIALIZATION
POINT: the SDK builds one vault operation per transaction, so a batched saving
would have been a claim without bytes behind it.
