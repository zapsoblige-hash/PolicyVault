# v0.7-kas rooted KAS safe-payment profile — ECONOMIC VIABILITY (gate I4)

Consensus validity and standardness are necessary, not sufficient. This
record computes what the ROOTED KAS SAFE-PAYMENT PROFILE
(`contracts/PolicyVault.v0.7-kas.sil`, contract `PolicyVaultRootedKas`)
actually costs in KAS network fees under CURRENT mainnet fee policy
(rusty-kaspa v2.0.1, post-Toccata), at MINIMAL required compute budgets, for
its representative transaction shapes. It is the sibling of
`docs/postlaunch/v0.7-economic-viability.md` (the rooted payment/token
profile); read that record for the root-only and per-organization curve,
which this profile shares unchanged (same root covenant).

**Every number below is measured through the real TxScriptEngine**
(`tests/vm/tests/v7_kas_production.rs`, test `v7kas_economic_viability_minimal_budgets`
and the surrounding measurement suite, release build, 2026-09-03). Nothing is
estimated: the committed compute budgets are the MINIMAL values
`core/model/compute-budget-v7-kas.js` derives from priced-engine measurements
(sig-op pricing 100,000 units/executed checkSig), and every transaction below
was executed and ACCEPTED at that exact budget before its mass was measured.

**Finding — the KAS profile costs more per transaction than the payment
profile, for a specific, expected reason.** This profile carries the full
v0.4.1 vault-level M-of-N approver machinery (10 approver slots, a
650-byte approval blob, 45-pair distinctness checks, two half-count helper
frames) so that individual delegate spends above a per-agent threshold can
require a SECOND, vault-wide approval tier — a security capability the
payment profile does not have at all (it inherits the frozen v0.5 model,
which has no approver tier). That capability is not free: it roughly
doubles the vault redeem size and is the majority of the static sig-op
difference (11 vs 1). An organization that does not need the vault-level
approval tier (approvalM = 0, no approvers configured) still pays for the
approver machinery's PRESENCE in the redeem (SilverScript inlines every
function at every call site regardless of whether a given call exercises
it), but pays NOTHING extra in EXECUTED sig-ops or script units for that
tier when it is unused (compare the honest-owner-op measurements: selector
1, `ownerSetApprovers`, is the only owner selector whose script units differ
meaningfully from the others — 364,474 vs ~359,400 — because it is the only
one that walks the approver set).

## Per-organization cost model

Reuses `docs/postlaunch/v0.7-economic-viability.md`'s per-organization
findings UNCHANGED for the root side (root genesis, root-only governance,
the owner-set curve 1-of-1..12-of-12, the dead-man's-switch heartbeat cost,
THE SERIALIZATION POINT): none of that depends on which rooted-vault profile
the organization also runs, since the root covenant is byte-identical. What
changes for an organization choosing the KAS profile over the payment
profile is:

- **rooted vault genesis**: unmeasured for this profile specifically (not
  yet built through a genesis-shape test); expect a small, roughly
  redeem-size-proportional constant similar to the payment profile's
  0.00208 KAS, since genesis has no counting/proof cost.
- **owner operations cost ~+40%** more than the payment profile
  (0.0644 vs 0.0461 KAS) — the vault-level approver machinery's redeem-size
  tax applies to every owner operation regardless of whether that operation
  touches approvers.
- **delegate spending costs ~+64%** more than the payment profile at the
  basic shape (0.0404 vs 0.0246 KAS), and the gap narrows in RELATIVE terms
  at production proof depths (0.0422 vs an unmeasured-for-this-profile
  deeper shape) since the fixed redeem-size tax is amortized over a larger
  transaction.

## Honest limits

1. **Relay floor only.** Every number is the consensus MINIMUM; a fee market
   above the floor multiplies all of them linearly.
2. **Rooted vault genesis, root genesis, and the vault-level M-of-N approval
   tier itself (a spend requiring vault-wide approvals, not just the agent's
   own threshold) were NOT separately mass-measured for this profile** — only
   the owner operations and the below-threshold delegate spend shapes were.
   A spend that also exercises the approver tier would cost more (it carries
   up to 650 B of approval signatures and up to 10 EXECUTED checkSigs,
   priced at 100,000 units each — see the `v7kas_worst_case_stack_and_execute`
   / `v7kas_measure_priced_worst_case_delegate_spend` measurements in
   `tests/vm/tests/v7_kas_production.rs`: the worst case, depth 12/16 + a
   10-of-10 approval, prices at 1,317,007 units, required budget 131 —
   roughly 5x the basic shape's budget).
3. **No KAS price.** Costs are in KAS only.
4. **These are TESTNET-shaped measurements of production bytes on the real
   TxScriptEngine, not live testnet or mainnet transactions.** v0.7-kas is
   NOT testnet-verified (gate I5). Nothing here
   is an audit, and this covenant is a CANDIDATE, not frozen.
5. **Budgets are MINIMAL-but-safe, not exact-to-the-unit.** The compute-
   budget-v7-kas.js model adds a fixed HEADROOM (20,000 units) and rounds up
   generously in several places (see that file's header comment); a
   production SDK would use the same model, so real transactions would carry
   the same small margin above the true minimum this record measured.


## Correction (2026-09-03, Wave 2): KIP-9 storage mass and UTXO plurality

Every storage-mass figure in this record was computed with the plurality-1
model (`core/model/storage-mass.js` before commit 6b9da7e). rusty-kaspa
v2.0.1 weighs each UTXO by its storage plurality p = ceil((63 + script
length + 32 if it carries a covenant id) / 100), contributing C·p²/amount —
a covenant-bearing P2SH output has p = 2 and therefore weighs FOUR times the
plain-output estimate used here. Consequences: (1) the dust / minimum-output
thresholds stated for covenant outputs (token notes, protocol-fee outputs,
covenant successors) are understated by up to 4×; the exact numbers are now
produced by the corrected module and enforced pre-sign by the builders'
storage-mass preflight; (2) no live evidence is invalidated (every accepted
transaction was accepted by the node under the correct rule); (3) the
frozen covenant bytes are unaffected (storage mass is not a covenant rule).
Found live on 2026-09-03 when an HD level-1 spend with a 0.05 KAS covenant
carry was refused at 840,919 grams (pinned as an exact regression vector in
`core/model/test/storage-mass-plurality.test.js`).

## KIP-9 plurality — quantitative re-check (2026-09-04, post-Wave-2 hardening)

Re-checked with the exact corrected model (`core/model/storage-mass.js`,
plurality 2 for covenant-bearing P2SH cells). This profile's shapes are
MINIMALLY affected: KAS delegate spends pay a PLAIN P2PK recipient
(plurality 1, unchanged) and owner operations carry only LARGE-amount
covenant outputs (vault + root successors), so corrected storage mass stays
small and well within the 500,000-gram limit (representative KAS delegate
spend ≈ 5,016 grams; representative owner op ≈ 20,178 grams). No
dust/minimum-carry threshold for this profile came from the old model or
changes under the correction. Frozen/candidate covenant bytes are
unaffected (storage mass is a consensus validity rule, not a covenant rule);
the builders' storage-mass preflight fails closed regardless.
