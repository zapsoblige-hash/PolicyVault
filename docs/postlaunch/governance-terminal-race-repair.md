# GOVERNANCE-TERMINAL-RACE-01 — finding, correction and evidence

Status: **repair included in the schema-011 successor of RC42.** It was implemented and independently reviewed during development, then backported unchanged in substance to the RC42 base, where it received its own independent review of the exact backport, RED-first reproduction on the RC42 base and PostgreSQL 16 parity on a fresh schema-011 database. RC42 carried the pre-repair `server/src/governance.js` (Git blob `7fa00638…`). No production incident is established.

## The finding

1. **Confirmed (reproduced RED-first before the repair, and again on the RC42 base):** every governance proposal transition (`cancelProposal`, `markProposalConsumed`) is serialised by a per-proposal create-only transition lock (`xlock-<proposalId>`) that any contender may reclaim once its **own** clock sees the lock as older than 30 s. A contender whose clock is skewed by >30 s removes a **live** holder's lock, re-arbitrates, and completes its own terminal transition; the original holder then performs its **unconditional** record write and replaces the contender's terminal evidence. Both callers observe success (`CANCELLED` and `CONSUMED`); the invariant is exactly one success.
2. **Confirmed here (the previously unconfirmed "build-before-consume" question):** an AUTHORITY-EXPANSION build is admitted (`requireApprovedProposal`), built and durably saved with a verified intent manifest, and only then consumes the proposal. When consumption refuses (the proposal became terminal between admission and consumption), the API refuses the build response but the persisted request stayed finalizable/submittable: the finalize/submit gate re-verified only the manifest.

## The correction (smallest, additive; frozen bytes untouched)

- `server/src/governance.js` — the terminal transition itself is arbitrated by a create-only **terminal claim** (`xterm-<proposalId>`, schema `policyvault-governance-terminal-claim/v1`; `link()`/EEXIST on the JSON backend, `INSERT … ON CONFLICT DO NOTHING` on PostgreSQL) written **before** the record write. Exactly one contender creates it; every other contender refuses on the claim's terminal state without writing (`refuseTransition` codes unchanged; a same-request consume replay returns idempotently). Reads (`loadProposalRecord`) and listings (`listProposals`) overlay a present claim, so a crash after the claim but before the record write still reads terminal. The stale-lock reclaim stays (it serves crashed holders) but can no longer yield a second success. Claims are durable evidence and are never removed; the key prefix is outside the API id charset and claims are filtered from every listing.
- `sdk/src/store.js` — identity mapping for the claim schema (the same mechanism the lock uses).
- `server/src/metrics.js` — proposal counts consider proposal records only.
- `server/src/api.js` — a refused consumption marks the already-durable request `governanceConsumption: "REFUSED"` (+ code), audits `FAIL_CLOSED`, then refuses the response.
- `server/src/intent-records.js` — the finalize/submit gate refuses such requests (`GOVERNANCE_PROPOSAL_TERMINAL`), exactly like the intent-derivation `FAILED` marker; for a governed request with a recorded intent manifest it also re-checks the durable proposal truth at finalize/submit (the proposal must be CONSUMED by this request), so the gate does not depend on the persisted marker alone.
- `server/src/attestations.js` — such requests present decision `REFUSED`, never `AUTHORIZED`.

## Verification (RED-first, permanent regressions, sabotage sensitivity)

- `sdk/test/governance-terminal-race.test.js` — two real processes (fork), injected write hold in the first, `Date.now` offset +31001 ms in the second: RED on the unmodified code (both succeed), GREEN after the repair (exactly one success, record equals the winner, loser refuses deterministically); zero-skew control; crash-after-claim overlay and idempotent same-request replay; the losing branches of the claim arbitration; stale reclaim without a claim; SABOTAGE (per-call claim keys neutralise claim and overlay) resurrects the double success and restoring re-arms it.
- `sdk/test/governance-consume-refusal-fail-closed.test.js` — a cancel injected between admission and consumption: build refuses `GOVERNANCE_PROPOSAL_TERMINAL`, exactly one built request was persisted, and the finalize/submit gate refuses it (RED before, GREEN after); an ordinary consumed build stays finalizable; the finalize/submit durable-proposal re-check cases (a crash before the refusal marker, a proposal consumed by a different request) are pinned.
- `sdk/test/rc-gv1-governance-terminal.test.js` — unchanged regressions; the sabotage probe now shows defence in depth (guard alone neutralised → the claim still refuses; guard + claim keying neutralised → the live RC-GV-1 defect returns).
- `sdk/test/governance-terminal-race-pg.test.js` — the two-process race and the crash-after-claim overlay on PostgreSQL (`INSERT … ON CONFLICT DO NOTHING`); runs against a fresh schema-011 database and passes.
- Independent internal falsification reviews: two during development (the repair; its follow-up with the finalize-time proposal re-check, losing-branch tests and PostgreSQL parity) and one of the exact backport onto the RC42 base (REVIEW_PASS). All three reproduced RED→GREEN in isolated copies and confirmed sabotage sensitivity.
- Private receipts (RED/GREEN output, frozen candidate copies, review packs) are retained outside the public tree.

## What this does not establish

No production incident is established or repaired. Known residuals (LOW): a malformed terminal claim fails closed on read and transition paths but listings still show the proposal as open; after a crash between the claim and the record write the raw proposal record is not rewritten (reads overlay the claim; metrics count the raw status); a governed request whose consumption was refused stays listed as BUILT, and the unchanged web client does not yet explain that state before signing; attestations for governed v0.4 requests follow the finalize/submit gate's governance refusal (store-path attestation ladder), except where broadcast evidence exists: a request in a broadcast-pipeline state keeps its record, and a signed row (FINALIZED or PREFLIGHT_VERIFIED) with a receipt for its transaction id keeps its broadcast rung while the gate refuses it — a receipt that carries a request id (submit pipeline or request-scoped recovery) names the request that executed, but a vault-reconcile receipt (no request id) cannot distinguish a reconciled own transaction from an executed content-identical retry; an unsigned row whose content-identical retry executed is presented REFUSED like the gate, and its record does not mention the retry; a governed row built before this release whose proposal was not consumed by it, and that was marked STALE after its own transaction reached the chain, is presented REFUSED (a STALE row whose proposal it consumed, or an ungoverned one, is still presented AUTHORIZED with a STALE failure); the refusal-marker branch presents REFUSED regardless of broadcast (reachable over a broadcast only after an image-only return to RC42), and so do the intent-verification branches (reachable over a broadcast only through tampering or a verifier change); and some gate/attestation differences on tampered records remain. Informational: a governed request interrupted before its intent manifest is recorded skips the finalize/submit re-check while its proposal stays open, and a request built before this release that shares another request's content-identical manifest record is not bound to its own proposal by the re-check. Clock skew between processes remains possible; the claim makes the outcome exactly-one regardless of it. Rollback: an image-only return to RC42 is not a qualified recovery once this release has written records — RC42 ignores the terminal claims and the `REFUSED` marker, so a proposal whose claim landed without its record write reads as open and a refused request becomes finalizable again. Recovery is forward-only.
