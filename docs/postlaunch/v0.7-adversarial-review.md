## 3. What was NOT probed, and why

- **Argument-aliasing at the owner-counting call site.** Source-level
  analysis (not an engine probe): `countOwnerApprovals` calls
  `countSixOwners` exactly twice with hardcoded literal byte offsets (0 and
  390) and hardcoded state-field references (`s.owner1`..`s.owner12`); there
  is no runtime-indexed or caller-supplied offset anywhere in the counting
  path. Aliasing one slot into two count sites is not a reachable shape in
  this bytecode — a transaction cannot parameterize which state field or
  which blob offset a given `checkSig` call inspects. Probe [D] (the
  low/high split boundary) and the existing "one signature replayed into a
  second slot" / "duplicate owner key" rows in `v7_root_production.rs`
  jointly cover the practical consequences of this architecture. Not probed
  further because there is no parameter surface to attack.
- **Cross-generation substitution, the reverse direction and v0.6.** Probe
  [C1] used a real v0.5 controller as the impostor "root"; a v0.6 impostor
  was not separately built (its redeem is comparably alien in geometry to
  v0.7-root's, and the defense mechanism [C1] exercises — the P2SH/template
  hash check at `requireRootAuthorization` step 1 — does not depend on which
  wrong contract is presented, only on its geometry disagreeing with the
  pinned lengths, which every other generation's redeem does). Presenting a
  v0.7-root *state region* to the *payment* covenant's own pin (rather than
  to another covenant) was not separately built; it collapses to the same
  P2SH/hash check family [B1]-[B3] and [C1] already exercise from different
  angles. Time-budget decision, not a blocked probe.
- **Recovery-destination type confusion** (`recipientNew.identifierType =
  IDENTIFIER_COVENANT_ID` instead of `IDENTIFIER_PUBKEY` on `ownerRecover`).
  Would require a real KCC20 token-pin derivation (this suite deliberately
  uses a fixed dummy `TokenPin` since no other probe here touches token
  state); the existing suite's "recovery redirected to an attacker key" /
  "recovery paying out only part of the token position" rows already cover
  the destination-value redirection class. Deprioritized for time budget,
  not attempted.
- **Stack headroom under hostile argument shapes / oversized pushes.** The
  existing production suites already measure `MAX_STACK_SIZE` headroom on
  the worst-case HONEST path for both covenants (root ROTATE 12-of-12:
  headroom 83; vault `tokenAgentSpend`: headroom 117). This review did not
  construct a new hostile stack-padding probe; SilverScript's argument
  model reads fixed positions relative to the top of the stack, so
  leading/trailing padding on an otherwise-conforming call was judged low
  incremental risk relative to the probes actually built, given the time
  budget.
- **Live testnet-10 negative validation.** Out of scope for this review
  (VM/engine only, matching the earlier v0.6 adversarial review's scope);
  the design record's own I5 gate already ran 9 authorized testnet
  negative-validation transactions independently of the application.

## 4. Findings, classified

**FUNDS-CRITICAL:** none found.

**AUTHORITY-CRITICAL:**

- Every guard probed (succession/recovery well-formedness on the new set,
  the predecessor well-formedness check on `rootSuccession`, the
  low/high split counting boundary, the `emergencyK`/`recoveryM`
  lower bounds, the byte-level root-pin geometry, the v0.5-impostor
  substitution) held. **No probe produced an authority escalation, a funds
  movement, a recovery redirect, or a state mutation without the stated
  quorum against the frozen candidate bytes.**
- The one probe that DID produce such an outcome — probe 18, `zero owner
  quorum participation authorizes an EMERGENCY pause` — did so **only**
  against `contracts/experiments/V7ReviewNoD1.sil`, a measurement-only file
  that is not, and has never been, an acceptance candidate. It exists
  specifically to answer the question "is D1 load-bearing?" The answer,
  proven on the real engine and stated exactly: **yes.** Without D1, a bare
  successor key (an escape-hatch key distinct from both the owner set and
  the emergency quorum) can make `rootSuccession` produce a state
  byte-identical to what a legitimate `K`-of-`N` emergency-quorum FREEZE
  produces (owner set unchanged, `frozen` 0→1, nonce+1) — and a real,
  unmodified `PolicyVault.v0.7-payment.sil` vault's byte-level pin, which by
  design never inspects *which* root entrypoint ran (only the resulting
  bytes), accepts it as authorization for `ownerControl(4)`. That is an
  outsider-relative-to-the-emergency-quorum reaching an
  AUTHORITY-REDUCING-but-still-real vault mutation with zero owner
  participation. Probe 19 then re-ran the identical shape against the REAL
  candidate (D1 present) and confirmed the root refuses it
  (`VerifyError`); the vault's own independent check on that same input,
  checked separately and reported only as context, returned `Ok()` —
  which is expected and correct, because the vault's security boundary is
  never "did the right entrypoint run," it is "did the root's own script
  (which does enforce D1) actually authorize this successor" — one failing
  input fails the whole transaction. **Conclusion: D1 is load-bearing, is
  present in the byte-frozen candidate, and closes the gap it exists to
  close. This is evidence FOR the freeze, not a falsification.**

**DEFENSE-IN-DEPTH:** probes 2, 3, 13 confirmed guards that are provably
redundant with a stronger guard elsewhere (blob-length checks that are also
implied by the fixed 780-byte total; the sentinel-zero skip that no
transaction shape could bypass given the fixed-offset counting
architecture) but are worth having and worth having proven, since a future
additive version could change that architecture.

**DOCUMENTATION:** probe 20. `docs/postlaunch/v0.7-organizational-root-design.md`
section 14.5 states multi-vault batching is "architecturally permitted (the
covenant's per-vault check is satisfied by one shared root input, and the
manifest already models a list of operations)," and
`docs/postlaunch/v0.7-byte-freeze-readiness.md` section 5 item 3 records it
as "permitted by the covenant... but NOT built by the SDK and NOT
measured." This review measured it for the first time and found the claim
does **not** hold for the `ownerControl` entrypoint as implemented: its own
`requireOnlyRootCovenantInputs` (contracts/PolicyVault.v0.7-payment.sil,
called once from `ownerControl` and once from `ownerRecover`'s no-token
branch) requires every input other than itself and the pinned root family
to carry a **zero** covenant id — so a second vault's own (non-zero,
non-root) covenant id is treated as an unaccounted foreign rider, and the
transaction is refused from BOTH vaults' own perspective, even in the most
permissive case tested (both vaults requesting the identical selector under
the identical root successor). The root's own script does not care — its
check is satisfied regardless of how many vault siblings ride along, which
is presumably what the design record's sentence was describing — but each
VAULT's own closure rule was apparently never checked against a second
vault instance before this review. **Direction is safe**: the candidate is
*more* restrictive than documented, not less; nothing here allows an
authority escalation, a funds movement, or a state mutation beyond what the
single-vault rows already prove. It is a documentation-accuracy gap, to be
corrected in the design record (either the sentence, or — if multi-vault
batching under one root successor is a wanted capability — a future
additive change to `requireOnlyRootCovenantInputs` to also permit inputs of
*any* covenant family sharing the *same* pinned `orgRootCovenantId`, which
is out of scope for this review to design).

**INFORMATIONAL:**

- Probe 1 (`OWNER-RECOVER` while already frozen accepted): confirms an
  asymmetry between action 4 (no `prevState.frozen==0` precondition) and
  actions 0/2 (which do require it) is intentional and safe — D6 already
  forces the successor to land frozen regardless of the predecessor's
  frozen bit, and the required quorum (`recoveryM`) and the idle-age gate
  are unaffected either way. Recorded because it was not previously an
  engine-proven honest path.
- Probe 10 (`AUTHORIZE` with zero value loss): confirms
  `requireRootValueRule` is a genuine lower bound (`>=`), not an implicit
  minimum-fee requirement; a fully fuel-subsidized, zero-shrinkage
  transition is legal.
- Probe 17's engine evidence: presenting a structurally alien redeem (v0.5,
  ~9.3–9.6 KB) against the vault's pinned v0.7-root geometry (prefix 1 B +
  state 467 B + suffix ≈11 KB) drives the byte-offset arithmetic in
  `requireRootAuthorization` negative (`rootRedeemStart = rootSigLen -
  (rootPrefixLen + rootStateLen + rootSuffixLen)`). The engine returned a
  clean `TxScriptError::InvalidIndex(-2202)` — a proper, bounds-checked
  script-validation refusal, not a Rust panic or any other uncontrolled
  failure. This is a small but genuine piece of engine-robustness evidence:
  the underlying `OpTxInputScriptSigSubstr`-family opcode implementation in
  `~/rusty-kaspa` does not trust a negative computed offset, which matters
  because that computation is reachable by a misconfigured (not just
  malicious) vault genesis, per probes [B1]-[B3].

## 5. Explicit statement (required)

**Did any probe produce an ACCEPTED transaction in which a legitimate
delegate, a sub-quorum owner subset, the emergency quorum, or an outsider
exceeds the authority the design assigns them, moves protected value,
redirects recovery, or mutates state without the stated quorum?**

Against the two byte-frozen candidate files
(`PolicyVault.v0.7-root.sil` sha256 `69417514…`,
`PolicyVault.v0.7-payment.sil` sha256 `09cdbb6c…`): **no.** Every hostile
row against those exact bytes was refused; every honest row accepted
exactly the authority the design assigns. No delegate, no sub-quorum
subset, no emergency quorum, and no outsider was ever observed exceeding
its assigned authority, moving value, redirecting recovery, or mutating
state without the required quorum, in any transaction actually built
against the frozen bytes.

Against the measurement-only, non-candidate
`contracts/experiments/V7ReviewNoD1.sil` (never frozen, never proposed for
freezing, never referenced by any generator/SDK/production path): **yes,
once, by design** — probe 18, described in full in §4, is exactly the
counterfactual this review built to answer "what does D1 protect against."
It is evidence that the frozen candidate's D1 rule is necessary and
sufficient to close that gap, not evidence that the frozen candidate is
falsified.
